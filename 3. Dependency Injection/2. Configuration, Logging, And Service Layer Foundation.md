# 2. Injecting ILogger

## What

`ILogger` is used to write logs in ASP.NET Core.

Logs help us understand what is happening inside the application.

Simple meaning:

```text
ILogger records important application events, warnings, errors, and debugging information.
```

---

## Why

Without logging, production support becomes difficult.

For example, if a resident says:

```text
I submitted a complaint but it is not visible.
```

Then we need logs to check:

```text
Was the complaint form submitted?
Did validation fail?
Did the service method execute?
Did database save fail?
Was there an exception?
```

Logging helps with troubleshooting.

---

## When To Use Logging

Use logging when:

```text
Complaint is created
Complaint status is updated
Complaint details are requested
Invalid complaint ID is accessed
Exception occurs
Admin assigns complaint
Staff updates complaint progress
Dashboard data is loaded
```

---

## How To Inject ILogger In Service

Example:

```csharp
public class ComplaintService : IComplaintService
{
    private readonly ILogger<ComplaintService> _logger;

    public ComplaintService(ILogger<ComplaintService> logger)
    {
        _logger = logger;
    }
}
```

## Explanation

| Code                        | Meaning                                   |
| --------------------------- | ----------------------------------------- |
| `ILogger<ComplaintService>` | Logger specifically for ComplaintService  |
| `_logger`                   | Private field used inside service         |
| Constructor parameter       | ASP.NET Core injects logger automatically |
| `ILogger<T>`                | T tells which class is writing the log    |

---

## Example Usage

```csharp
public Task CreateComplaintAsync(ComplaintCreateViewModel model)
{
    _logger.LogInformation("Creating complaint with title: {Title}", model.Title);

    return Task.CompletedTask;
}
```

## Why Structured Logging Is Better

This is better:

```csharp
_logger.LogInformation("Creating complaint with title: {Title}", model.Title);
```

Than this:

```csharp
_logger.LogInformation("Creating complaint with title: " + model.Title);
```

Because structured logging keeps values searchable and cleaner in log systems.

---

## Smart Society Mapping

| Situation                  | Log Example                 |
| -------------------------- | --------------------------- |
| Resident creates complaint | Complaint creation started  |
| Admin views complaint      | Complaint details requested |
| Staff updates status       | Complaint status updated    |
| Invalid complaint ID       | Complaint not found         |
| Dashboard loads            | Dashboard summary requested |

---

## Common Mistake

| Mistake                                  | Correction                                   |
| ---------------------------------------- | -------------------------------------------- |
| Not using logs at all                    | Use logs for important operations            |
| Logging sensitive data                   | Never log passwords, tokens, or private data |
| Using only `Console.WriteLine`           | Use `ILogger` in ASP.NET Core                |
| Logging too much unnecessary information | Log meaningful events                        |
| Logging only errors                      | Also log important business actions          |

---

## Interview Line

**ILogger is injected into services or controllers to record application events, warnings, and errors. In the Smart Society project, I use logging to track complaint creation, status updates, invalid complaint access, and dashboard operations.**

# 3. Injecting IConfiguration

## What

`IConfiguration` is used to read configuration values from sources like:

```text
appsettings.json
appsettings.Development.json
Environment variables
User secrets
Command-line configuration
```

Simple meaning:

```text
IConfiguration helps read application settings without hardcoding them in code.
```

---

## Why

Hardcoding values is a bad practice.

Bad example:

```csharp
var maxFileSize = 5;
var uploadFolder = "wwwroot/uploads/complaints";
```

Better approach:

```text
Store these values in appsettings.json
Read them using IConfiguration
```

This makes the application easier to change without modifying code.

---

## Example appsettings.json

```json
{
  "ComplaintSettings": {
    "DefaultStatus": "New",
    "MaxAttachmentSizeInMB": 5,
    "AllowedAttachmentTypes": ".jpg,.jpeg,.png,.pdf"
  }
}
```

---

## Inject IConfiguration

```csharp
public class ComplaintService : IComplaintService

    private readonly IConfiguration _configuration;

    public ComplaintService(IConfiguration configuration)
    {
        _configuration = configuration;
    }
}
```

---

## Reading Configuration Value

```csharp

{
    var defaultStatus = _configuration["ComplaintSettings:DefaultStatus"];

    return defaultStatus ?? "New";

```

---

## Smart Society Mapping

Configuration can be used for:

```text
Default complaint status
Allowed file upload types
Maximum attachment size
Dashboard cache duration
Support email
Application display name
Environment-specific database connection
```

---

## Example Service With IConfiguration

```csharp
public class ComplaintService : IComplaintService
{
    private readonly ILogger<ComplaintService> _logger;
    private readonly IConfiguration _configuration;

    public ComplaintService(
        ILogger<ComplaintService> logger,
        IConfiguration configuration)
    {
        _logger = logger;
        _configuration = configuration;
    }

    public Task CreateComplaintAsync(ComplaintCreateViewModel model)
    {
        var defaultStatus = _configuration["ComplaintSettings:DefaultStatus"] ?? "New";

        _logger.LogInformation(
            "Creating complaint with title: {Title} and default status: {Status}",
            model.Title,
            defaultStatus);

        return Task.CompletedTask;
    }
}
```

---

## Common Mistake

| Mistake                                        | Correction                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------- |
| Hardcoding configurable values                 | Store them in appsettings.json                                      |
| Storing passwords directly in appsettings.json | Use user secrets or environment variables                           |
| Reading wrong key path                         | Use correct colon-based path like `ComplaintSettings:DefaultStatus` |
| Overusing IConfiguration everywhere            | For many settings, later use Options Pattern                        |
| Changing appsettings but not restarting app    | Some config changes may need app restart                            |

---

## Interview Line

**IConfiguration allows ASP.NET Core applications to read settings from appsettings.json, environment variables, and other configuration sources. It keeps configuration separate from application code.**

# 4. Injecting Application Services

## What

Application services contain business logic.

In our project:

```text
ComplaintService is an application service.
```

It handles complaint-related operations.

---

## Why

Controllers should not contain all business logic.

Bad controller:

```csharp
public class ComplaintsController : Controller
{
    public IActionResult Create(ComplaintCreateViewModel model)
    {
        // Validate business rules
        // Set default status
        // Create complaint object
        // Save to database
        // Write logs
        // Send notification
        // Return response

        return RedirectToAction("Index");
    }
}
```

This becomes difficult to maintain.

Better controller:

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    return RedirectToAction("Index");
}
```

Now business logic is inside service.

---

## Smart Society Application Services

We can gradually create:

```text
IComplaintService
ComplaintService

IDashboardService
DashboardService

IAssignmentService
AssignmentService

IFileUploadService
FileUploadService
```

For now, we start with:

```text
IComplaintService
ComplaintService
```

---

## Interface Example

```csharp
public interface IComplaintService
{
    Task CreateComplaintAsync(ComplaintCreateViewModel model);

    Task<List<Complaint>> GetAllComplaintsAsync();

    Task<Complaint?> GetComplaintByIdAsync(int id);

    Task UpdateComplaintStatusAsync(int complaintId, string newStatus);

    Task<DashboardSummaryViewModel> GetDashboardSummaryAsync();
}
```

---

## Common Mistake

| Mistake                                   | Correction                                            |
| ----------------------------------------- | ----------------------------------------------------- |
| Putting all business logic in controller  | Move logic into service                               |
| Creating too many tiny services too early | Start with meaningful services                        |
| Making service depend on controller       | Service should not depend on controller               |
| Returning View from service               | Service returns data/result, controller returns View  |
| Service directly handling UI messages     | Controller handles UI response, service handles logic |

---

## Interview Line

**Application services contain business logic and keep controllers clean. In the Smart Society project, ComplaintService handles complaint creation, listing, details, status updates, and dashboard-related complaint logic.**

# 6. Controller Responsibility

## What

A controller handles HTTP requests and returns responses.

Controller responsibility includes:

```text
Receive request
Validate basic model state
Call service layer
Handle result
Return View, Redirect, JSON, NotFound, or error response
```

---

## What Controller Should Not Do

A controller should not be overloaded with:

```text
Large business rules
Database queries everywhere
File system logic everywhere
Email sending logic
Complex calculations
Long workflow decisions
Repeated code
```

---

## Good Controller Example

```csharp
public class ComplaintsController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintsController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }

    [HttpPost]
    public async Task<IActionResult> Create(ComplaintCreateViewModel model)
    {
        if (!ModelState.IsValid)
        {
            return View(model);
        }

        await _complaintService.CreateComplaintAsync(model);

        TempData["SuccessMessage"] = "Complaint created successfully.";

        return RedirectToAction("Index");
    }
}
```

---

## Smart Society Controller Responsibility

`ComplaintsController` should handle:

```text
Opening complaint form
Receiving complaint form submission
Checking ModelState
Calling ComplaintService
Returning view or redirect
Returning NotFound when complaint does not exist
```

---

## Common Mistake

| Mistake                                         | Correction                                                 |
| ----------------------------------------------- | ---------------------------------------------------------- |
| Controller contains 300 lines of business logic | Move logic to service                                      |
| Controller directly manages database workflow   | Use service layer                                          |
| Controller returns data without validation      | Check ModelState                                           |
| Controller handles everything for all roles     | Split into Admin/Staff/Resident controllers or areas later |

---

## Interview Line

**A controller should handle request-response coordination, not heavy business logic. It should receive input, call the service layer, and return the appropriate response.**

Service responsibility includes:

```text

Call database layer later
```

# 10. Environment-Specific Settings Awareness

## What

Different environments may need different settings.

Common environments:

```text
Development
Testing
Staging
Production
```

ASP.NET Core supports environment-specific files such as:

```text
appsettings.json
appsettings.Development.json
appsettings.Production.json
```

---

## Why

Local development and production should not always use the same settings.

Example:

| Setting      | Development              | Production                   |
| ------------ | ------------------------ | ---------------------------- |
| Database     | Local SQL Server         | Production SQL Server        |
| Logging      | Detailed                 | Controlled                   |

| Debugging    | Enabled                  | Disabled                     |

Better:

```text

```

---

## Common Mistake

| Mistake                                    | Correction                        |
| ------------------------------------------ | --------------------------------- |

| Showing developer error page in production | Use friendly error page           |

---

## Interview Line

**Environment-specific settings allow the application to use different configuration values for development, staging, and production, such as different databases, logging levels, and error handling behavior.**

# 11. Testability Benefit Of DI

## What

Testability means how easily we can test code.

Dependency Injection improves testability because classes depend on interfaces.

---

## Why

If `ComplaintsController` depends on `IComplaintService`, then during testing we can provide a fake service.

Example:

```text
Real app uses ComplaintService
Test uses FakeComplaintService
```

Controller code does not change.

---

## Without DI

```text
Controller creates ComplaintService directly.
Test cannot easily replace it.
```

## With DI

```text
Controller asks for IComplaintService.
Test can inject fake implementation.
```

---

## Smart Society Example

We can test:

```text
If complaint exists, Details returns View
If complaint does not exist, Details returns NotFound
If form is invalid, Create returns same View
If form is valid, Create calls service and redirects
```

---

## Common Mistake

| Mistake                            | Correction                                        |
| ---------------------------------- | ------------------------------------------------- |
| Writing code that cannot be tested | Depend on interfaces                              |
| Creating dependencies manually     | Use constructor injection                         |
| Testing only UI manually           | Unit test service/controller logic where possible |
| Ignoring service separation        | Service separation improves testability           |

---

## Interview Line

**Dependency Injection improves testability because we can replace real services with fake or mock implementations during testing without changing the controller code.**

```csharp
using SmartSociety.Web.Interfaces;
using SmartSociety.Web.Models;
using SmartSociety.Web.ViewModels;

namespace SmartSociety.Web.Services
{
    public class ComplaintService : IComplaintService
    {
        private readonly ILogger<ComplaintService> _logger;

        public ComplaintService(
            ILogger<ComplaintService> logger,
            IConfiguration configuration)

            _logger = logger;
            _configuration = configuration;

        public Task CreateComplaintAsync(ComplaintCreateViewModel model)
        {
            var defaultStatus = _configuration["ComplaintSettings:DefaultStatus"] ?? "New";

            _logger.LogInformation(
                "Creating complaint. Title: {Title}, DefaultStatus: {DefaultStatus}",
                model.Title,
                defaultStatus);

            return Task.CompletedTask;
        }

        public Task<List<Complaint>> GetAllComplaintsAsync()
        {
            _logger.LogInformation("Fetching all complaints");

            var complaints = new List<Complaint>();

            return Task.FromResult(complaints);
        }

        public Task<Complaint?> GetComplaintByIdAsync(int id)
        {
            _logger.LogInformation(
                "Fetching complaint details for ComplaintId: {ComplaintId}",
                id);

            Complaint? complaint = null;

            return Task.FromResult(complaint);
        }

        public Task UpdateComplaintStatusAsync(int complaintId, string newStatus)
        {
            _logger.LogInformation(
                "Updating ComplaintId: {ComplaintId} to Status: {Status}",
                complaintId,
                newStatus);

            return Task.CompletedTask;
        }

        public Task<DashboardSummaryViewModel> GetDashboardSummaryAsync()
        {
            _logger.LogInformation("Fetching dashboard summary");

            var summary = new DashboardSummaryViewModel
            {
                TotalComplaints = 0,
                PendingComplaints = 0,
                InProgressComplaints = 0,
                ResolvedComplaints = 0,
                CriticalComplaints = 0
            };

            return Task.FromResult(summary);
        }
    }
}
```

```csharp
        {
            _logger.LogInformation("Complaint list page requested");

            var complaints = await _complaintService.GetAllComplaintsAsync();

            return View(complaints);
        }

        public async Task<IActionResult> Details(int id)
        {
            _logger.LogInformation(
                "Complaint details page requested for ComplaintId: {ComplaintId}",
                id);

            var complaint = await _complaintService.GetComplaintByIdAsync(id);

            if (complaint == null)
            {
                _logger.LogWarning(
                    "Complaint not found for ComplaintId: {ComplaintId}",
                    id);

                return NotFound();
            }

            return View(complaint);
        }

        [HttpGet]
        public IActionResult Create()
        {
            return View();
        }

        [HttpPost]
        public async Task<IActionResult> Create(ComplaintCreateViewModel model)
        {
            if (!ModelState.IsValid)
            {
                _logger.LogWarning("Invalid complaint creation form submitted");

                return View(model);
            }

            await _complaintService.CreateComplaintAsync(model);

            TempData["SuccessMessage"] = "Complaint created successfully.";

            return RedirectToAction(nameof(Index));
        }
    }
}
```

# 17. Common Mistakes

| Mistake                                           | Why It Is Wrong                     | Correction                           |
| ------------------------------------------------- | ----------------------------------- | ------------------------------------ |
| Putting all logic in controller                   | Controller becomes hard to maintain | Move logic to service                |
| Not using ILogger                                 | Debugging becomes difficult         | Inject and use ILogger               |
| Hardcoding settings                               | Changes require code modification   | Use appsettings.json                 |
| Injecting IConfiguration everywhere unnecessarily | Code becomes noisy                  | Use it where configuration is needed |
| Service returning View                            | Service becomes UI-dependent        | Controller returns View              |
| DbContext directly used in many controllers       | Business logic spreads everywhere   | Use service layer                    |
| Logging sensitive data                            | Security risk                       | Log only safe business events        |
| Ignoring environment settings                     | Production mistakes happen          | Use environment-specific config      |
| No interface for service                          | Harder to test/change               | Use interface for injected services  |
| Creating one huge service                         | Hard to maintain                    | Split by responsibility when needed  |

# 20. Short Answers

2. Logging helps troubleshoot issues, monitor behavior, and support production applications.
3. `IConfiguration` reads configuration values from appsettings, environment variables, and other sources.
4. Hardcoded settings make the application difficult to change and maintain.
5. appsettings can store logging settings, connection strings, upload limits, default statuses, and feature settings.
6. Controller handles request-response coordination.
7. Service contains business logic.
8. Service should remain UI-independent; controller decides which view or response to return.
9. Clean folder structure improves maintainability, readability, and teamwork.
10. Different environments need different databases, logging levels, and error settings.
11. DI allows real services to be replaced with fake/mock services during testing.
12. DI reduces tight coupling and makes implementations easier to replace.
13. Complaint creation, listing, details, status update, and dashboard summary methods are needed.
14. It should log important complaint operations and troubleshooting information.
