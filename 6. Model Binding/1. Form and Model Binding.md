# 1. What Is An HTML Form?

## What

An **HTML form** is used to collect user input and submit it to the server.

In ASP.NET Core MVC, forms are commonly used for:

```text
Creating records
Updating records
Searching data
Uploading files
Submitting filters
Changing status
```

In the **Smart Society Issue Management System**, the resident will use a form to raise a complaint.

---

## Smart Society Example

A resident wants to submit:

```text
Title: Water leakage in basement
Description: Water is leaking near parking area B2
Category: Plumbing
Priority: High
```

This data will be entered in an HTML form and submitted to ASP.NET Core.

---

## Basic HTML Form Example

```html
<form method="post" action="/Complaints/Create">
    <input type="text" name="Title" />
    <textarea name="Description"></textarea>
    <input type="text" name="Category" />
    <input type="text" name="Priority" />

    <button type="submit">Submit Complaint</button>
</form>
```

## Important Point

The `name` attribute is very important.

```html
<input type="text" name="Title" />
```

ASP.NET Core uses the `name` value to match form input with ViewModel property.

# 2. HTML Form Behavior

## What

When a user submits a form, the browser sends form data to the server.

The server receives that data and ASP.NET Core tries to bind it to an action method parameter.

---

## Flow

```text
Resident fills complaint form
↓
Resident clicks Submit
↓
Browser sends form data
↓
ASP.NET Core receives request
↓
Model binder reads form fields
↓
Form values are mapped to ViewModel properties
↓
Controller action receives ViewModel object
```

---

## Smart Society Flow

```text
Complaint form fields
↓
Title, Description, Category, Priority
↓
POST /Complaints/Create
↓
ComplaintsController.Create(ComplaintCreateViewModel model)
↓
ASP.NET Core fills model properties
```

# 3. GET Vs POST

## What

GET and POST are HTTP methods.

They are used for different purposes.

| Method | Purpose               | Example               |
| ------ | --------------------- | --------------------- |
| GET    | Read or display data  | Open complaint form   |
| POST   | Submit or change data | Submit complaint form |

---

## GET

GET is used to display a page or retrieve data.

Example:

```csharp
[HttpGet]
public IActionResult Create()
{
    return View();
}
```

This action shows the complaint creation form.

URL:

```text
/Complaints/Create
```

---

## POST

POST is used to submit data to the server.

Example:

```csharp
[HttpPost]
public IActionResult Create(ComplaintCreateViewModel model)
{
    return RedirectToAction(nameof(Index));
}
```

This action receives complaint form data.

---

## Smart Society Mapping

| User Action             | HTTP Method | Controller Action                        |
| ----------------------- | ----------- | ---------------------------------------- |
| Open complaint form     | GET         | `Create()`                               |
| Submit complaint form   | POST        | `Create(ComplaintCreateViewModel model)` |
| View complaint details  | GET         | `Details(int id)`                        |
| Search complaints       | GET         | `Index(string status)`                   |
| Update complaint status | POST        | `UpdateStatus(...)`                      |

---

## Common Mistake

| Mistake                                        | Correction                                                |
| ---------------------------------------------- | --------------------------------------------------------- |
| Using GET to save data                         | Use POST for data changes                                 |
| Using POST to open simple page                 | Use GET for displaying pages                              |
| Not separating form display and submit actions | Use GET action for display and POST action for submission |
| Returning View after successful POST           | Use RedirectToAction after successful POST                |

---

## Interview Line

**GET is used to retrieve or display data, while POST is used to submit data and change application state. In complaint creation, GET displays the form and POST submits the complaint.**

# 4. Form Fields And Name Attributes

## What

Each input field in a form should have a `name` attribute.

The `name` attribute is used by ASP.NET Core model binding.

---

## Example

```html
<input type="text" name="Title" />
```

This can bind to:

```csharp
public string Title { get; set; } = string.Empty;
```

---

## ViewModel

```csharp
public class ComplaintCreateViewModel
{
    public string Title { get; set; } = string.Empty;

    public string Description { get; set; } = string.Empty;

    public string Category { get; set; } = string.Empty;

    public string Priority { get; set; } = string.Empty;
}
```

---

## Matching Rule

| Form Field Name | ViewModel Property |
| --------------- | ------------------ |
| `Title`         | `Title`            |
| `Description`   | `Description`      |
| `Category`      | `Category`         |
| `Priority`      | `Priority`         |

If names do not match, binding may fail or values may remain empty.

---

## Bad Example

```html
<input type="text" name="ComplaintTitle" />
```

But ViewModel property is:

```csharp
public string Title { get; set; } = string.Empty;
```

ASP.NET Core will not automatically bind `ComplaintTitle` to `Title`.

---

## Better ASP.NET Core Tag Helper Example

```html
<input asp-for="Title" class="form-control" />
```

This automatically generates the correct `name` and `id`.

Generated output is similar to:

```html
<input class="form-control" type="text" id="Title" name="Title" />
```

---

## Smart Society Mapping

For complaint form, we should use:

```html
<input asp-for="Title" class="form-control" />
<textarea asp-for="Description" class="form-control"></textarea>
<select asp-for="Category" class="form-control"></select>
<select asp-for="Priority" class="form-control"></select>
```

This reduces manual mistakes.

---

## Common Mistake

| Mistake                               | Correction                               |
| ------------------------------------- | ---------------------------------------- |
| Wrong `name` attribute                | Match property name                      |
| Missing `name` attribute              | Add `name` or use `asp-for`              |
| Using `id` only                       | Model binding uses `name`, not only `id` |
| Typing field name manually everywhere | Use Tag Helpers with `asp-for`           |

---

## Interview Line

**ASP.NET Core model binding uses form field names to match input values with action parameters or ViewModel properties.**

# 5. Model Binder Overview

## What

The **model binder** is the ASP.NET Core component that maps incoming request data to action method parameters or model properties.

Simple meaning:

```text
Model binder reads data from request and fills C# objects.
```

---

## Sources Model Binder Can Read From

```text
Form data
Route values
Query string
Request body
Headers in some cases
Uploaded files
```

---

## Example

Form sends:

```text
Title=Water leakage
Description=Leakage near parking
Category=Plumbing
Priority=High
```

Controller action:

```csharp
[HttpPost]
public IActionResult Create(ComplaintCreateViewModel model)
{
    return View(model);
}
```

ASP.NET Core automatically creates and fills:

```text
model.Title = "Water leakage"
model.Description = "Leakage near parking"
model.Category = "Plumbing"
model.Priority = "High"
```

---

## Smart Society Flow

```text
POST /Complaints/Create
↓
Model binder checks form values
↓
Creates ComplaintCreateViewModel object
↓
Fills Title, Description, Category, Priority
↓
Passes model to Create action
```

---

## Common Mistake

| Mistake                                          | Correction                                    |
| ------------------------------------------------ | --------------------------------------------- |
| Thinking we manually read every form field       | Model binder does this automatically          |
| Field names do not match properties              | Keep matching names or use Tag Helpers        |
| Complex object structure not matching form names | Use correct naming for nested/complex binding |
| Ignoring ModelState                              | ModelState tells binding/validation status    |

---

## Interview Line

**Model binder maps incoming request data such as form values, route values, and query string values to action parameters or ViewModel properties.**

# 6. DefaultModelBinder Concept

## What

In older ASP.NET MVC, people often referred to the default model binder as `DefaultModelBinder`.

In ASP.NET Core, model binding is handled by the built-in model binding system.

For practical learning, understand it like this:

```text
ASP.NET Core has a default model binding system that automatically binds request values to action parameters and models.
```

---

## Why

This saves developers from manually writing code like:

```csharp
var title = Request.Form["Title"];
var description = Request.Form["Description"];
var category = Request.Form["Category"];
var priority = Request.Form["Priority"];
```

Instead, ASP.NET Core allows:

```csharp
public IActionResult Create(ComplaintCreateViewModel model)
```

---

## Smart Society Example

Form field:

```html
<input asp-for="Title" />
```

ViewModel property:

```csharp
public string Title { get; set; } = string.Empty;
```

Action:

```csharp
[HttpPost]
public IActionResult Create(ComplaintCreateViewModel model)
```

The built-in model binder connects these automatically.

---

## Common Mistake

| Mistake                                        | Correction                                                       |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| Manually reading all form values unnecessarily | Use model binding                                                |
| Assuming model binding saves to database       | Model binding only fills object; service/database logic saves it |
| Confusing model binding with validation        | Binding fills values; validation checks correctness              |
| Ignoring binding errors                        | Check ModelState                                                 |

---

## Interview Line

**ASP.NET Core has a built-in model binding system that automatically maps request data to action method parameters and model properties.**

# 8. Binding From Route

## What

Binding from route means ASP.NET Core reads values from the URL path and maps them to action parameters.

---

## Example URL

```text
/Complaints/Details/5
```

Action:

```csharp
public IActionResult Details(int id)
{
    return View();
}
```

Here:

```text
id = 5
```

comes from the route.

---

## Smart Society Example

```csharp
[HttpGet]
public async Task<IActionResult> Details(int id)
{
    var complaint = await _complaintService.GetComplaintByIdAsync(id);

    if (complaint == null)
    {
        return NotFound();
    }

    return View(complaint);
}
```

---

## Attribute Route Example

```csharp
[HttpGet("details/{id:int}")]
public IActionResult Details(int id)
{
    return View();
}
```

URL:

```text
/complaints/details/5
```

---

## Common Mistake

| Mistake                                              | Correction                             |
| ---------------------------------------------------- | -------------------------------------- |
| Route parameter name does not match action parameter | Use same name like `{id}` and `int id` |
| Not validating ID                                    | Check `id <= 0`                        |
| Not handling missing record                          | Return `NotFound()`                    |
| Passing string value to integer route                | Use route constraint `{id:int}`        |

---

## Interview Line

**Binding from route maps URL path values such as `/Complaints/Details/5` to action parameters like `int id`.**

# 9. Binding From Query String

## What

Binding from query string means ASP.NET Core reads values after `?` in the URL.

---

## Example URL

```text
/Complaints?status=Pending&priority=High
```

Action:

```csharp
public IActionResult Index(string? status, string? priority)
{
    return View();
}
```

ASP.NET Core binds:

```text
status = "Pending"
priority = "High"
```

---

## Why

Query strings are useful for:

```text
Searching
Filtering
Sorting
Pagination
Optional criteria
```

---

## Smart Society Example

Complaint list filters:

```text
/Complaints?status=Pending
/Complaints?priority=Critical
/Complaints?status=Resolved&priority=High
```

Action:

```csharp
[HttpGet]
public async Task<IActionResult> Index(string? status, string? priority)
{
    var complaints = await _complaintService.GetAllComplaintsAsync();

    return View(complaints);
}
```

Later, we will pass filters to service.

---

## Query String Vs Route Parameter

| Type            | Example                      | Best For                   |
| --------------- | ---------------------------- | -------------------------- |
| Route Parameter | `/Complaints/Details/5`      | Required resource identity |
| Query String    | `/Complaints?status=Pending` | Optional filters/search    |

---

## Common Mistake

| Mistake                                | Correction                            |
| -------------------------------------- | ------------------------------------- |
| Using route parameter for every filter | Use query string for optional filters |
| Putting sensitive data in query string | Avoid sensitive information in URL    |
| Not handling null filters              | Use nullable parameters               |
| Confusing `id` route with query value  | Understand path vs query              |

---

## Interview Line

**Binding from query string maps URL query values such as `?status=Pending` to action parameters, commonly used for filtering, searching, sorting, and pagination.**

# 11. ViewModel Binding

## What

**ViewModel binding** means binding form data to a ViewModel created specifically for a screen.

---

## Why

A ViewModel protects the application from overposting and keeps the form focused.

For example, the database `Complaint` entity may have:

```text
ComplaintId
Title
Description
Category
Priority
Status
CreatedByUserId
AssignedToStaffId
CreatedDate
ResolvedDate
InternalRemarks
```

But the complaint creation form should only accept:

```text
Title
Description
Category
Priority
```

So we create:

```text
ComplaintCreateViewModel
```

---

## ComplaintCreateViewModel

```csharp
namespace SmartSociety.Web.ViewModels
{
    public class ComplaintCreateViewModel
    {
        public string Title { get; set; } = string.Empty;

        public string Description { get; set; } = string.Empty;

        public string Category { get; set; } = string.Empty;

        public string Priority { get; set; } = string.Empty;
    }
}
```

---

## POST Action

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

---

## Why This Is Better Than Binding Entity Directly

Bad:

```csharp
public IActionResult Create(Complaint complaint)
```

Risk:

```text
User may submit values for Status, AssignedToStaffId, CreatedByUserId, etc.
```

Better:

```csharp
public IActionResult Create(ComplaintCreateViewModel model)
```

Only allowed form fields are accepted.

---

## Smart Society Mapping

| Form Field     | ViewModel Property      | Should User Provide?    |
| -------------- | ----------------------- | ----------------------- |
| Title          | `Title`                 | Yes                     |
| Description    | `Description`           | Yes                     |
| Category       | `Category`              | Yes                     |
| Priority       | `Priority`              | Yes                     |
| Status         | Not in create ViewModel | No, system sets it      |
| Assigned Staff | Not in create ViewModel | No, admin assigns later |
| Created Date   | Not in create ViewModel | No, system sets it      |

---

## Common Mistake

| Mistake                                              | Correction                          |
| ---------------------------------------------------- | ----------------------------------- |
| Binding database entity directly to create form      | Use ViewModel                       |
| Letting user submit status during complaint creation | System should set default status    |
| Putting all entity properties into ViewModel         | Only include required screen fields |
| Ignoring overposting                                 | Use ViewModels to reduce risk       |

---

## Interview Line

**ViewModel binding maps form data to a screen-specific class. It improves security and maintainability by accepting only the fields required for that screen.**

# 12. ModelState

## What

`ModelState` stores the result of model binding and validation.

Simple meaning:

```text
ModelState tells whether the submitted form data was successfully bound and valid.
```

---

## Why

Before processing submitted data, we should check:

```csharp
ModelState.IsValid
```

If the form has invalid or missing values, we should return the same form with errors.

---

## Example

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    return RedirectToAction(nameof(Index));
}
```

---

## What ModelState Contains

```text
Submitted values
Binding errors
Validation errors
Field-level error information
```

---

## Smart Society Example

If resident submits empty title:

```text
Title = empty
Description = Water leakage issue
Category = Plumbing
Priority = High
```

When validation attributes are added later, `ModelState.IsValid` becomes false.

The same form is returned with validation messages.

---

## Important Note

Model binding and validation are related but not same.

| Concept       | Meaning                              |
| ------------- | ------------------------------------ |
| Model Binding | Fills object with request values     |
| Validation    | Checks whether values are acceptable |
| ModelState    | Stores binding and validation result |

---

## Common Mistake

| Mistake                                                       | Correction                          |
| ------------------------------------------------------------- | ----------------------------------- |
| Not checking ModelState                                       | Always check before processing form |
| Redirecting when ModelState is invalid                        | Return same view with model         |
| Losing user-entered values                                    | Return `View(model)`                |
| Thinking ModelState only checks required fields automatically | Validation attributes are needed    |

---

## Interview Line

**ModelState stores model binding and validation results. We check ModelState.IsValid before processing submitted form data.**

# 18. Short Answers

1. An HTML form collects user input and submits it to the server.
2. `method="post"` sends form data using an HTTP POST request.
3. GET retrieves/displays data; POST submits data and usually changes application state.
4. Complaint creation changes application state, so it should use POST.
5. The `name` attribute helps the model binder match form values with model properties.
6. `asp-for` generates matching `name` and `id` attributes based on the model property.
7. Model binding maps request data to action parameters or model properties.
8. The built-in model binder reads request values and fills C# objects.
9. Binding from form maps submitted form fields to a model/ViewModel.
10. Binding from route maps URL path values to action parameters.
11. Binding from query string maps values after `?` in the URL to action parameters.
12. Binding to complex classes maps multiple values into one object.
13. ViewModel accepts only screen-specific fields and helps prevent overposting.
14. ModelState stores binding and validation results.
15. We check `ModelState.IsValid` before processing submitted data.
16. The property may remain empty or binding may fail.
17. Direct entity binding can expose fields that users should not control, such as Status or AssignedToStaffId.
18. Title, Description, Category, and Priority.
19. The controller should call the service and redirect to Index or details page.
20. The controller should return the same view with the submitted model.

# 22. Interview Explanation

Learner should be able to explain:

```text
In my Smart Society Issue Management System, I used ASP.NET Core model binding to bind complaint form data to a ViewModel.

The resident opens the complaint form using a GET Create action. The form contains fields such as Title, Description, Category, and Priority. When the resident submits the form, the browser sends a POST request to ComplaintsController.Create.

ASP.NET Core model binding reads the submitted form fields and creates a ComplaintCreateViewModel object. The controller checks ModelState and then passes the ViewModel to ComplaintService for complaint creation logic.

I used a ViewModel instead of binding directly to the Complaint entity because the create form should only accept fields that the resident is allowed to submit. Fields like Status, AssignedToStaffId, and CreatedDate should be controlled by the system, not by the user.
```
