# 1. Why This Topic Is Important

## What

In the previous topic, we learned login foundation using ASP.NET Core Identity.

Login tells the application:

```text
Who is using the system?
```

But after login, the application must also know:

```text
What is this user allowed to do?
```

This is where these concepts are used:

```text
Roles
Claims
Policies
Ownership checks
Security hardening
```

---

## Why

In Smart Society Issue Management System, every logged-in user should not have the same access.

Example:

```text
Resident can raise complaint
Resident can view only own complaints
Admin can view all complaints
Admin can assign complaint to staff
Staff can view assigned complaints
Staff can update only assigned complaints
```

Without proper authorization, a user may tamper with URL, form fields, or hidden inputs and access data that does not belong to them.

---

## Real-Life Analogy

Think of a society office.

A person enters after showing ID card.

That is authentication.

Then the office checks the person's role:

```text
Resident
Admin
Maintenance Staff
```

This is authorization.

Even after entering the office:

```text
Resident cannot open staff duty register
Staff cannot approve society budget
Admin cannot ignore audit trail
```

So login is only the beginning.

Security must continue on every important action.

---

## Smart Society Mapping

| User Type | Role | Allowed Work |
|---|---|---|
| Resident | `Resident` | Create complaint and view own complaints |
| Admin | `Admin` | View all complaints, assign complaints, monitor dashboard |
| Staff | `Staff` | View assigned complaints and update progress |
| Anonymous User | No role | View public pages only |

---

## Interview Line

**Authentication proves who the user is, while roles, claims, policies, and ownership checks decide what that user can safely access or modify.**

# 2. Roles

## What

A role is a named permission group.

Examples:

```text
Resident
Admin
Staff
```

A user can belong to one or more roles.

Example:

```text
Deepak = Resident
Kapil = Admin
Ramesh = Staff
```

---

## Why

Roles make authorization easier.

Instead of checking every user separately, we check the user's role.

Example:

```text
Only Admin can assign complaints.
Only Staff can update assigned complaint progress.
Only Resident can create complaint.
```

---

## Smart Society Roles

```text
Resident
Admin
Staff
```

---

## Role Constants

Instead of typing role names again and again, create one constants file.

### File: `Constants/AppRoles.cs`

```csharp
namespace SmartSociety.Web.Constants
{
    public static class AppRoles
    {
        public const string Resident = "Resident";
        public const string Admin = "Admin";
        public const string Staff = "Staff";
    }
}
```

---

## Why Use Constants?

Bad:

```csharp
[Authorize(Roles = "admin")]
```

Somewhere else:

```csharp
[Authorize(Roles = "Admin")]
```

This can cause confusion.

Better:

```csharp
[Authorize(Roles = AppRoles.Admin)]
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Typing role names manually everywhere | Use constants |
| Using different spellings like `admin`, `Admin`, `ADMIN` | Keep one fixed role name |
| Thinking role is same as login | Login proves identity; role controls access |
| Giving every user Admin role for testing | Test with separate users |
| Hiding admin menu only in view | Protect controller/action also |

---

## Interview Line

**A role is a named group of permissions such as Resident, Admin, or Staff, used to control what an authenticated user can access.**

# 4. Enable Roles In Program.cs

## What

Before using roles, Identity must be configured with role support.

---

## Program.cs Setup

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using SmartSociety.Web.Data;
using SmartSociety.Web.Models;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddIdentity<ApplicationUser, IdentityRole>()
    .AddEntityFrameworkStores<ApplicationDbContext>()
    .AddDefaultTokenProviders();

var app = builder.Build();

app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

---

## Important Point

This line is important:

```csharp
builder.Services.AddIdentity<ApplicationUser, IdentityRole>()
```

It means:

```text
Application uses custom ApplicationUser
Application also supports IdentityRole
```

---

## Middleware Order

Correct order:

```text
UseRouting
UseAuthentication
UseAuthorization
MapControllerRoute
```

---

## Why

```text
UseAuthentication reads login cookie
UseAuthorization checks roles, claims, and policies
```

Authorization cannot work properly before authentication.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using `AddIdentity<ApplicationUser, IdentityRole>` but forgetting `UseAuthorization` | Add authorization middleware |
| Calling `UseAuthorization` before `UseAuthentication` | Authentication should come first |
| Using `IdentityUser` in services but `ApplicationUser` in models | Keep type consistent |
| Forgetting migration after Identity changes | Add migration and update database |
| Not adding `Microsoft.AspNetCore.Identity` using | Add required namespace |

---

## Interview Line

**Role support is enabled by configuring ASP.NET Core Identity with ApplicationUser and IdentityRole, then using authentication and authorization middleware in the correct order.**

# 5. Seed Roles

## What

Seed roles means creating required roles automatically when the application starts.

For Smart Society, we want these roles:

```text
Resident
Admin
Staff
```

---

## Why

If roles are not created, assigning user to a role will fail.

Bad situation:

```text
User registered successfully
Application tries to assign Resident role
Resident role does not exist
Role assignment fails
```

So we create roles first.

---

## Step 1: Create Seed Service

### File: `Data/IdentitySeedData.cs`

```csharp
using Microsoft.AspNetCore.Identity;
using SmartSociety.Web.Constants;
using SmartSociety.Web.Models;

namespace SmartSociety.Web.Data
{
    public static class IdentitySeedData
    {
        public static async Task SeedRolesAndAdminAsync(IServiceProvider serviceProvider)
        {
            var roleManager = serviceProvider.GetRequiredService<RoleManager<IdentityRole>>();
            var userManager = serviceProvider.GetRequiredService<UserManager<ApplicationUser>>();

            string[] roles =
            {
                AppRoles.Resident,
                AppRoles.Admin,
                AppRoles.Staff
            };

            foreach (var role in roles)
            {
                bool roleExists = await roleManager.RoleExistsAsync(role);

                if (!roleExists)
                {
                    await roleManager.CreateAsync(new IdentityRole(role));
                }
            }

            await SeedDefaultAdminAsync(userManager);
        }

        private static async Task SeedDefaultAdminAsync(UserManager<ApplicationUser> userManager)
        {
            string adminEmail = "admin@smartsociety.com";
            string adminPassword = "Admin@12345";

            var existingAdmin = await userManager.FindByEmailAsync(adminEmail);

            if (existingAdmin != null)
            {
                return;
            }

            var adminUser = new ApplicationUser
            {
                UserName = adminEmail,
                Email = adminEmail,
                FullName = "Default Admin",
                EmailConfirmed = true
            };

            var result = await userManager.CreateAsync(adminUser, adminPassword);

            if (result.Succeeded)
            {
                await userManager.AddToRoleAsync(adminUser, AppRoles.Admin);
            }
        }
    }
}
```

---

## Step 2: Call Seed Method In Program.cs

Add this before `app.Run();`

```csharp
using (var scope = app.Services.CreateScope())
{
    var services = scope.ServiceProvider;

    await IdentitySeedData.SeedRolesAndAdminAsync(services);
}
```

Full bottom part:

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

using (var scope = app.Services.CreateScope())
{
    var services = scope.ServiceProvider;

    await IdentitySeedData.SeedRolesAndAdminAsync(services);
}

app.Run();
```

---

## Important Production Note

For real production, do not keep default admin password hardcoded.

Better production approach:

```text
Read admin email/password from secure configuration
Use environment variables
Force password change after first login
Use strong password
Restrict deployment access
```

For beginner lab, hardcoded admin helps us understand the flow.

---

## Smart Society Seed Result

After application starts:

```text
Resident role exists
Admin role exists
Staff role exists
Default admin user exists
Default admin user has Admin role
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Assigning role before creating role | Seed roles first |
| Hardcoding weak production password | Use secure configuration in production |
| Running seed without service scope | Create scope using `app.Services.CreateScope()` |
| Forgetting `await` | Use async properly |
| Not checking role/user exists | Avoid duplicate creation |

---

## Interview Line

**Role seeding creates required roles such as Resident, Admin, and Staff at application startup so users can be safely assigned to those roles.**

Example:

```text
Resident user → Resident role
Admin user → Admin role
Maintenance worker → Staff role
```

Identity stores this relation in:

```text
AspNetUserRoles
```

## Why

After login, ASP.NET Core can check the user's role.

Example:

```csharp
[Authorize(Roles = "Admin")]
```

This works only if the logged-in user has Admin role.

---

## Full Register POST Concept

```csharp
[HttpPost]

public async Task<IActionResult> Register(RegisterViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var user = new ApplicationUser
    {
        UserName = model.Email,
        Email = model.Email,
        FullName = model.FullName,
        FlatNumber = model.FlatNumber,

    }
}
```

# 8. Role-Based Authorization

## What

Role-based authorization allows or denies access based on the user's role.

Example:

```text
Admin can assign complaints.
Resident cannot assign complaints.
Staff can update progress.
```

---

## Smart Society Role Rules

```text
Resident can view only own complaints
Admin can assign complaints
Staff can update assigned complaints
```

---

## Resident Controller Example

```csharp
[Authorize(Roles = AppRoles.Resident)]
public class ResidentComplaintsController : Controller
{
    private readonly ApplicationDbContext _context;
    private readonly UserManager<ApplicationUser> _userManager;

    public ResidentComplaintsController(
        ApplicationDbContext context,
        UserManager<ApplicationUser> userManager)
    {
        _context = context;
        _userManager = userManager;
    }

    public async Task<IActionResult> MyComplaints()
    {
        var userId = _userManager.GetUserId(User);

        var complaints = await _context.Complaints
            .Where(c => c.ResidentId == userId)
            .ToListAsync();

        return View(complaints);
    }
}
```

---

## Admin Controller Example

```csharp
[Authorize(Roles = AppRoles.Admin)]
public class AdminComplaintsController : Controller
{
    private readonly ApplicationDbContext _context;

    public AdminComplaintsController(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<IActionResult> Index()
    {
        var complaints = await _context.Complaints
            .ToListAsync();

        return View(complaints);
    }
}
```

---

## Staff Controller Example

```csharp
[Authorize(Roles = AppRoles.Staff)]
public class StaffComplaintsController : Controller
{
    private readonly ApplicationDbContext _context;
    private readonly UserManager<ApplicationUser> _userManager;

    public StaffComplaintsController(
        ApplicationDbContext context,
        UserManager<ApplicationUser> userManager)
    {
        _context = context;
        _userManager = userManager;
    }

    public async Task<IActionResult> Assigned()
    {
        var staffId = _userManager.GetUserId(User);

        var complaints = await _context.Complaints
            .Where(c => c.AssignedStaffId == staffId)
            .ToListAsync();

        return View(complaints);
    }
}
```

---

## Important Note

Role check alone is not enough for ownership rule.

Example:

```text
Resident role allows access to MyComplaints page.
But database query must still filter by current ResidentId.
```

This is why we need ownership-based access also.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Role check but no data filtering | Filter data by current user |
| Staff can see all complaints because role is Staff | Filter by AssignedStaffId |
| Resident can open another complaint by changing ID in URL | Check complaint.ResidentId |
| Using UI menu as security | Protect server action and query |
| Returning all data then hiding in view | Filter at database query level |

---

## Interview Line

**Role-based authorization controls which role can access an action, but data-level filtering is still required to protect user-specific records.**

# 9. Claims Concept

## What

A claim is a piece of information about the user.

A claim has:

```text
Claim Type
Claim Value
```

Examples:

```text
FullName = Deepak Bajaj
FlatNumber = A-101
Department = Plumbing
CanApproveComplaint = true
```

---

## Role Vs Claim

| Concept | Meaning | Example |
|---|---|---|
| Role | User group | Admin |
| Claim | User-specific information | FlatNumber = A-101 |
| Policy | Authorization rule built from roles/claims/custom logic | Require Admin role |

---

## Why Claims Are Useful

Claims help store extra user information used by authorization or UI.

Examples:

```text
Resident flat number
Staff department
Admin permission level
Society block
```

---

## Add Claim To User

```csharp
using System.Security.Claims;

await _userManager.AddClaimAsync(user, new Claim("FlatNumber", "A-101"));
```

---

## Read Claim In Controller

```csharp
string? flatNumber = User.FindFirst("FlatNumber")?.Value;
```

---

## Example: Add Department Claim For Staff

```csharp
await _userManager.AddClaimAsync(staff, new Claim("Department", "Electrical"));
```

---

## Example: Read Department

```csharp
string? department = User.FindFirst("Department")?.Value;
```

---

## Smart Society Usage

| Claim | Example Value | Usage |
|---|---|---|
| `FlatNumber` | A-101 | Show resident flat in profile |
| `TowerBlock` | Tower A | Filter resident context if needed |
| `Department` | Electrical | Staff work category |
| `CanAssignComplaint` | true | Advanced permission awareness |
| `SocietyId` | 1 | Future multi-society support |

---

## Important Note

Do not put secret or sensitive data in claims unnecessarily.

Claims can become part of the authentication identity and may be stored in cookies depending on setup.

Use claims for small authorization/profile information only.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Thinking claims are only permissions | Claims are user information |
| Storing large data in claims | Keep claims small |
| Storing sensitive secrets in claims | Avoid secrets |
| Confusing role and claim | Role is group; claim is information |
| Depending only on claims for changing data | Re-check database when needed |

---

## Interview Line

**A claim is a small piece of information about a user, such as FlatNumber or Department, which can help with authorization or personalization.**

# 10. Policy-Based Authorization Awareness

## What

Policy-based authorization means creating named security rules.

A policy can require:

```text
Role
Claim
Multiple requirements
Custom rule
```

---

## Why

Policies make security rules more meaningful and centralized.

Instead of writing only:

```csharp
[Authorize(Roles = "Admin")]
```

We can write:

```csharp
[Authorize(Policy = "CanAssignComplaint")]
```

This reads closer to business language.

---

## Add Policies In Program.cs

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("AdminOnly", policy =>
        policy.RequireRole(AppRoles.Admin));

    options.AddPolicy("CanAssignComplaint", policy =>
        policy.RequireRole(AppRoles.Admin));

    options.AddPolicy("CanUpdateComplaintProgress", policy =>
        policy.RequireRole(AppRoles.Staff));
});
```

---

## Use Policy In Controller

```csharp
[Authorize(Policy = "CanAssignComplaint")]
public async Task<IActionResult> Assign(int id)
{
    return View();
}
```

---

## Policy With Claim

Example:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("ElectricalStaffOnly", policy =>
        policy.RequireRole(AppRoles.Staff)
              .RequireClaim("Department", "Electrical"));
});
```

Use it:

```csharp
[Authorize(Policy = "ElectricalStaffOnly")]
public IActionResult ElectricalComplaints()
{
    return View();
}
```

---

## Role-Based Vs Policy-Based

| Role-Based | Policy-Based |
|---|---|
| Simple role check | Business rule name |
| `[Authorize(Roles = "Admin")]` | `[Authorize(Policy = "CanAssignComplaint")]` |
| Good for simple apps | Better for growing apps |
| Role-focused | Role + claim + custom rule possible |
| Less expressive | More expressive |

---

## Smart Society Policy Examples

| Policy Name | Rule |
|---|---|
| `AdminOnly` | User must be Admin |
| `CanAssignComplaint` | User must be Admin |
| `CanCreateComplaint` | User must be Resident |
| `CanUpdateComplaintProgress` | User must be Staff |
| `ElectricalStaffOnly` | User must be Staff with Electrical department claim |

---

## Important Note

Policy can check role and claim, but ownership usually needs database data.

Example:

```text
Can this resident view complaint ID 10?
```

To answer this, application must check:

```text
Complaint.ResidentId == CurrentUserId
```

This is data-level authorization.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Creating policies for everything too early | Start simple, add policy when rule grows |
| Thinking policy replaces database ownership check | Ownership needs record-level check |
| Using unclear policy names | Use business names like `CanAssignComplaint` |
| Forgetting to register policy | Add it in Program.cs |
| Using policy only in UI | Use policy on server action |

---

## Interview Line

**Policy-based authorization defines named security rules, such as CanAssignComplaint, using roles, claims, or custom requirements.**

# 11. Ownership-Based Access

## What

Ownership-based access means checking whether the logged-in user owns the requested data or is assigned to it.

Examples:

```text
Resident can view only complaints created by self
Staff can update only complaints assigned to self
Admin can view and manage all complaints
```

---

## Why

Role check alone is not enough.

Suppose Deepak is a Resident.

This URL belongs to Deepak's complaint:

```text
/Complaints/Details/10
```

But another resident changes URL:

```text
/Complaints/Details/10
```

If we only check:

```csharp
[Authorize(Roles = "Resident")]
```

then any Resident may open any resident's complaint.

So we also check ownership.

---

## Resident Details Example

# 12. Anti-Forgery Token

## What

Anti-forgery token protects POST forms from cross-site request forgery attacks.

It helps ensure that a form submission came from the real application page, not from another malicious website.

---

## Why

POST actions change data.

Examples:

```text
Create complaint
Assign complaint
Update status
Upload completion proof
Delete attachment
```

These actions should be protected.

---

## Controller Protection

```csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(CreateComplaintViewModel model)
{
    // Save complaint
}
```

---

## Razor Form

When using Tag Helpers, MVC automatically generates anti-forgery token for normal forms.

```html
<form asp-controller="Complaints" asp-action="Create" method="post">
    <div>
        <label asp-for="Title"></label>
        <input asp-for="Title" />
        <span asp-validation-for="Title"></span>
    </div>

    <button type="submit">Submit</button>
</form>
```

Rendered HTML includes hidden anti-forgery token.

---

## Manual Anti-Forgery Token

If needed, add manually:

```html
<form method="post">
    @Html.AntiForgeryToken()

    <input name="Title" />

    <button type="submit">Save</button>
</form>
```

---

## Smart Society Usage

| Form | Anti-Forgery Needed? |
|---|---|
| Register | Yes |
| Login | Yes |
| Logout | Yes |
| Create complaint | Yes |
| Assign complaint | Yes |
| Staff update progress | Yes |
| Upload proof | Yes |
| Search form using GET | Usually not required |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Missing `[ValidateAntiForgeryToken]` on POST | Add it |
| Using GET for delete/update | Use POST for state-changing actions |
| Manually writing form without token | Add `@Html.AntiForgeryToken()` |
| Thinking authentication alone prevents CSRF | Use anti-forgery token also |
| Using anti-forgery only on some forms | Use consistently for POST forms |

---

## Interview Line

**Anti-forgery tokens protect POST forms by verifying that the submitted form came from the trusted application page.**

# 13. Overposting Protection

## What

Overposting happens when a user submits extra form fields that should not be updated.

Example:

```html
<input type="hidden" name="Status" value="Closed" />
<input type="hidden" name="AssignedStaffId" value="admin-id" />
```

A malicious user can add these fields using browser developer tools.

---

## Why It Is Dangerous

Resident should submit:

```text
Title
Description
Category
Image
```

Resident should not submit:

```text
Status
AssignedStaffId
ResolvedDate
AdminRemarks
CompletionProofPath
```

If controller directly binds full entity, overposting can happen.

Bad:

```csharp
[HttpPost]
public async Task<IActionResult> Create(Complaint complaint)
{
    _context.Complaints.Add(complaint);
    await _context.SaveChangesAsync();

    return RedirectToAction(nameof(Index));
}
```

This is risky because attacker may send extra properties.

---

## Better: Use ViewModel

```csharp
using System.ComponentModel.DataAnnotations;
using Microsoft.AspNetCore.Http;

namespace SmartSociety.Web.ViewModels
{
    public class CreateComplaintViewModel
    {
        [Required]
        public string Title { get; set; } = string.Empty;

        [Required]
        public string Description { get; set; } = string.Empty;

        [Required]
        public string Category { get; set; } = string.Empty;

        public IFormFile? Image { get; set; }
    }
}
```

---

## Safe Create Action

```csharp
[Authorize(Roles = AppRoles.Resident)]
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(CreateComplaintViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var residentId = _userManager.GetUserId(User);

    var complaint = new Complaint
    {
        Title = model.Title,
        Description = model.Description,
        Category = model.Category,
        ResidentId = residentId!,
        Status = "Open",
        CreatedAt = DateTime.UtcNow
    };

    _context.Complaints.Add(complaint);

    await _context.SaveChangesAsync();

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(MyComplaints));
}
```

---

## Why This Is Safe

The resident form can only affect:

```text
Title
Description
Category
Image
```

The server decides:

```text
ResidentId = current logged-in user
Status = Open
CreatedAt = current time
AssignedStaffId = null
```

---

## Bind Attribute Awareness

`[Bind]` can limit binding properties.

Example:

```csharp
public async Task<IActionResult> Create(
    [Bind("Title,Description,Category")] Complaint complaint)
{
}
```

But for beginner and enterprise style, ViewModel is usually clearer.

---

## Safe Update Pattern

Bad:

```csharp
_context.Update(complaint);
```

Better:

```csharp
var complaintFromDb = await _context.Complaints.FindAsync(model.Id);

if (complaintFromDb == null)
{
    return NotFound();
}

complaintFromDb.Title = model.Title;
complaintFromDb.Description = model.Description;

await _context.SaveChangesAsync();
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Binding full entity from form | Use ViewModel |
| Updating entity directly from posted model | Load from database first |
| Trusting hidden field values | Use server-side values |
| Letting resident post `Status` | Server decides status |
| Letting resident post `AssignedStaffId` | Only Admin assigns staff |

---

## Interview Line

**Overposting protection means allowing only safe fields to be updated from the form, usually by using ViewModels and server-side assignment.**

# 14. Secure File Upload Thinking

## What

Secure file upload thinking means validating and storing uploaded files carefully.

In Smart Society, files may be:

```text
Complaint image uploaded by Resident
Completion proof uploaded by Staff
Attachment uploaded by Admin
```

---

## Why

File upload is sensitive because users can upload dangerous files.

Possible risks:

```text
Uploading executable files
Uploading very large files
Uploading fake file extensions
Overwriting existing files
Storing files in unsafe location
Allowing direct execution
Trusting original file name
```

---

## Form enctype

File upload form must use:

```html
enctype="multipart/form-data"
```

Example:

```html
<form asp-action="Create" method="post" enctype="multipart/form-data">
    <input asp-for="Title" />
    <input asp-for="Description" />
    <input asp-for="Image" type="file" />

    <button type="submit">Submit Complaint</button>
</form>
```

---

## Safe File Validation

```csharp
private bool IsAllowedImage(IFormFile file)
{
    string[] allowedExtensions = { ".jpg", ".jpeg", ".png" };

    string extension = Path.GetExtension(file.FileName).ToLowerInvariant();

    if (!allowedExtensions.Contains(extension))
    {
        return false;
    }

    if (file.Length > 2 * 1024 * 1024)
    {
        return false;
    }

    return true;
}
```

---

## Safe File Save Example

```csharp
private async Task<string?> SaveComplaintImageAsync(IFormFile? image)
{
    if (image == null || image.Length == 0)
    {
        return null;
    }

    if (!IsAllowedImage(image))
    {
        throw new InvalidOperationException("Only JPG and PNG files up to 2 MB are allowed.");
    }

    string uploadsFolder = Path.Combine(
        Directory.GetCurrentDirectory(),
        "wwwroot",
        "uploads",
        "complaints");

    Directory.CreateDirectory(uploadsFolder);

    string extension = Path.GetExtension(image.FileName).ToLowerInvariant();
    string safeFileName = $"{Guid.NewGuid()}{extension}";
    string fullPath = Path.Combine(uploadsFolder, safeFileName);

    using (var stream = new FileStream(fullPath, FileMode.Create))
    {
        await image.CopyToAsync(stream);
    }

    return $"/uploads/complaints/{safeFileName}";
}
```

---

## Use In Create Complaint

```csharp
string? imagePath = null;

try
{
    imagePath = await SaveComplaintImageAsync(model.Image);
}
catch (InvalidOperationException ex)
{
    ModelState.AddModelError(nameof(model.Image), ex.Message);
    return View(model);
}

var complaint = new Complaint
{
    Title = model.Title,
    Description = model.Description,
    Category = model.Category,
    ImagePath = imagePath,
    ResidentId = residentId!,
    Status = "Open",
    CreatedAt = DateTime.UtcNow
};
```

---

## Completion Proof Upload

Staff can upload proof only for assigned complaint.

```csharp
[Authorize(Roles = AppRoles.Staff)]
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> UploadProof(UploadProofViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var staffId = _userManager.GetUserId(User);

    var complaint = await _context.Complaints
        .FirstOrDefaultAsync(c =>
            c.Id == model.ComplaintId &&
            c.AssignedStaffId == staffId);

    if (complaint == null)
    {
        return Forbid();
    }

    string? proofPath = await SaveComplaintImageAsync(model.ProofImage);

    complaint.CompletionProofPath = proofPath;
    complaint.Status = "Completed";

    await _context.SaveChangesAsync();

    TempData["SuccessMessage"] = "Completion proof uploaded.";

    return RedirectToAction(nameof(Assigned));
}
```

---

## Secure Upload Rules

| Rule | Reason |
|---|---|
| Check file extension | Avoid unsupported files |
| Check file size | Avoid large upload attack |
| Generate new file name | Avoid overwrite and path tricks |
| Do not trust original file name | User controls it |
| Store only safe path in database | Do not store physical full path |
| Check user role and ownership before upload | Avoid unauthorized upload |
| Do not allow executable extensions | Avoid dangerous file execution |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Saving original file name directly | Use `Guid.NewGuid()` |
| No file size check | Limit file size |
| Accepting all extensions | Allow only required types |
| Uploading before authorization check | Check role and ownership first |
| Storing files in random folder | Use controlled upload folder |
| Trusting `ContentType` only | Also check extension and size |

---

## Interview Line

**Secure file upload requires validating file type and size, generating safe file names, storing files in controlled locations, and checking authorization before saving.**

# 15. Avoid Security Only In UI

## What

UI security means hiding or showing menu/buttons based on user role.

Example:

```html
@if (User.IsInRole("Admin"))
{
    <a asp-controller="AdminComplaints" asp-action="Index">Admin Complaints</a>
}
```

This is useful for user experience, but it is not enough for security.

---

## Why UI Security Is Not Enough

Users can manually type URL:

```text
/AdminComplaints/Index
```

Or change form data using browser developer tools.

So security must be enforced on the server.

---

## Correct Pattern

### 1. Hide UI Option

```html
@if (User.IsInRole(AppRoles.Admin))
{
    <li>
        <a asp-controller="AdminComplaints" asp-action="Index">All Complaints</a>
    </li>
}
```

### 2. Protect Controller

```csharp
[Authorize(Roles = AppRoles.Admin)]
public class AdminComplaintsController : Controller
{
}
```

### 3. Protect Data Query

```csharp
var complaints = await _context.Complaints.ToListAsync();
```

Only Admin controller should access all complaints.

---

## Smart Society Example

Resident should not see Assign button.

But even if resident tries POST manually:

```text
/AdminComplaints/Assign
```

Server should reject it because action has:

```csharp
[Authorize(Roles = AppRoles.Admin)]
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Hiding button and thinking feature is secure | Add server-side authorization |
| Showing menu based on role but controller open | Add `[Authorize]` |
| Trusting disabled input fields | Disabled/hidden fields can be changed |
| Returning all data and filtering in view | Filter data in query |
| Relying only on JavaScript validation | Validate on server |

---

## Interview Line

**UI hiding improves user experience, but real security must always be enforced on the server using authorization and data checks.**

# 16. Access Denied Handling

## What

Access denied handling means showing a proper page when a logged-in user tries to access a page they are not allowed to access.

Example:

```text
Resident tries /AdminComplaints/Index
```

They are logged in, but not Admin.

The application should show:

```text
Access Denied
```

---

## Configure Access Denied Path

In `Program.cs`, add cookie configuration after Identity registration:

```csharp
builder.Services.ConfigureApplicationCookie(options =>
{
    options.LoginPath = "/Account/Login";
    options.AccessDeniedPath = "/Account/AccessDenied";
});
```

---

## AccountController AccessDenied Action

```csharp
[HttpGet]
public IActionResult AccessDenied()
{
    return View();
}
```

---

## AccessDenied View

### File: `Views/Account/AccessDenied.cshtml`

```html
@{
    ViewData["Title"] = "Access Denied";
}

<div class="alert alert-danger">
    <h2>Access Denied</h2>
    <p>You do not have permission to access this page.</p>
</div>

<a asp-controller="Home" asp-action="Index" class="btn btn-primary">
    Go To Home
</a>
```

---

## Return Types For Security

| Return Type | When To Use |
|---|---|
| `Forbid()` | User is logged in but not allowed |
| `Challenge()` | User is not logged in and should login |
| `NotFound()` | Record does not exist or should not be revealed |
| `Unauthorized()` | More common in APIs |
| Redirect to AccessDenied | User-friendly MVC page |

---

## Smart Society Examples

| Situation | Response |
|---|---|
| Resident opens admin dashboard | Access denied |
| Staff opens another staff complaint | Forbid |
| Anonymous opens complaint create page | Redirect to login |
| Wrong complaint ID | NotFound |
| Logged-in user tries restricted POST | Forbid |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Showing raw error page | Create friendly AccessDenied view |
| Returning success with no data | Return proper security response |
| Redirecting all errors to home | Show clear message |
| Revealing sensitive record existence | Use careful NotFound/Forbid decision |
| Not configuring AccessDeniedPath | Configure application cookie |

---

## Interview Line

**Access denied handling gives a controlled response when an authenticated user tries to access a resource they are not authorized to use.**

# 18. Complete Controller Security Example

## Resident Complaint Create

```csharp
[Authorize(Roles = AppRoles.Resident)]
public class ResidentComplaintsController : Controller
{
    private readonly ApplicationDbContext _context;
    private readonly UserManager<ApplicationUser> _userManager;

    public ResidentComplaintsController(
        ApplicationDbContext context,
        UserManager<ApplicationUser> userManager)
    {
        _context = context;
        _userManager = userManager;
    }

    [HttpGet]
    public IActionResult Create()
    {
        return View();
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(CreateComplaintViewModel model)
    {
        if (!ModelState.IsValid)
        {
            return View(model);
        }

        var residentId = _userManager.GetUserId(User);

        string? imagePath = await SaveComplaintImageAsync(model.Image);

        var complaint = new Complaint
        {
            Title = model.Title,
            Description = model.Description,
            Category = model.Category,
            ImagePath = imagePath,
            ResidentId = residentId!,
            Status = "Open",
            CreatedAt = DateTime.UtcNow
        };

        _context.Complaints.Add(complaint);
        await _context.SaveChangesAsync();

        TempData["SuccessMessage"] = "Complaint created successfully.";

        return RedirectToAction(nameof(MyComplaints));
    }

    public async Task<IActionResult> MyComplaints()
    {
        var residentId = _userManager.GetUserId(User);

        var complaints = await _context.Complaints
            .Where(c => c.ResidentId == residentId)
            .ToListAsync();

        return View(complaints);
    }

    public async Task<IActionResult> Details(int id)
    {
        var residentId = _userManager.GetUserId(User);

        var complaint = await _context.Complaints
            .FirstOrDefaultAsync(c =>
                c.Id == id &&
                c.ResidentId == residentId);

        if (complaint == null)
        {
            return Forbid();
        }

        return View(complaint);
    }

    private async Task<string?> SaveComplaintImageAsync(IFormFile? image)
    {
        if (image == null || image.Length == 0)
        {
            return null;
        }

        string[] allowedExtensions = { ".jpg", ".jpeg", ".png" };
        string extension = Path.GetExtension(image.FileName).ToLowerInvariant();

        if (!allowedExtensions.Contains(extension))
        {
            throw new InvalidOperationException("Only JPG and PNG files are allowed.");
        }

        if (image.Length > 2 * 1024 * 1024)
        {
            throw new InvalidOperationException("File size must be less than 2 MB.");
        }

        string uploadsFolder = Path.Combine(
            Directory.GetCurrentDirectory(),
            "wwwroot",
            "uploads",
            "complaints");

        Directory.CreateDirectory(uploadsFolder);

        string safeFileName = $"{Guid.NewGuid()}{extension}";
        string fullPath = Path.Combine(uploadsFolder, safeFileName);

        using (var stream = new FileStream(fullPath, FileMode.Create))
        {
            await image.CopyToAsync(stream);
        }

        return $"/uploads/complaints/{safeFileName}";
    }
}
```

# 20. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Login implemented but no role checks | Any logged-in user may access protected pages | Add roles and `[Authorize]` |
| Creating role manually in DB | Can break Identity consistency | Use RoleManager |
| Allowing user to choose role in register form | User can become Admin | Assign safe role on server |
| Using full entity in POST action | Overposting risk | Use ViewModel |
| Trusting hidden field `ResidentId` | User can change it | Use current logged-in user ID |

# 23. Short Answers

1. A role is a named permission group.
2. Smart Society roles are Resident, Admin, and Staff.
3. RoleManager creates and manages roles.
4. We seed roles so required roles exist before assigning users.
5. `UserManager.AddToRoleAsync` assigns a user to a role.
6. Identity stores user-role mapping in `AspNetUserRoles`.
7. `[Authorize]` protects controllers and actions.
8. Use `[Authorize(Roles = AppRoles.Admin)]`.
9. Use comma-separated roles such as Admin and Staff.
10. A claim is a small piece of information about a user.
11. A role is a group; a claim is user-specific information.
12. Policy-based authorization uses named rules to allow or deny access.
13. Policy is useful because it gives business names to authorization rules.
14. Ownership-based access checks whether the record belongs to the current user.
15. Role check alone does not prove the user owns the record.
16. Resident complaints must be filtered by ResidentId to protect private data.
17. Staff complaints must be filtered by AssignedStaffId to protect assignment data.
18. Anti-forgery token protects POST forms from CSRF attacks.
19. Data-changing POST actions need `[ValidateAntiForgeryToken]`.
20. Overposting is when extra unwanted fields are submitted and updated.
21. ViewModel allows only safe fields to come from the form.
22. Status should be controlled by server workflow.
23. AssignedStaffId should be controlled by Admin workflow.
24. Secure file upload means validating file type, size, name, and access.
25. Original file name is user-controlled and can be unsafe.
26. UI hiding is not enough because users can manually call URLs.
27. AccessDeniedPath configures where unauthorized logged-in users are redirected.
28. Return `Forbid()` when logged-in user is not allowed.
29. Use `UserManager.GetUserId(User)` to get current user ID.
30. Always check authentication, role, ownership, safe binding, and validation.

# 27. Interview Explanation

Learner should be able to explain:

```text
In my Smart Society Issue Management System, I use ASP.NET Core Identity roles to secure different workflows for Residents, Admins, and Staff.

I created three roles: Resident, Admin, and Staff. These roles are seeded at application startup using RoleManager. When a resident registers, I assign the Resident role using UserManager.AddToRoleAsync. Staff users are created by Admin and assigned the Staff role. Admin users are created through controlled seeding or admin-only setup.

I use the Authorize attribute to protect controllers and actions. For example, AdminComplaintsController is protected with Admin role, ResidentComplaintsController is protected with Resident role, and StaffComplaintsController is protected with Staff role.

For data security, I do not depend only on role checks. I also implement ownership-based access. A resident can view only complaints where ResidentId matches the current logged-in user. A staff member can update only complaints where AssignedStaffId matches the current logged-in staff user.

I also protect POST actions with anti-forgery tokens. I prevent overposting by using ViewModels instead of binding full database entities directly. The server decides sensitive fields such as Status, ResidentId, AssignedStaffId, and CreatedAt.

For file uploads, I validate extension, file size, and generate safe file names. I also check authorization before saving uploaded complaint images or completion proof.

This gives the Smart Society application a stronger security foundation because access is protected at controller, action, data, and update levels, not only in the UI.
```
