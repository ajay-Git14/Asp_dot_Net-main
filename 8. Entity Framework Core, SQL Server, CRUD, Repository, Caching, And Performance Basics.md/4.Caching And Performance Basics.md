# 1. Why This Topic Is Important

## What

Caching means storing frequently used data temporarily so the application does not need to calculate or load it again and again.

Simple meaning:

```text
Cache stores reusable data for faster access.
```

In the Smart Society Issue Management System, some data may be requested repeatedly:

```text
Dashboard summary counts
Complaint category list
Priority list
Status list
Admin dashboard widgets
Common dropdown values
```

If every request hits the database unnecessarily, the application can become slow.

---

## Why

Caching improves:

```text
Page loading speed
Database performance
Server response time
User experience
Scalability
```

But caching must be used carefully.

Wrong caching can create serious problems:

```text
User sees outdated complaint status
Resident sees another resident's complaint data
Admin dashboard shows stale numbers
Sensitive complaint details are exposed
Archived complaint still appears as active
```

So caching is powerful, but it must be designed safely.

---

## Smart Society Mapping

Use caching carefully for:

```text
Dashboard summary
Complaint category list
Priority list
Status list
Non-sensitive dropdown values
```

Avoid unsafe caching for:

```text
Resident-specific complaint details
Sensitive complaint descriptions
Complaint attachments
Authorization-sensitive data
User-specific complaint lists unless carefully keyed and expired
```

---

## Real-Life Analogy

Think of a society office notice board.

It is useful to keep common information on the notice board:

```text
Office timings
Emergency numbers
Complaint categories
Maintenance department list
```

But it is unsafe to put private complaint details there:

```text
Resident personal complaint
Flat-specific issue
Private contact number
Security complaint details
```

Cache is like a notice board.

Use it for safe shared information, not private sensitive information.

---

## Engineering View

```text
Request comes in
↓
Application checks cache
↓
If data exists in cache → return cached data
↓
If data missing → load from database
↓
Store result in cache
↓
Return data
```

---

## Interview Line

**Caching improves performance by storing frequently used data temporarily, but sensitive or user-specific data must be cached very carefully or avoided.**

# 2. Caching In Repository

## What

Caching in repository means storing data retrieved by repository queries so repeated database calls can be avoided.

Example:

```text
Complaint categories rarely change.
Repository loads them once.
Application stores them in cache.
Next request uses cache instead of database.
```

---

## Why

Repositories are close to the data access layer.

Some read-heavy data can be cached there, especially:

```text
Category list
Priority list
Status list
Reference data
Dashboard summary if carefully designed
```

---

## Important Design Rule

Do not blindly cache every repository query.

Ask:

```text
Is the data shared or user-specific?
Is the data sensitive?
How often does it change?
How stale can it be?
What cache key should be used?
When should cache expire?
```

---

## Smart Society Safe Repository Caching Example

Cache complaint category list:

```csharp
public async Task<List<string>> GetComplaintCategoriesAsync()
{
    const string cacheKey = "complaint_categories";

    if (_memoryCache.TryGetValue(cacheKey, out List<string>? categories))
    {
        return categories!;
    }

    categories = await _context.Complaints
        .Select(c => c.Category)
        .Distinct()
        .OrderBy(c => c)
        .ToListAsync();

    var cacheOptions = new MemoryCacheEntryOptions()
        .SetAbsoluteExpiration(TimeSpan.FromMinutes(30));

    _memoryCache.Set(cacheKey, categories, cacheOptions);

    return categories;
}
```

---

## Better For Static Categories

If categories are predefined, avoid database query:

```csharp
public List<string> GetDefaultComplaintCategories()
{
    return new List<string>
    {
        "Plumbing",
        "Electrical",
        "Lift",
        "Security",
        "Housekeeping",
        "Parking"
    };
}
```

This can be cached or kept as configuration/static list.

---

## What Not To Cache In Repository

Avoid caching:

```text
Complaint details with private information
Resident-specific complaint list without user-specific cache key
Authorization-sensitive data
Uploaded file paths if access-controlled
Data that changes very frequently
Data that must always be real-time
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Caching all repository queries | Cache only safe and useful data |
| Using same cache key for all users | Include user ID if user-specific cache is unavoidable |
| Caching sensitive complaint details | Avoid or use strict safeguards |
| Not expiring cache | Add expiration |
| Not invalidating cache after update | Remove/update cache when data changes |

---

## Interview Line

**Caching in repository can reduce repeated database calls for safe reference data, but user-specific and sensitive data must not be cached carelessly.**

# 3. Cache Tag Helpers

## What

Cache Tag Helpers allow caching of parts of Razor views.

They are used in `.cshtml` files.

Example:

```html
<cache expires-after="@TimeSpan.FromMinutes(10)">
    <partial name="_ComplaintCategoryList" />
</cache>
```

---

## Why

Some UI sections do not change frequently.

Caching those sections can improve rendering performance.

Examples:

```text
Complaint category menu
Static dashboard help section
Public notice panel
Common footer section
Reference dropdown explanation
```

---

## Smart Society Example

Cache a non-sensitive category block:

```html
<cache expires-after="@TimeSpan.FromMinutes(30)">
    <div class="card">
        <div class="card-header">
            Complaint Categories
        </div>
        <div class="card-body">
            <ul>
                <li>Plumbing</li>
                <li>Electrical</li>
                <li>Lift</li>
                <li>Security</li>
                <li>Housekeeping</li>
                <li>Parking</li>
            </ul>
        </div>
    </div>
</cache>
```

---

## Vary-By Awareness

If cached output depends on a value, use vary-by.

Example:

```html
<cache vary-by="@User.Identity?.Name" expires-after="@TimeSpan.FromMinutes(5)">
    <p>Welcome, @User.Identity?.Name</p>
</cache>
```

But for user-specific content, be very careful.

---

## Avoid Caching Sensitive View Sections

Do not cache:

```text
Resident complaint details
Complaint attachments
Admin-only data blocks
User-specific private messages
Staff assigned complaint list
Authentication-sensitive content
```

unless you understand vary-by, access control, and cache lifetime properly.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Caching user-specific UI without vary-by | Use vary-by or avoid caching |
| Caching sensitive data | Avoid caching sensitive view sections |
| Long cache duration for changing data | Use short expiration |
| Caching admin dashboard blindly | Cache summary carefully in service layer |
| Assuming cache tag helper replaces server-side checks | Authorization still required |

---

## Interview Line

**Cache Tag Helpers cache parts of Razor views and are useful for non-sensitive, rarely changing UI sections.**

# 4. Memory Caching Introduction

## What

Memory caching stores data in the memory of the web server.

ASP.NET Core provides:

```text
IMemoryCache
```

for in-memory caching.

---

## Why

Memory access is faster than database access.

For data that is safe to reuse temporarily, memory cache can improve performance.

---

## Smart Society Suitable Data

Good candidates:

```text
Complaint category list
Priority list
Status list
Dashboard summary for a short duration
Static reference values
```

Poor candidates:

```text
Private complaint details
Resident personal information
Sensitive attachments
User authorization decisions
Highly real-time data
```

---

## Memory Cache Flow

```text
Request asks for dashboard summary
↓
Service checks memory cache
↓
If found → return cached summary
↓
If not found → query database
↓
Store summary in memory cache
↓
Return summary
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Caching sensitive data | Avoid sensitive data in cache |
| Assuming memory cache is shared across servers | It is local to one server |
| No expiration | Set expiration |
| Cache grows too much | Use size limits/expiration where needed |
| Caching stale dashboard for too long | Use short expiration |

---

## Interview Line

**Memory caching stores data in the web server's memory for fast access and is suitable for safe, frequently used, temporary data.**

---

# 5. In-Memory Caching

## What

In-memory caching means cached data is stored inside the memory of the current application instance.

---

## Why

It is simple and fast.

It works well for:

```text
Single-server applications
Learning projects
Small to medium applications
Reference data
Short-lived dashboard summaries
```

---

## Add Memory Cache In Program.cs

```csharp
builder.Services.AddMemoryCache();
```

---

## Inject IMemoryCache

```csharp
private readonly IMemoryCache _memoryCache;

public ComplaintService(IMemoryCache memoryCache)
{
    _memoryCache = memoryCache;
}
```

---

## Important Limitation

In-memory cache is not shared across multiple servers.

If application runs on two servers:

```text
Server 1 has cache A
Server 2 has cache B
```

This can cause inconsistent cache behavior.

For multi-server environments, distributed cache is usually better.

---

## Smart Society Usage

For training and first implementation:

```text
Use IMemoryCache for category list and short dashboard summary cache.
```

For enterprise scale later:

```text
Use distributed cache such as Redis for shared cache.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using memory cache in multi-server without planning | Use distributed cache |
| Storing large objects | Keep cache small and controlled |
| No expiration | Add absolute/sliding expiration |
| Caching user data globally | Use careful user-specific keys or avoid |
| Assuming cache survives app restart | Memory cache is lost on restart |

---

## Interview Line

**In-memory caching stores cached data inside the current application server process and is fast but not shared across multiple servers.**

# 7. Cache Key

## What

A cache key is the unique name used to store and retrieve cached data.

Example:

```text
dashboard_summary
complaint_categories
priority_list
```

---

## Why

Cache keys must be clear and unique.

If two different data items use the same key, wrong data may be returned.

---

## Smart Society Good Cache Keys

```text
dashboard_summary_admin
complaint_categories
complaint_priorities
complaint_statuses
dashboard_summary_admin_2026_05_19
```

---

## User-Specific Cache Key Awareness

If user-specific cache is unavoidable, include user ID:

```csharp
var cacheKey = $"resident_complaints_{residentUserId}";
```

But use this carefully.

For sensitive complaint data, avoid caching unless there is a strong reason and proper invalidation.

---

## Cache Key Constants

Create file:

```text
Constants/CacheKeys.cs
```

Code:

```csharp
namespace SmartSociety.Web.Constants
{
    public static class CacheKeys
    {
        public const string ComplaintCategories = "complaint_categories";

        public const string ComplaintPriorities = "complaint_priorities";

        public const string ComplaintStatuses = "complaint_statuses";

        public const string AdminDashboardSummary = "admin_dashboard_summary";
    }
}
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using vague key like `data` | Use descriptive keys |
| Same key for different users | Include user ID or avoid caching |
| Same key for different filters | Include filter value |
| Hardcoding strings everywhere | Use constants |
| Not planning invalidation | Define when key should be removed |

---

## Interview Line

**A cache key uniquely identifies cached data and should be clear, consistent, and safe for the data being cached.**

# 8. Absolute Expiration

## What

Absolute expiration removes cached data after a fixed time, regardless of how often it is accessed.

Example:

```text
Cache this dashboard summary for 5 minutes.
After 5 minutes, remove it.
```

---

## Code Example

```csharp
var cacheOptions = new MemoryCacheEntryOptions()
    .SetAbsoluteExpiration(TimeSpan.FromMinutes(5));

_memoryCache.Set(CacheKeys.AdminDashboardSummary, summary, cacheOptions);
```

---

## Why

Absolute expiration ensures data does not remain stale forever.

---

## Smart Society Usage

Use absolute expiration for:

```text
Dashboard summary
Category list
Priority list
Status list
```

Suggested durations:

| Data | Suggested Absolute Expiration |
|---|---|
| Dashboard summary | 1 to 5 minutes |
| Category list | 30 to 60 minutes |
| Priority list | 60 minutes |
| Status list | 60 minutes |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Very long dashboard cache | Use short duration |
| No expiration | Cache may become stale |
| Using absolute expiration for all scenarios blindly | Choose based on data behavior |
| Not invalidating after update | Remove cache when related data changes |
| Confusing absolute with sliding expiration | Understand difference |

---

## Interview Line

**Absolute expiration removes cached data after a fixed duration, even if the data is accessed frequently.**

---

# 9. Sliding Expiration

## What

Sliding expiration resets the cache lifetime every time the cached item is accessed.

Example:

```text
Cache expires after 10 minutes of no access.
If accessed again, timer resets.
```

---

## Code Example

```csharp
var cacheOptions = new MemoryCacheEntryOptions()
    .SetSlidingExpiration(TimeSpan.FromMinutes(10));

_memoryCache.Set(CacheKeys.ComplaintCategories, categories, cacheOptions);
```

---

## Why

Sliding expiration is useful when data should stay cached while it is actively used.

---

## Smart Society Usage

Good for:

```text
Complaint category list
Priority list
Status list
Reference data
```

Be careful with:

```text
Dashboard summary
```

because frequent access may keep stale dashboard data alive too long.

For dashboard, prefer absolute expiration or combine both.

---

## Combine Absolute And Sliding Expiration

```csharp
var cacheOptions = new MemoryCacheEntryOptions()
    .SetSlidingExpiration(TimeSpan.FromMinutes(10))
    .SetAbsoluteExpiration(TimeSpan.FromHours(1));
```

Meaning:

```text
Expire if unused for 10 minutes.
But always expire after 1 hour maximum.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Sliding expiration keeps stale data too long | Add absolute expiration also |
| Using sliding expiration for real-time data | Avoid caching real-time data |
| Not understanding timer reset | Sliding timer resets on access |
| Long sliding duration for dashboard | Use short absolute expiration |
| Caching sensitive data with sliding expiration | Avoid sensitive cache |

---

## Interview Line

**Sliding expiration removes cached data after a period of inactivity and resets the timer each time the data is accessed.**

---

# 10. Dashboard Summary Caching

## What

Dashboard summary caching stores calculated dashboard counts temporarily.

Example dashboard values:

```text
Total complaints
Pending complaints
Assigned complaints
In-progress complaints
Resolved complaints
Critical complaints
```

---

## Why

Dashboard count queries may run frequently.

Caching summary for a short time reduces repeated database aggregation.

---

## DashboardSummaryViewModel

```csharp
namespace SmartSociety.Web.ViewModels
{
    public class DashboardSummaryViewModel
    {
        public int TotalComplaints { get; set; }

        public int NewComplaints { get; set; }

        public int AssignedComplaints { get; set; }

        public int InProgressComplaints { get; set; }

        public int ResolvedComplaints { get; set; }

        public int CriticalComplaints { get; set; }
    }
}
```

---

## Service Method With Cache

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Caching.Memory;
using SmartSociety.Web.Constants;
using SmartSociety.Web.Data;
using SmartSociety.Web.ViewModels;

public class DashboardService
{
    private readonly ApplicationDbContext _context;
    private readonly IMemoryCache _memoryCache;

    public DashboardService(
        ApplicationDbContext context,
        IMemoryCache memoryCache)
    {
        _context = context;
        _memoryCache = memoryCache;
    }

    public async Task<DashboardSummaryViewModel> GetAdminDashboardSummaryAsync()
    {
        if (_memoryCache.TryGetValue(
            CacheKeys.AdminDashboardSummary,
            out DashboardSummaryViewModel? cachedSummary))
        {
            return cachedSummary!;
        }

        var summary = new DashboardSummaryViewModel
        {
            TotalComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived),

            NewComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived && c.Status == "New"),

            AssignedComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived && c.Status == "Assigned"),

            InProgressComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived && c.Status == "InProgress"),

            ResolvedComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived && c.Status == "Resolved"),

            CriticalComplaints = await _context.Complaints
                .CountAsync(c => !c.IsArchived && c.Priority == "Critical")
        };

        var cacheOptions = new MemoryCacheEntryOptions()
            .SetAbsoluteExpiration(TimeSpan.FromMinutes(2));

        _memoryCache.Set(CacheKeys.AdminDashboardSummary, summary, cacheOptions);

        return summary;
    }
}
```

---

## Cache Invalidation After Complaint Changes

When complaint is created, assigned, updated, resolved, or archived:

```csharp
_memoryCache.Remove(CacheKeys.AdminDashboardSummary);
```

This ensures dashboard refreshes after important changes.

---

## Smart Society Rule

Dashboard summary can be cached because it is aggregate data.

But keep cache duration short:

```text
1 to 5 minutes
```

Also invalidate when important complaint changes happen.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Caching dashboard forever | Use short absolute expiration |
| Not removing cache after complaint update | Remove dashboard cache |
| Caching resident-specific dashboard globally | Use user-specific key or avoid |
| Dashboard shows stale data after update | Add invalidation |
| Caching sensitive details in summary | Cache only aggregate counts |

---

## Interview Line

**Dashboard summary can be cached carefully for a short duration because it contains aggregate counts, but it should be invalidated when complaint data changes.**

# 11. Cache Complaint Category List

## What

Complaint categories are reference values used in the complaint form.

Examples:

```text
Plumbing
Electrical
Lift
Security
Housekeeping
Parking
```

---

## Why

Category list is a good cache candidate because:

```text
It is non-sensitive
It changes rarely
It is used frequently
It appears in forms/dropdowns
```

---

## Category Service Example

```csharp
using Microsoft.Extensions.Caching.Memory;
using SmartSociety.Web.Constants;

public class ComplaintLookupService
{
    private readonly IMemoryCache _memoryCache;

    public ComplaintLookupService(IMemoryCache memoryCache)
    {
        _memoryCache = memoryCache;
    }

    public List<string> GetComplaintCategories()
    {
        if (_memoryCache.TryGetValue(
            CacheKeys.ComplaintCategories,
            out List<string>? categories))
        {
            return categories!;
        }

        categories = new List<string>
        {
            "Plumbing",
            "Electrical",
            "Lift",
            "Security",
            "Housekeeping",
            "Parking"
        };

        var cacheOptions = new MemoryCacheEntryOptions()
            .SetSlidingExpiration(TimeSpan.FromMinutes(30))
            .SetAbsoluteExpiration(TimeSpan.FromHours(2));

        _memoryCache.Set(CacheKeys.ComplaintCategories, categories, cacheOptions);

        return categories;
    }
}
```

---

## Register Service

```csharp
builder.Services.AddScoped<ComplaintLookupService>();
```

---

## Use In Controller

```csharp
public IActionResult Create()
{

    return View();
}
```

---

## Use In View

```html
    <option value="">-- Select Category --</option>

    @foreach (var category in ViewBag.Categories)
    {
        <option value="@category">@category</option>
    }
</select>
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Querying category list repeatedly | Cache reference list |

| Hardcoding categories in many views | Centralize in service/config |
| Caching user-specific values as categories | Keep category list shared and safe |
| Forgetting to refresh cache after category changes | Remove cache if admin changes categories |

## Interview Line

**Complaint category list is a good caching candidate because it is non-sensitive, reused frequently, and changes rarely.**

# 12. Response Cache

## What

Response caching stores the entire HTTP response for reuse.

It can reduce server work for responses that are safe to cache.

---

## Why

Response cache is useful for:

```text
Public pages
Static informational pages
Non-user-specific content
```

---

## ASP.NET Core ResponseCache Attribute

```csharp
[ResponseCache(Duration = 60, Location = ResponseCacheLocation.Any)]
public IActionResult About()
{
    return View();
}
```

This means response may be cached for 60 seconds.

---

## Smart Society Suitable Response Cache

Good candidates:

```text
Public About page
Public Contact page
Public Help page
Public FAQ page
```

Avoid response caching:

```text
Complaint list
Complaint details
Admin dashboard
Staff assigned complaints
Resident dashboard
Login page with user-specific messages
```

---

## No Cache For Sensitive Pages

```csharp
[ResponseCache(NoStore = true, Location = ResponseCacheLocation.None)]
public IActionResult Details(int id)
{
    return View();
}
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Response caching private pages | Avoid caching sensitive pages |
| Caching pages with logged-in user data | Disable or vary carefully |
| Thinking response cache is same as memory cache | Response cache caches HTTP response |
| Caching admin dashboard response | Avoid or use service-level summary cache |
| Not understanding browser/proxy caching | Be careful with cache location |

---

## Interview Line

**Response caching caches HTTP responses and is suitable for public non-sensitive pages, not private complaint or dashboard pages.**

# 13. Distributed Cache

## What

Distributed cache stores cached data outside the application server so multiple servers can share the same cache.

Examples:

```text
Redis
SQL Server distributed cache
NCache
Cloud cache services
```

---

## Why

In-memory cache is local to one server.

Distributed cache is useful when:

```text
Application runs on multiple servers
Load balancing is used
Cache must be shared
Session data needs shared backing store
High availability is required
```

---

## Smart Society Scaling Scenario

If Smart Society runs on two servers:

```text
Server 1 handles some users
Server 2 handles other users
```

With memory cache:

```text
Each server has separate cache
Dashboard cache may differ
```

With distributed cache:

```text
Both servers use same cache source
```

---

## Distributed Cache Interface

ASP.NET Core provides:

```csharp
IDistributedCache
```

It stores byte/string data.

---

## Redis Awareness

In enterprise applications, Redis is commonly used for distributed caching.

Example use cases:

```text
Shared dashboard cache
Shared reference data cache
Distributed session
High-scale read optimization
```

---

## Important Course Note

For current Smart Society training:

```text
Use IMemoryCache for basic caching.
Understand distributed cache as enterprise scaling concept.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using memory cache in multi-server without awareness | Use distributed cache |
| Thinking distributed cache solves all performance issues | Optimize queries too |
| Caching sensitive data without encryption/access design | Avoid sensitive cache |
| Not planning cache invalidation | Define invalidation strategy |
| Using distributed cache too early for simple app | Start simple, scale when needed |

---

## Interview Line

**Distributed cache stores cache outside the web server so multiple application instances can share cached data, commonly using Redis in enterprise systems.**

# 15. Query Optimization Awareness

## What

Query optimization means writing database queries that retrieve only necessary data efficiently.

---

## Why

Bad queries can slow down the application even if caching is used.

---

## Bad Query

```csharp
var complaints = await _context.Complaints
    .Include(c => c.Comments)
    .Include(c => c.Attachments)
    .Include(c => c.StatusHistory)
    .ToListAsync();
```

Problem:

```text
Loads all complaints
Loads all related data
May become very slow
Not needed for list page
```

---

## Better Query For List Page

```csharp
var complaints = await _context.Complaints
    .Where(c => !c.IsArchived)
    .OrderByDescending(c => c.CreatedDate)
    .Select(c => new ComplaintListViewModel
    {
        ComplaintId = c.ComplaintId,
        Title = c.Title,
        Category = c.Category,
        Priority = c.Priority,
        Status = c.Status,
        CreatedDate = c.CreatedDate
    })
    .ToListAsync();
```

---

## Why Projection Helps

Projection selects only required fields.

List page does not need:

```text
Full description
All comments
All attachments
Full status history
```

So do not load them.

---

## Smart Society Query Optimization Rules

```text
List page → Use projection and pagination
Details page → Use Include for related details
Dashboard → Use count queries and short cache
Dropdowns → Use cached reference lists
Resident list → Filter by CreatedByUserId
Staff list → Filter by AssignedToStaffId
Admin list → Filter/archive/paginate
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Include everything everywhere | Load only what page needs |
| Filtering after ToListAsync | Filter before executing query |
| No projection for list pages | Use ViewModel projection |
| Loading archived records unnecessarily | Add `!c.IsArchived` |
| No ordering | Use useful ordering |

---

## Interview Line

**Query optimization means filtering, projecting, ordering, and loading only the data required by the current screen or operation.**

# 16. Pagination Awareness

## What

Pagination means showing data in pages instead of loading all records at once.

Example:

```text
Page 1 → 10 complaints
Page 2 → next 10 complaints
Page 3 → next 10 complaints
```

---

## Why

Complaint data can grow over time.

Loading thousands of complaints on one page is bad for:

```text
Database
Server memory
Network response size
Browser rendering
User experience
```

---

## Smart Society Pagination Use Cases

```text
Resident complaint list
Admin all complaints
Staff assigned complaints
Complaint comments
Audit history
Status history
```

---

## Basic Pagination Query

```csharp
public async Task<List<Complaint>> GetPagedComplaintsAsync(
    int pageNumber,
    int pageSize)
{
    return await _context.Complaints
        .Where(c => !c.IsArchived)
        .OrderByDescending(c => c.CreatedDate)
        .Skip((pageNumber - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync();
}
```

---

## Pagination ViewModel

```csharp
public class PagedResult<T>
{
    public List<T> Items { get; set; } = new();

    public int PageNumber { get; set; }

    public int PageSize { get; set; }

    public int TotalRecords { get; set; }

    public int TotalPages =>
        (int)Math.Ceiling((double)TotalRecords / PageSize);
}
```

---

## Paged Query With Count

```csharp
public async Task<PagedResult<ComplaintListViewModel>> GetPagedComplaintListAsync(
    int pageNumber,
    int pageSize)
{
    var query = _context.Complaints
        .Where(c => !c.IsArchived);

    var totalRecords = await query.CountAsync();

    var items = await query
        .OrderByDescending(c => c.CreatedDate)
        .Skip((pageNumber - 1) * pageSize)
        .Take(pageSize)
        .Select(c => new ComplaintListViewModel
        {
            ComplaintId = c.ComplaintId,
            Title = c.Title,
            Category = c.Category,
            Priority = c.Priority,
            Status = c.Status,
            CreatedDate = c.CreatedDate
        })
        .ToListAsync();

    return new PagedResult<ComplaintListViewModel>
    {
        Items = items,
        PageNumber = pageNumber,
        PageSize = pageSize,
        TotalRecords = totalRecords
    };
}
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Loading all complaints | Use Skip and Take |
| Pagination without ordering | Always apply stable ordering |
| Not validating page number | Ensure pageNumber >= 1 |
| Very large page size | Limit page size |
| Caching paginated user data incorrectly | Be careful with user/filter-specific keys |

---

## Interview Line

**Pagination improves performance by loading data in smaller pages using Skip and Take instead of loading all records at once.**

```csharp
using Microsoft.Extensions.Caching.Memory;
using SmartSociety.Web.Constants;

namespace SmartSociety.Web.Services
{
    public class ComplaintLookupService
    {
        private readonly IMemoryCache _memoryCache;

        public ComplaintLookupService(IMemoryCache memoryCache)
        {
            _memoryCache = memoryCache;
        }

        public List<string> GetComplaintCategories()
        {
            if (_memoryCache.TryGetValue(
                CacheKeys.ComplaintCategories,
                out List<string>? categories))
            {
                return categories!;
            }

            categories = new List<string>
            {
                "Plumbing",
                "Electrical",
                "Lift",
                "Security",
                "Housekeeping",
                "Parking"
            };

            var cacheOptions = new MemoryCacheEntryOptions()
                .SetSlidingExpiration(TimeSpan.FromMinutes(30))
                .SetAbsoluteExpiration(TimeSpan.FromHours(2));

            _memoryCache.Set(CacheKeys.ComplaintCategories, categories, cacheOptions);

            return categories;
        }
    }
}
```

# 19. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Caching sensitive complaint details | Privacy risk | Avoid sensitive caching |
| Same cache key for all users | Data leakage risk | Use safe keys or avoid user cache |
| No expiration | Stale data problem | Add expiration |
| Long dashboard cache | Wrong counts shown | Use short expiration |
| Not invalidating after update | Dashboard stale | Remove cache on changes |
| Response caching private pages | Sensitive data exposure | Avoid response cache on private pages |
| Loading all complaints | Slow and memory-heavy | Use pagination |
| Include everything | Heavy queries | Load only required data |
| Filtering after ToListAsync | Database pulls too much | Filter before execution |
| Thinking cache fixes bad design | Cache supports optimization, not poor queries | Optimize queries first |

# 26. Interview Explanation

Learner should be able to explain:

```text
In my Smart Society Issue Management System, I use caching carefully to improve performance without compromising security.

I cache safe and frequently used reference data such as complaint categories because it is non-sensitive and changes rarely. I also cache admin dashboard summary for a short duration because it contains aggregate counts, not private complaint details. Whenever complaint data changes, such as create, assign, status update, priority update, or archive, I remove the dashboard summary cache so the next request can rebuild fresh data.

I avoid caching sensitive user-specific complaint details globally because that can expose private data to the wrong user. If user-specific caching is ever required, the cache key must include the user identity and the cache lifetime must be short, but in most cases I prefer optimized database queries.

For performance, I also use query optimization and pagination. List pages should not load all records or all related entities. They should filter at database level, project only required fields into ViewModels, order results, and use Skip and Take for pagination.

This gives the application a safer and more scalable performance foundation.
```
