# 1. Why This Topic Is Important

## What

Most enterprise applications need secure user access.

In the Smart Society Issue Management System, different users have different responsibilities:

```text
Residents raise complaints
Admins assign and monitor complaints
Maintenance staff update complaint status
```

So the application must know:

```text
Who is using the system?
What is the user allowed to do?
```

This is handled by:

```text
Authentication
Authorization
ASP.NET Core Identity
```

---

## Why

Without authentication and authorization, anyone could:

```text
View any complaint
Create fake complaints
Access admin dashboard
Assign complaints to staff
Update complaint status
View resident-sensitive information
Modify workflow records
```

That would make the system unsafe and unprofessional.

---

## Real-Life Analogy

Think of a residential society gate.

Security guard first asks:

```text
Who are you?
```

This is authentication.

Then the guard checks:

```text
Are you allowed to enter this tower?
Are you a resident, visitor, staff, or admin?
```

This is authorization.

In software:

```text
Authentication = Who are you?
Authorization = What are you allowed to access?
```

---

## Smart Society Mapping

| User Type | Authentication Need | Authorization Need |
|---|---|---|
| Resident | Login securely | Raise and view own complaints |
| Admin | Login securely | View all complaints, assign staff, monitor dashboard |
| Staff | Login securely | View assigned complaints and update progress |
| Anonymous User | No login | Can only access public pages |

---

## Interview Line

**Authentication verifies the user's identity, while authorization controls what the authenticated user is allowed to access or perform.**

# 2. Authentication Vs Authorization

## What

Authentication and authorization are related but not the same.

---

## Authentication

Authentication means verifying the identity of the user.

Simple question:

```text
Who are you?
```

Examples:

```text
Email and password login
OTP login
Microsoft login
Google login
JWT token authentication
Cookie-based login
```

In Smart Society:

```text
Resident logs in using email and password.
Admin logs in using email and password.
Staff logs in using email and password.
```

---

## Authorization

Authorization means checking what the user is allowed to do.

Simple question:

```text
What are you allowed to access?
```

Examples:

```text
Resident can raise complaint
Admin can assign complaint
Staff can update assigned complaint
Resident cannot open admin dashboard
Staff cannot view all resident complaints
```

---

## Comparison

| Area | Authentication | Authorization |
|---|---|---|
| Main Question | Who are you? | What can you access? |
| Happens First? | Yes | After authentication |
| Example | Login with email/password | Allow Admin dashboard only to Admin |
| ASP.NET Core Feature | Identity, login, cookie | Roles, claims, policies, `[Authorize]` |
| Smart Society Example | Resident login | Resident can view only own complaints |

---

## Smart Society Example

A resident logs in successfully.

Authentication result:

```text
System knows the user is Deepak Resident.
```

Authorization result:

```text
System checks whether Deepak Resident can access /Admin/Dashboard.
Answer: No.
```

---

## Code Awareness

```csharp
[Authorize]
public class ComplaintsController : Controller
{
}
```

This means:

```text
Only authenticated users can access this controller.
```

Role-based authorization later:

```csharp
[Authorize(Roles = "Admin")]
public class AdminController : Controller
{
}
```

This means:

```text
Only Admin users can access this controller.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Thinking login means access to everything | Login only proves identity; authorization controls access |
| Hiding menu item only in UI | Protect controller/action on server |
| Checking role only in Razor view | Also use `[Authorize]` on controller/action |
| Confusing authentication cookie with authorization | Cookie stores identity; authorization checks permissions |
| Allowing anonymous access to sensitive actions | Use `[Authorize]` |

---

## Interview Line

**Authentication confirms who the user is, while authorization decides what that authenticated user is allowed to do.**

# 4. ApplicationUser

## What

`ApplicationUser` is a custom user class that extends ASP.NET Core Identity's default user.

Usually, it inherits from:

```csharp
IdentityUser
```

Example:

```csharp
using Microsoft.AspNetCore.Identity;

namespace SmartSociety.Web.Models
{
    public class ApplicationUser : IdentityUser
    {
        public string FullName { get; set; } = string.Empty;

        public string? FlatNumber { get; set; }

        public string? TowerBlock { get; set; }
    }
}
```

---

## Why

The default `IdentityUser` already has properties like:

```text
Id
UserName
Email
PasswordHash
PhoneNumber
EmailConfirmed
SecurityStamp
```

But Smart Society needs extra user information:

```text
Full name
Flat number
Tower/block
User type awareness
Resident profile information
Staff department later
```

So we create `ApplicationUser`.

---

## Smart Society Mapping

| Required User Data | ApplicationUser Property |
|---|---|
| Full name | `FullName` |
| Email | Built-in `Email` |
| Phone | Built-in `PhoneNumber` |
| Flat number | `FlatNumber` |
| Tower/block | `TowerBlock` |
| Password | Stored as hash by Identity |
| Role | Stored separately through Identity roles |

---

## Important Note

Do not add password property manually in `ApplicationUser`.

Identity manages password hashing through secure internal properties and services.

Bad:

```csharp
public string Password { get; set; }
```

Better:

```text
Use Identity registration flow.
Identity handles password hashing.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Adding plain Password property | Never store plain password |
| Adding too many unrelated fields | Keep user profile focused |
| Storing role as simple string only | Use Identity roles |
| Forgetting migration after changing ApplicationUser | Add migration and update database |
| Not inheriting from IdentityUser | Inherit from IdentityUser for Identity integration |

---

## Interview Line

**ApplicationUser is a custom Identity user class used to extend the default IdentityUser with project-specific user profile fields such as FullName, FlatNumber, and TowerBlock.**

```csharp
        }

```

---


## Why

A user must have an account before logging in.


---

## Register ViewModel

```csharp
using System.ComponentModel.DataAnnotations;

namespace SmartSociety.Web.ViewModels
{
    public class RegisterViewModel
    {
        [Required(ErrorMessage = "Full name is required.")]
        [Display(Name = "Full Name")]
        public string FullName { get; set; } = string.Empty;

        [Required(ErrorMessage = "Email is required.")]
        [EmailAddress(ErrorMessage = "Enter a valid email address.")]
        public string Email { get; set; } = string.Empty;

        [Required(ErrorMessage = "Password is required.")]
        [DataType(DataType.Password)]
        public string Password { get; set; } = string.Empty;

        [Required(ErrorMessage = "Confirm password is required.")]
        [Compare("Password", ErrorMessage = "Password and confirm password do not match.")]
        [DataType(DataType.Password)]
        [Display(Name = "Confirm Password")]
        public string ConfirmPassword { get; set; } = string.Empty;

        [Display(Name = "Flat Number")]
        public string? FlatNumber { get; set; }

        [Display(Name = "Tower / Block")]
        public string? TowerBlock { get; set; }
    }
}
```

---

## Register Flow

```text
User opens register page
↓
User enters details
↓
POST Register action receives RegisterViewModel
↓
Controller checks ModelState
↓
ApplicationUser object is created
↓
UserManager.CreateAsync() creates user
↓
Identity hashes password
↓
User is saved in AspNetUsers
↓
User can login
```

---

## Register Controller Concept

```csharp
[HttpPost]
public async Task<IActionResult> Register(RegisterViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var user = new ApplicationUser
    {
        UserName = model.Email,
        Email = model.Email,
        FullName = model.FullName,
        FlatNumber = model.FlatNumber,
        TowerBlock = model.TowerBlock
    };

    var result = await _userManager.CreateAsync(user, model.Password);

    if (result.Succeeded)
    {
        TempData["SuccessMessage"] = "Registration successful. Please login.";

        return RedirectToAction(nameof(Login));
    }

    foreach (var error in result.Errors)
    {
        ModelState.AddModelError(string.Empty, error.Description);
    }

    return View(model);
}
```

---

## Smart Society Rule

For production-quality workflow:

```text
Resident self-registration may be allowed.
Admin account should be seeded securely.
Staff account should usually be created by Admin.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Saving password manually | Use UserManager.CreateAsync |
| Not checking IdentityResult | Check `result.Succeeded` |
| Ignoring Identity errors | Add errors to ModelState |
| Letting anyone register as Admin | Admin role should be controlled |
| Not validating email | Use EmailAddress validation |

---

## Interview Line

**Registration creates a new Identity user using UserManager. Identity validates password rules, hashes the password, and stores the user in AspNetUsers.**

# 8. Login

## What

Login means verifying user credentials and signing the user into the application.

---

## Why

Residents, Admins, and Staff must log in before accessing protected features.

Examples:

```text
Resident login before raising complaint
Admin login before assigning complaint
Staff login before updating complaint status
```

---

## Login ViewModel

```csharp
using System.ComponentModel.DataAnnotations;

namespace SmartSociety.Web.ViewModels
{
    public class LoginViewModel
    {
        [Required(ErrorMessage = "Email is required.")]
        [EmailAddress(ErrorMessage = "Enter a valid email address.")]
        public string Email { get; set; } = string.Empty;

        [Required(ErrorMessage = "Password is required.")]
        [DataType(DataType.Password)]
        public string Password { get; set; } = string.Empty;

        [Display(Name = "Remember Me")]
        public bool RememberMe { get; set; }

        public string? ReturnUrl { get; set; }
    }
}
```

---

## Login Flow

```text
User opens login page
↓
User enters email and password
↓
POST Login action receives LoginViewModel
↓
Controller checks ModelState
↓
SignInManager.PasswordSignInAsync() verifies credentials
↓
If success, authentication cookie is created
↓
User is redirected to return URL or dashboard
↓
If failure, error message is shown
```

---

## Login Controller Concept

```csharp
[HttpPost]
public async Task<IActionResult> Login(LoginViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var result = await _signInManager.PasswordSignInAsync(
        model.Email,
        model.Password,
        model.RememberMe,
        lockoutOnFailure: false);

    if (result.Succeeded)
    {
        if (!string.IsNullOrWhiteSpace(model.ReturnUrl) && Url.IsLocalUrl(model.ReturnUrl))
        {
            return Redirect(model.ReturnUrl);
        }

        return RedirectToAction("Index", "Dashboard");
    }

    ModelState.AddModelError(string.Empty, "Invalid login attempt.");

    return View(model);
}
```

---

## ReturnUrl Concept

If user tries to access:

```text
/Complaints/Create
```

without login, application may redirect to:

```text
/Account/Login?ReturnUrl=/Complaints/Create
```

After successful login, user can be sent back to the original page.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Comparing password manually | Use SignInManager |
| Not checking ModelState | Validate login form |
| Redirecting to unsafe external return URL | Use `Url.IsLocalUrl()` |
| Showing exact login failure reason | Use generic message |
| Storing password in cookie/session | Never store password |

---

## Interview Line

**Login verifies user credentials using SignInManager. On successful login, ASP.NET Core Identity creates an authentication cookie that represents the signed-in user.**

# 10. Authentication Cookie

## What

An authentication cookie is a secure cookie created after successful login.

It tells the application that the user is authenticated.

---

## Why

HTTP is stateless.

After login, the server needs a way to recognize the user in future requests.

The authentication cookie solves this.

---

## Flow

```text
User logs in successfully
↓
Identity creates authentication cookie
↓
Browser stores cookie
↓
Browser sends cookie with each request
↓
ASP.NET Core reads cookie
↓
HttpContext.User is populated
↓
[Authorize] can allow/deny access
```

---

## Smart Society Example

Resident logs in.

Then browser requests:

```text
/Complaints/Create
```

The authentication cookie is sent with the request.

ASP.NET Core checks the cookie and knows:

```text
This request belongs to an authenticated resident.
```

---

## Important Note

Do not manually create insecure authentication cookies.

Use ASP.NET Core Identity and SignInManager.

---

## Cookie Security Awareness

Authentication cookies should be:

```text
HttpOnly
Secure in production
Protected by ASP.NET Core data protection
Configured with appropriate expiry
Used with server-side authorization checks
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Manually storing user ID in custom cookie | Use Identity authentication cookie |
| Storing password in cookie | Never store password |
| Trusting custom cookie for role | Use Identity roles/claims |
| Thinking cookie means authorization automatically | Authorization still checks roles/policies |
| Not using HTTPS in production | Use HTTPS |

---

## Interview Line

**An authentication cookie is created after successful login and allows ASP.NET Core to recognize the authenticated user on future requests.**

# 11. Password Hashing Concept

## What

Password hashing means converting a password into a one-way protected hash before storing it.

The actual password is not stored.

---

## Why

If a database is leaked, plain passwords should not be exposed.

Bad storage:

```text
Password = MyPassword123
```

Better storage:

```text
PasswordHash = AQAAAAIAAYagAAAA...
```

Identity stores password hashes, not plain passwords.

---

## How Login Works With Hashing

```text
User enters password
↓
Identity hashes the entered password using password hasher
↓
Identity compares it with stored password hash
↓
If match, login succeeds
```

The original password is not retrieved.

---

## Smart Society Example

Resident registers with password:

```text
Resident@123
```

Identity stores only password hash in `AspNetUsers.PasswordHash`.

During login, Identity verifies the entered password against the hash.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Storing plain password | Never store plain password |
| Creating custom weak hashing | Use Identity password hasher |
| Logging password | Never log passwords |
| Returning password in view/API | Never expose password |
| Thinking encryption and hashing are same | Hashing is one-way; encryption is reversible with key |

---

## Interview Line

**Password hashing stores a one-way hash of the password instead of the plain password. ASP.NET Core Identity handles password hashing automatically.**

# 14. Identity Setup Awareness In Program.cs

## What

ASP.NET Core Identity must be registered in `Program.cs`.

This setup connects:

```text
ApplicationUser
ApplicationDbContext
Identity services
Authentication cookie
Login/logout flow
```

---

## Conceptual Program.cs Setup

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using SmartSociety.Web.Data;
using SmartSociety.Web.Models;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddIdentity<ApplicationUser, IdentityRole>()
    .AddEntityFrameworkStores<ApplicationDbContext>()
    .AddDefaultTokenProviders();

var app = builder.Build();

app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

---

## Important Middleware Order

```text
UseRouting
UseAuthentication
UseAuthorization
MapControllerRoute
```

Authentication must come before authorization.

---

## Why

`UseAuthentication()` reads the authentication cookie and sets `HttpContext.User`.

`UseAuthorization()` checks whether that user is allowed to access the resource.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forgetting `UseAuthentication()` | User will not be authenticated properly |
| Placing authorization before authentication | Authentication must run first |
| Forgetting AddIdentity | Identity services will not work |
| Forgetting DbContext setup | Identity cannot store users |
| Missing migration | Identity tables will not exist |

---

## Interview Line

**ASP.NET Core Identity is registered in Program.cs using AddIdentity and EntityFrameworkStores, and the middleware pipeline must include UseAuthentication before UseAuthorization.**

# 15. Smart Society AccountController Foundation

## What

`AccountController` handles registration, login, and logout.

---

## Controller Structure

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.AspNetCore.Mvc;
using SmartSociety.Web.Models;
using SmartSociety.Web.ViewModels;

namespace SmartSociety.Web.Controllers
{
    public class AccountController : Controller
    {
        private readonly UserManager<ApplicationUser> _userManager;
        private readonly SignInManager<ApplicationUser> _signInManager;
        private readonly ILogger<AccountController> _logger;

        public AccountController(
            UserManager<ApplicationUser> userManager,
            SignInManager<ApplicationUser> signInManager,
            ILogger<AccountController> logger)
        {
            _userManager = userManager;
            _signInManager = signInManager;
            _logger = logger;
        }

        [HttpGet]
        public IActionResult Register()
        {
            return View();
        }

        [HttpPost]
        public async Task<IActionResult> Register(RegisterViewModel model)
        {
            if (!ModelState.IsValid)
            {
                return View(model);
            }

            var user = new ApplicationUser
            {
                UserName = model.Email,
                Email = model.Email,
                FullName = model.FullName,
                FlatNumber = model.FlatNumber,
                TowerBlock = model.TowerBlock
            };

            var result = await _userManager.CreateAsync(user, model.Password);

            if (result.Succeeded)
            {
                _logger.LogInformation("New user registered: {Email}", model.Email);

                TempData["SuccessMessage"] = "Registration successful. Please login.";

                return RedirectToAction(nameof(Login));
            }

            foreach (var error in result.Errors)
            {
                ModelState.AddModelError(string.Empty, error.Description);
            }

            return View(model);
        }

        [HttpGet]
        public IActionResult Login(string? returnUrl = null)
        {
            return View(new LoginViewModel
            {
                ReturnUrl = returnUrl
            });
        }

        [HttpPost]
        public async Task<IActionResult> Login(LoginViewModel model)
        {
            if (!ModelState.IsValid)
            {
                return View(model);
            }

            var result = await _signInManager.PasswordSignInAsync(
                model.Email,
                model.Password,
                model.RememberMe,
                lockoutOnFailure: false);

            if (result.Succeeded)
            {
                _logger.LogInformation("User logged in: {Email}", model.Email);

                if (!string.IsNullOrWhiteSpace(model.ReturnUrl) &&
                    Url.IsLocalUrl(model.ReturnUrl))
                {
                    return Redirect(model.ReturnUrl);
                }

                return RedirectToAction("Index", "Dashboard");
            }

            ModelState.AddModelError(string.Empty, "Invalid login attempt.");

            return View(model);
        }

        [HttpPost]
        public async Task<IActionResult> Logout()
        {
            await _signInManager.SignOutAsync();

            TempData["SuccessMessage"] = "You have logged out successfully.";

            return RedirectToAction("Index", "Home");
        }
    }
}
```

# 16. Smart Society Security Flow

## Resident Login Flow

```text
Resident opens /Account/Login
↓
Resident enters email and password
↓
Login POST calls SignInManager.PasswordSignInAsync
↓
Identity validates credentials
↓
Authentication cookie is created
↓
Resident is redirected to complaint page/dashboard
```

---

## Admin Login Flow

```text
Admin logs in
↓
Identity authenticates admin
↓
Role/authorization module later checks Admin role
↓
Admin accesses /Admin/Dashboard
```

---

## Staff Login Flow

```text
Staff logs in
↓
Identity authenticates staff
↓
Role/authorization module later checks Staff role
↓
Staff accesses assigned complaints
```

# 17. Complete Identity Request Flow

```text
Register
↓
UserManager.CreateAsync
↓
Password is hashed
↓
User saved in AspNetUsers
↓
User logs in
↓
SignInManager.PasswordSignInAsync
↓
Password verified against hash
↓
Authentication cookie created
↓
Browser sends cookie on future requests
↓
UseAuthentication reads cookie
↓
HttpContext.User is populated
↓
UseAuthorization checks access
```

# 18. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Confusing authentication and authorization | Different responsibilities | Authentication first, authorization second |
| Storing password manually | Security risk | Use Identity password hashing |
| Creating users directly with DbContext | Bypasses Identity logic | Use UserManager |
| Logging in manually with custom cookie | Risky and unnecessary | Use SignInManager |
| Forgetting UseAuthentication | User identity not loaded | Add it before UseAuthorization |
| Allowing users to register as Admin | Security risk | Admin creation should be controlled |
| Showing exact login failure reason | Security risk | Use generic error message |
| Not checking IdentityResult | Errors ignored | Add errors to ModelState |
| Storing user role in custom cookie | User can tamper | Use Identity roles |
| Not protecting controllers with Authorize | Login exists but access remains open | Use `[Authorize]` later |

# 21. Short Answers

1. Authentication verifies who the user is.
2. Authorization checks what the user is allowed to access.
3. Authentication verifies identity; authorization checks permission.
4. ASP.NET Core Identity is the built-in user management and authentication system.
5. Identity handles password hashing, user storage, cookies, roles, claims, and security features.
6. ApplicationUser is a custom user class that extends IdentityUser.
7. We extend IdentityUser to add project-specific profile fields.
8. IdentityDbContext is an EF Core DbContext that includes Identity tables.
9. AspNetUsers, AspNetRoles, AspNetUserRoles, AspNetUserClaims, AspNetRoleClaims, AspNetUserLogins, AspNetUserTokens.
10. AspNetUsers stores user account data.
11. AspNetRoles stores role definitions.
12. AspNetUserRoles maps users to roles.
13. Register creates a new user account.
14. Login verifies credentials and signs the user in.
15. Logout signs the user out and removes the authentication session.
16. Authentication cookie identifies the logged-in user across requests.
17. Hashing protects passwords by not storing them in plain text.
18. UserManager manages user creation, lookup, update, and user-related operations.
19. SignInManager manages login, logout, and sign-in behavior.
20. Authentication must load the user before authorization can check permissions.

# 25. Interview Explanation

Learner should be able to explain:

```text
In my Smart Society Issue Management System, I use ASP.NET Core Identity to manage secure login for Residents, Admins, and Maintenance Staff.

Authentication verifies who the user is, while authorization controls what the user can access. Identity helps with registration, login, logout, password hashing, authentication cookies, roles, claims, and user management.

I created an ApplicationUser class that extends IdentityUser so I can store project-specific profile fields such as FullName, FlatNumber, and TowerBlock. I use IdentityDbContext<ApplicationUser> so that EF Core can create and manage Identity tables such as AspNetUsers, AspNetRoles, and AspNetUserRoles.

For registration, I use UserManager.CreateAsync, which validates the user and hashes the password before storing it. For login, I use SignInManager.PasswordSignInAsync, which verifies the password and creates the authentication cookie. For logout, I use SignInManager.SignOutAsync.

This gives the project a secure authentication foundation before implementing role-based access for Resident, Admin, and Staff workflows.
```
