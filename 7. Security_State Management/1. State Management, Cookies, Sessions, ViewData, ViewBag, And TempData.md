# 1. Why HTTP Is Stateless

## What

HTTP is a stateless protocol.

Simple meaning:

```text
Every request is independent.
The server does not automatically remember the previous request.
```

For example:

```text
Request 1: Resident opens complaint form
Request 2: Resident submits complaint form
Request 3: Resident opens complaint list
```

By default, each request is treated separately.

---

## Why

HTTP was designed this way to keep web communication simple and scalable.

But business applications need continuity.

For example, the application may need to remember:

```text
Who is logged in
What message should be shown after redirect
Which filter was selected on dashboard
Which temporary value is needed for next request
```

This is where state management is required.

---

## Real-Life Analogy

Imagine a society office where every time a resident enters, the staff forgets everything from the previous visit.

The resident says:

```text
I came yesterday and submitted a complaint.
```

The staff replies:

```text
I do not remember. Please explain again.
```

That is how stateless HTTP behaves by default.

State management adds controlled memory to the application.

---

## Smart Society Example

Without state management:

```text
Resident submits complaint
↓
Application redirects to complaint list
↓
Success message is lost
```

With state management:

```text
Resident submits complaint
↓
Application stores success message temporarily
↓
Application redirects to complaint list
↓
Success message is displayed once
```

---

## Engineering View

```text
HTTP Request 1
↓
Server processes request
↓
Response returned
↓
Connection ends

HTTP Request 2
↓
Server treats it as a new request
```

State management techniques help preserve selected information across requests.

---

## Interview Line

**HTTP is stateless, which means each request is independent and the server does not automatically remember previous requests. State management is used to preserve selected information across requests.**

# 2. State Management Techniques

## What

State management means storing data temporarily or persistently so the application can remember useful information across requests.

---

## Common State Management Techniques In ASP.NET Core MVC

```text
Cookies
Sessions
TempData
ViewData
ViewBag
Query String
Hidden Fields
Database
Cache
Authentication Cookie
```

In this topic, we focus on:

```text
Cookies
Sessions
TempData
ViewData
ViewBag
```

---

## Why

State management is useful for:

```text
Showing success/error messages
Remembering selected filters
Maintaining user session
Preserving temporary values after redirect
Supporting login workflows
Improving user experience
```

---

## Smart Society Mapping

| Need | Suitable Technique |
|---|---|
| Show success message after complaint creation | TempData |
| Show page title in current request | ViewBag / ViewData |
| Remember dashboard filter preference | Cookie or Session |
| Store logged-in user identity | Authentication cookie, handled by Identity later |
| Store complaint data permanently | Database |
| Store sensitive complaint details temporarily | Avoid cookies/session; use database or secure server-side logic |

---

## Important Rule

State management should be used carefully.

Do not store everything in cookies or session.

Ask:

```text
Is this data temporary?
Is it sensitive?
Does it belong to one request?
Does it need to survive redirect?
Does it need to be stored permanently?
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Storing business data everywhere | Store permanent business data in database |
| Storing sensitive data in cookies | Avoid sensitive data in client-side storage |
| Using Session for everything | Use Session only when truly needed |
| Using ViewBag after redirect | Use TempData after redirect |
| Confusing ViewData, ViewBag, and TempData | Understand their lifetime |

---

## Interview Line

**State management techniques allow ASP.NET Core MVC applications to preserve selected information across requests, but each technique has a different purpose and lifetime.**

# 3. Cookies

## What

A cookie is a small piece of data stored in the user's browser.

The browser sends the cookie back to the server with future requests.

---

## Why

Cookies are useful when the application needs to remember small pieces of information on the client side.

Examples:

```text
User preference
Theme selection
Dashboard filter preference
Language preference
Authentication token/cookie managed by framework
```

---

## Smart Society Example

A dashboard user may choose:

```text
Filter: Pending Complaints
```

The application may remember this preference using a cookie.

Next time the admin opens dashboard, the same filter can be applied.

---

## Basic Cookie Write Example

```csharp
public IActionResult SetDashboardFilter()
{
    Response.Cookies.Append("DashboardFilter", "Pending");

    return RedirectToAction("Dashboard", "Admin");
}
```

---

## Basic Cookie Read Example

```csharp
public IActionResult Dashboard()
{
    var selectedFilter = Request.Cookies["DashboardFilter"];

    ViewBag.SelectedFilter = selectedFilter ?? "All";

    return View();
}
```

---

## Engineering Flow

```text
Server writes cookie in response
↓
Browser stores cookie
↓
Browser sends cookie with next request
↓
Server reads cookie
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Storing full complaint data in cookie | Store only small non-sensitive preferences |
| Storing passwords or tokens manually in cookies | Never store sensitive values directly |
| Assuming user cannot edit cookies | Cookies can be inspected/modified |
| Storing large data in cookies | Cookies have size limitations |
| Using cookies for server-only business state | Use database/session/server-side storage |

---

## Interview Line

**Cookies are small pieces of data stored in the user's browser and sent back to the server with future requests. They are useful for small non-sensitive preferences.**

---

# 4. Cookie Storage

## What

Cookie storage means storing data in the user's browser as key-value pairs.

Example:

```text
Key: DashboardFilter
Value: Pending
```

---

## Why

Cookie storage is useful when data should stay with the browser across multiple requests.

---

## Example With Options

```csharp
public IActionResult SaveDashboardFilter(string filter)
{
    var cookieOptions = new CookieOptions
    {
        Expires = DateTimeOffset.UtcNow.AddDays(7),
        HttpOnly = true,
        Secure = true,
        SameSite = SameSiteMode.Strict
    };

    Response.Cookies.Append("DashboardFilter", filter, cookieOptions);

    return RedirectToAction("Dashboard", "Admin");
}
```

---

## Meaning Of Options

| Option | Meaning |
|---|---|
| `Expires` | Defines when cookie expires |
| `HttpOnly` | Prevents JavaScript from reading cookie |
| `Secure` | Sends cookie only over HTTPS |
| `SameSite` | Helps reduce cross-site request risks |

---

## Smart Society Safe Cookie Example

Acceptable cookie data:

```text
Dashboard filter preference
Theme preference
Page size preference
Language preference
```

Avoid storing:

```text
Complaint description
Resident phone number
User password
Assigned staff ID as trusted value
Sensitive complaint evidence path
Authorization decision data
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Trusting cookie values blindly | Validate cookie values before use |
| Storing sensitive data in cookies | Avoid sensitive data |
| Not setting secure options | Use HttpOnly, Secure, SameSite where appropriate |
| Storing large JSON in cookies | Keep cookies small |
| Using cookie as source of truth for business decisions | Use database/server-side checks |

---

## Interview Line

**Cookie storage keeps small key-value data in the browser, but values must be treated as untrusted and sensitive data should not be stored there.**

---

# 5. Cookie Expiry

## What

Cookie expiry defines how long a cookie remains available in the browser.

---

## Types Of Cookies

| Type | Meaning |
|---|---|
| Session Cookie | Removed when browser session ends |
| Persistent Cookie | Stored until expiry time |

---

## Persistent Cookie Example

```csharp
Response.Cookies.Append(
    "DashboardFilter",
    "Pending",
    new CookieOptions
    {
        Expires = DateTimeOffset.UtcNow.AddDays(7)
    });
```

This cookie will remain for 7 days unless deleted earlier.

---

## Deleting Cookie

```csharp
Response.Cookies.Delete("DashboardFilter");
```

---

## Smart Society Example

Dashboard filter preference can expire after 7 days:

```text
Admin prefers Pending complaint filter.
System remembers it for 7 days.
After expiry, dashboard shows All complaints again.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Never expiring cookies | Use reasonable expiry |
| Using long expiry for sensitive data | Avoid storing sensitive data |
| Thinking deleted server variable removes browser cookie | Use `Response.Cookies.Delete()` |
| Not considering shared computers | Do not store sensitive data in persistent cookies |

---

## Interview Line

**Cookie expiry controls how long a browser keeps a cookie. Persistent cookies have an expiry date, while session cookies end when the browser session ends.**

# 6. Secure Cookies

## What

Secure cookies are configured to reduce security risks.

Important options:

```text
HttpOnly
Secure
SameSite
Expires
IsEssential when needed
```

---

## Cookie Security Options

| Option | Purpose |
|---|---|
| `HttpOnly` | Prevents JavaScript access |
| `Secure` | Sends cookie only through HTTPS |
| `SameSite` | Controls cross-site cookie sending |
| `Expires` | Controls cookie lifetime |
| `IsEssential` | Marks cookie as essential in consent scenarios |

---

## Example

```csharp
var options = new CookieOptions
{
    HttpOnly = true,
    Secure = true,
    SameSite = SameSiteMode.Strict,
    Expires = DateTimeOffset.UtcNow.AddDays(7)
};

Response.Cookies.Append("DashboardFilter", "Pending", options);
```

---

## Smart Society Security Rule

Do not store these in cookies:

```text
Complaint full description
Resident personal data
Admin authorization decisions
Staff assignment authorization
Uploaded file paths if sensitive
Password
Tokens manually
```

---

## Why

Cookies are stored on the client side.

Even if protected by options, they should not be treated as secure storage for sensitive business data.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Storing secret information in cookies | Store sensitive data server-side |
| Not using HTTPS secure cookies | Use Secure in production |
| Allowing JavaScript access to sensitive cookies | Use HttpOnly |
| Trusting role from cookie manually | Use ASP.NET Core Identity/claims authorization |
| Storing complaint ownership in cookie | Check ownership from database/user context |

---

## Interview Line

**Secure cookies use options such as HttpOnly, Secure, and SameSite to reduce risks, but sensitive business data should still not be stored in client-side cookies.**

# 7. Sessions

## What

Session stores user-specific data on the server side for a limited time.

The browser usually stores only a session identifier cookie.

---

## Why

Session is useful when the application needs to store temporary user-specific data across multiple requests.

Examples:

```text
Temporary wizard data
Short-lived filter preference
Temporary selected values
Multi-step form progress
```

---

## Smart Society Example

Session may be used to remember:

```text
Selected dashboard filter during admin session
Temporary multi-step complaint draft
Current selected society block during session
```

But complaint data itself should be saved in the database.

---

## Session Write Example

```csharp
HttpContext.Session.SetString("DashboardFilter", "Pending");
```

---

## Session Read Example

```csharp
var filter = HttpContext.Session.GetString("DashboardFilter");
```

---

## Session Remove Example

```csharp
HttpContext.Session.Remove("DashboardFilter");
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using Session as database replacement | Store permanent data in database |
| Storing sensitive information without need | Avoid sensitive session data |
| Assuming session lasts forever | Session expires |
| Storing large objects in session | Keep session small |
| Depending heavily on session for core workflow | Prefer database-backed workflow |

---

## Interview Line

**Session stores temporary user-specific data on the server side, while the browser holds a session identifier. It should be used carefully and not as a replacement for database storage.**

---

# 8. Session Vs Cookie

## What

Cookies and sessions both help manage state, but they are different.

---

## Comparison

| Area | Cookie | Session |
|---|---|---|
| Storage Location | Browser/client | Server |
| Data Size | Small | More than cookie, but should still be limited |
| Security | User can inspect/modify | Server-side, safer but still must be managed |
| Lifetime | Based on expiry/browser | Based on session timeout |
| Sent With Every Request | Yes | Session ID cookie is sent |
| Best For | Small preferences | Temporary server-side user data |

---

## Smart Society Decision Table

| Requirement | Better Choice | Reason |
|---|---|---|
| Remember dashboard filter for 7 days | Cookie | Small preference |
| Show success message after redirect | TempData | One-time message |
| Temporary multi-step complaint draft | Session | Short-lived server-side data |
| Store complaint details permanently | Database | Business data |
| Store login information | Identity Authentication Cookie | Framework-managed |
| Store sensitive complaint description | Database | Not cookie/session |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Thinking session is always secure | Still avoid unnecessary sensitive data |
| Thinking cookie and session are same | Cookie is client-side; session is server-side |
| Using session for long-term business data | Use database |
| Using cookie for sensitive values | Avoid it |

---

## Interview Line

**Cookies store small data in the browser, while session stores temporary user-specific data on the server side using a session identifier cookie.**

# 9. Session Configuration Awareness

## What

ASP.NET Core does not use session automatically unless configured.

We need to add session services and middleware.

---

## Configure Session In Program.cs

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddDistributedMemoryCache();

builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromMinutes(20);
    options.Cookie.HttpOnly = true;
    options.Cookie.IsEssential = true;
});

var app = builder.Build();

app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseSession();

app.UseAuthorization();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

---

## Important Middleware Order

`UseSession()` should be placed after:

```text
UseRouting()
```

and before endpoint/action execution.

Common placement:

```text
UseRouting
UseSession
UseAuthentication
UseAuthorization
MapControllerRoute
```

When authentication is added, middleware order must be reviewed carefully.

---

## Smart Society Example

Store dashboard filter in session:

```csharp
public IActionResult SetFilter(string filter)
{
    HttpContext.Session.SetString("DashboardFilter", filter);

    return RedirectToAction("Dashboard", "Admin");
}
```

Read dashboard filter:

```csharp
public IActionResult Dashboard()
{
    var filter = HttpContext.Session.GetString("DashboardFilter") ?? "All";

    ViewBag.SelectedFilter = filter;

    return View();
}
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using Session without configuration | Add session services and middleware |
| Forgetting `AddDistributedMemoryCache()` | Required for in-memory session |
| Forgetting `UseSession()` | Session will not work |
| Placing UseSession incorrectly | Add in correct middleware order |
| Storing complex objects directly | Serialize carefully if needed, but keep simple |

---

## Interview Line

**Session in ASP.NET Core must be configured using AddSession and UseSession. It stores temporary user-specific data server-side and uses a cookie to track the session ID.**

# 10. TempData

## What

`TempData` stores data temporarily between two requests.

It is commonly used after redirects.

---

## Why

After a successful POST, we usually redirect.

This is called the Post-Redirect-Get pattern.

```text
POST complaint form
↓
Create complaint
↓
Set TempData success message
↓
Redirect to complaint list
↓
Display success message once
```

---

## Smart Society Example

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

Display in view:

```html
@if (TempData["SuccessMessage"] != null)
{
    <div class="alert alert-success">
        @TempData["SuccessMessage"]
    </div>
}
```

---

## When To Use TempData

Use TempData for:

```text
Success messages
Error messages after redirect
Warning messages
One-time confirmation
Short flash messages
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using ViewBag after redirect | Use TempData |
| Storing large data in TempData | Store small messages only |
| Expecting TempData to last forever | It is temporary |
| Storing sensitive data in TempData | Avoid sensitive information |

---

## Interview Line

**TempData is used to pass short-lived data between requests, especially success or error messages after redirects.**

# 14. Avoiding Sensitive Data In State

## What

Sensitive data means information that should not be exposed unnecessarily or stored insecurely.

In Smart Society, sensitive data may include:

```text
Resident phone number
Resident email
Complaint full description
Complaint attachment path
Personal identity data
Security-related complaint details
Authentication token
Password
Internal admin remarks
```

---

## Why

State mechanisms like cookies and ViewBag are not suitable for sensitive data.

Even Session should not become a dumping ground for sensitive business data.

---

## Safe Rule

```text
Permanent business data → Database
Authentication information → ASP.NET Core Identity/framework-managed auth
Temporary one-time messages → TempData
Small non-sensitive preferences → Cookie or Session
Current view labels → ViewBag/ViewData
Sensitive complaint details → Database with authorization checks
```

---

## Bad Example

```csharp
Response.Cookies.Append("ComplaintDescription", model.Description);
```

This is bad because complaint description can be sensitive.

---

## Better Example

```text
Store complaint description in database.
Use complaint ID to retrieve it securely.
Check user authorization before showing it.
```

---

## Smart Society Secure State Table

| Data | Where To Store |
|---|---|
| Complaint title/description | Database |
| Complaint image path | Database, access-controlled |
| Success message | TempData |
| Dashboard filter preference | Cookie/Session |
| Logged-in user identity | ASP.NET Core Identity auth cookie |
| User role | Identity/claims, not manual cookie |
| Admin internal notes | Database with authorization |
| Temporary page title | ViewBag/ViewData |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Storing sensitive complaint data in cookies | Store in database |
| Trusting role stored in custom cookie | Use Identity authorization |
| Storing large objects in session | Use database/cache carefully |
| Showing exception details through TempData | Log exception, show friendly error |
| Using client-side state for authorization decisions | Always check authorization server-side |

---

## Interview Line

**Sensitive data should not be stored in cookies, ViewBag, or unnecessary session state. Business data should be stored securely in the database and protected by server-side authorization.**

}

# 17. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Using ViewBag after redirect | ViewBag works only in same request | Use TempData |
| Storing complaint data in cookie | Cookie is client-side | Store complaint data in database |
| Storing everything in session | Session becomes heavy | Store only temporary user-specific data |
| Trusting cookie filter blindly | User can modify cookie | Validate allowed values |
| Showing exception details in flash messages | Security risk | Log details, show friendly message |
| Not setting cookie security options | Increases risk | Use HttpOnly, Secure, SameSite |
| Forgetting session configuration | Session will not work | Add AddSession and UseSession |
| Using state for authorization decisions | Unsafe | Use server-side authorization and database checks |
| Storing large objects in TempData | Bad design | Store only short messages |
| Not clearing unneeded state | Can cause stale behavior | Remove or expire state properly |

# 20. Short Answers

1. HTTP is stateless because each request is independent and the server does not automatically remember previous requests.
2. State management preserves selected information across requests.
3. Cookies, sessions, TempData, ViewData, ViewBag, query string, hidden fields, cache, and database.
4. A cookie is small data stored in the user's browser.
5. Cookies are stored on the client/browser.
6. Cookie expiry defines how long the browser keeps the cookie.
7. HttpOnly, Secure, SameSite, Expires, and IsEssential.
8. Session stores temporary user-specific data on the server.
9. Session data is stored server-side, while the browser stores a session identifier.
10. Cookie is client-side; session is server-side.
11. Add `AddDistributedMemoryCache`, `AddSession`, and `UseSession`.
12. TempData stores short-lived data between requests.
13. TempData should be used for flash messages after redirects.
14. ViewData is a dictionary for passing data from controller to view in the same request.
15. ViewBag is a dynamic wrapper over ViewData.
16. ViewBag uses dynamic property syntax, while ViewData uses dictionary syntax.
17. ViewBag/ViewData do not survive redirect, but TempData does.
18. Cookies are client-side and can be inspected or modified.
19. Complaint descriptions, attachments, admin notes, user data, and workflow history.
20. The database with proper authorization checks.

In my Smart Society Issue Management System, I used state management carefully.
