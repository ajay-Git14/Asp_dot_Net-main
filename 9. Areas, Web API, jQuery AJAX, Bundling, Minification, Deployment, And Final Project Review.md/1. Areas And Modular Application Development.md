# 2. Understanding Areas

## What

An **Area** is a feature in ASP.NET Core MVC that allows you to organize related controllers and views into a separate module.

An Area usually contains:

```text
Controllers
Views
Models or ViewModels if needed
```

Example:

```text
Areas/Admin
Areas/Resident
Areas/Staff
```

---

## Why

Areas are useful when the application has multiple functional sections.

Examples:

```text
Admin panel
Customer portal
Employee portal
Reporting module
Support module
Staff module
```

In Smart Society:

```text
Admin manages complaints and assignments.
Resident raises and tracks complaints.
Staff handles assigned complaints.
```

Each can become a separate Area.

---

## Without Areas

```text
Controllers/AdminController.cs
Controllers/ResidentController.cs
Controllers/StaffController.cs
Views/Admin
Views/Resident
Views/Staff
```

This works for small apps.

---

## With Areas

```text
Areas/Admin/Controllers/DashboardController.cs
Areas/Resident/Controllers/MyComplaintsController.cs
Areas/Staff/Controllers/AssignedComplaintsController.cs
```

This is cleaner for larger apps.

---

## Smart Society Area Responsibilities

| Area | Responsibility |
|---|---|
| Admin | Dashboard, assignment, reports, user monitoring |
| Resident | My complaints, create complaint, complaint details |
| Staff | Assigned complaints, status updates, resolution proof |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Creating Areas for very small apps unnecessarily | Use Areas when modules are clearly separate |
| Putting all controllers in root after app grows | Move role/module-specific controllers into Areas |
| Thinking Area replaces authorization | Areas organize code; authorization still required |
| Forgetting route configuration for Areas | Add area route in Program.cs |
| Not using `[Area]` attribute | Add `[Area("Admin")]`, `[Area("Resident")]`, etc. |

---

## Interview Line

**An Area is a modular section of an ASP.NET Core MVC application that groups related controllers and views under a separate feature or user module.**

# 5. Area Controllers

## What

Area controllers are controllers placed inside an Area and marked with the `[Area]` attribute.

Example:

```csharp
[Area("Admin")]
public class DashboardController : Controller
{
}
```

---

## Why

The `[Area]` attribute tells MVC that this controller belongs to a specific Area.

Without this attribute, routing may not find the controller as an Area controller.

---

## Admin Dashboard Controller

Create:

```text
Areas/Admin/Controllers/DashboardController.cs
```

Code:

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

namespace SmartSociety.Web.Areas.Admin.Controllers
{
    [Area("Admin")]
    [Authorize(Roles = "Admin")]
    public class DashboardController : Controller
    {
        public IActionResult Index()
        {
            return View();
        }
    }
}
```

---

## Resident MyComplaints Controller

Create:

```text
Areas/Resident/Controllers/MyComplaintsController.cs
```

Code:

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

namespace SmartSociety.Web.Areas.Resident.Controllers
{
    [Area("Resident")]
    [Authorize(Roles = "Resident")]
    public class MyComplaintsController : Controller
    {
        public IActionResult Index()
        {
            return View();
        }
    }
}
```

---

## Staff AssignedComplaints Controller

Create:

```text
Areas/Staff/Controllers/AssignedComplaintsController.cs
```

Code:

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
```

---

## Smart Society Security Rule

Area organization does not automatically protect the area.

Still use:

```text
[Authorize(Roles = "Admin")]
[Authorize(Roles = "Resident")]
[Authorize(Roles = "Staff")]
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forgetting `[Area("Admin")]` | Add Area attribute |
| Forgetting role authorization | Add `[Authorize(Roles = "...")]` |
| Wrong namespace | Use clear area-based namespace |
| Using same controller name without route clarity | Area separates modules |
| Assuming folder alone makes it Area controller | Attribute and routing are required |

---

## Interview Line

**Area controllers are normal MVC controllers placed under an Area and decorated with `[Area("AreaName")]` to identify their module.**

# 7. Defining Area Routes

## What

Area routes define how URLs map to controllers inside Areas.

---

## Why

The application must understand URLs like:

```text
/Admin/Dashboard
/Resident/MyComplaints
/Staff/AssignedComplaints
```

These should map to Area controllers.

---

## Program.cs Area Route

Add this before default route:

```csharp
app.MapControllerRoute(
    name: "areas",
    pattern: "{area:exists}/{controller=Dashboard}/{action=Index}/{id?}");
```

Then keep default route:

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
```

---

## Full Routing Example

```csharp
app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllerRoute(
    name: "areas",
    pattern: "{area:exists}/{controller=Dashboard}/{action=Index}/{id?}");

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

---

## Meaning

```text
{area:exists} → Match only when area exists
{controller=Dashboard} → Default controller inside area
{action=Index} → Default action
{id?} → Optional id
```

---

## Smart Society Route Mapping

| URL | Area | Controller | Action |
|---|---|---|---|
| `/Admin/Dashboard` | Admin | Dashboard | Index |
| `/Resident/MyComplaints` | Resident | MyComplaints | Index |
| `/Staff/AssignedComplaints` | Staff | AssignedComplaints | Index |

---

## Important Route Order

Area route should be placed before default route.

```text
Specific area route first
Default route later
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forgetting area route | Area URLs may not work |
| Placing default route before area route | Area matching may fail/confuse |
| Missing `{area:exists}` | Area routing is not properly constrained |
| Wrong controller default for all areas | Use explicit links when needed |
| Not testing Area URLs manually | Test each route |

---

## Interview Line

**Area routes are configured in Program.cs using `{area:exists}` so URLs can map to controllers inside specific Areas.**

# 8. Linking Between Areas

## What

Linking between Areas means creating links from one part of the application to another Area.

Example:

```text
Home page → Admin Dashboard
Admin Dashboard → Staff Assignment
Resident Dashboard → My Complaints
```

---

## Why

In modular applications, navigation must clearly specify:

```text
Area
Controller
Action
Route values
```

---

## Link To Admin Area

```html
<a asp-area="Admin"
   asp-controller="Dashboard"
   asp-action="Index">
    Admin Dashboard
</a>
```

---

## Link To Resident Area

```html
<a asp-area="Resident"
   asp-controller="MyComplaints"
   asp-action="Index">
    My Complaints
</a>
```

---

## Link To Staff Area

```html
<a asp-area="Staff"
   asp-controller="AssignedComplaints"
   asp-action="Index">
    Assigned Complaints
</a>
```

---

## Link From Area Back To Root Controller

To link to root HomeController from an Area:

```html
<a asp-area=""
   asp-controller="Home"
   asp-action="Index">
    Home
</a>
```

Important:

```text
asp-area="" means no Area/root application.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forgetting asp-area in links | Link may go to wrong controller |
| Using asp-area when linking to root | Use `asp-area=""` |
| Hardcoding URLs everywhere | Use Tag Helpers |
| Wrong controller name | Use controller name without Controller suffix |
| Link visible to wrong role | Combine with role-based navigation |

---

## Interview Line

**When linking between Areas, use `asp-area`, `asp-controller`, and `asp-action` so MVC generates the correct modular route.**

# 9. asp-area

## What

`asp-area` is a Razor Tag Helper attribute used to specify the Area for a link or form.

Example:

```html
<a asp-area="Admin" asp-controller="Dashboard" asp-action="Index">
    Admin Dashboard
</a>
```

---

## Why

Without `asp-area`, MVC may look for a root controller instead of Area controller.

---

## Smart Society Examples

### Admin Dashboard

```html
<a asp-area="Admin"
   asp-controller="Dashboard"
   asp-action="Index">
    Admin Dashboard
</a>
```

Generated route:

```text
/Admin/Dashboard
```

---

### Resident My Complaints

```html
<a asp-area="Resident"
   asp-controller="MyComplaints"
   asp-action="Index">
    My Complaints
</a>
```

Generated route:

```text
/Resident/MyComplaints
```

---

### Staff Assigned Complaints

```html
<a asp-area="Staff"
   asp-controller="AssignedComplaints"
   asp-action="Index">
    Assigned Complaints
</a>
```

Generated route:

```text
/Staff/AssignedComplaints
```

---

### Root Home Link From Any Area

```html
<a asp-area=""
   asp-controller="Home"
   asp-action="Index">
    Home
</a>
```

---

## Forms With asp-area

```html

      asp-controller="ComplaintAssignment"
```

## Common Mistake

| Mistake | Correction |
|---|---|
| Missing asp-area for Area link | Add correct asp-area |
| Using wrong Area name | Match folder and `[Area]` name |
| Forgetting asp-area="" for root link | Clear area for root controllers |
| Hardcoding `/Admin/Dashboard` | Prefer Tag Helpers |
| Not adding Tag Helpers import | Add `_ViewImports.cshtml` |

---

## Interview Line

**asp-area tells Razor Tag Helpers which Area should be used when generating links or forms.**

# 10. Role-Based Area Navigation

## What

Role-based area navigation means showing navigation links based on the logged-in user's role.

---

## Why

Different users should see different navigation options.

A resident should not see admin assignment links.

A staff user should not see resident complaint submission as staff workflow.

An admin should see admin tools.

---

## Smart Society Navigation Rules

| Role | Navigation |
|---|---|
| Resident | My Complaints, Raise Complaint |
| Admin | Dashboard, Assign Complaints, Reports |
| Staff | Assigned Complaints, Update Status |
| Anonymous | Login, Register, Home |

---

## Razor Role-Based Navigation Example

```html
@if (User.Identity != null && User.Identity.IsAuthenticated)
{
    if (User.IsInRole("Admin"))
    {
        <a asp-area="Admin"
           asp-controller="Dashboard"
           asp-action="Index">
            Admin Dashboard
        </a>
    }

    if (User.IsInRole("Resident"))
    {
        <a asp-area="Resident"
           asp-controller="MyComplaints"
           asp-action="Index">
            My Complaints
        </a>
    }

    if (User.IsInRole("Staff"))
    {
        <a asp-area="Staff"
           asp-controller="AssignedComplaints"
           asp-action="Index">
            Assigned Complaints
        </a>
    }
}
else
{
    <a asp-area=""
       asp-controller="Account"
       asp-action="Login">
        Login
    </a>
}
```

---

## Important Security Rule

Role-based navigation only controls what user sees in UI.

It does not secure the action.

Always protect controllers/actions:

```csharp
[Authorize(Roles = "Admin")]
```

---

## Better With Role Constants

```csharp
public static class AppRoles
{
    public const string Resident = "Resident";
    public const string Admin = "Admin";
    public const string Staff = "Staff";
}
```

In Razor, direct constants require importing namespace or using simpler string values for now.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Hiding links but not protecting actions | Use `[Authorize]` |
| Showing all links to all users | Use role-based checks |
| Hardcoding routes manually | Use Tag Helpers |
| Forgetting anonymous user handling | Show Login/Register |
| Role names inconsistent | Use constants where possible |

---

## Interview Line

**Role-based area navigation shows Admin, Resident, or Staff links based on user roles, but server-side authorization must still protect the Area controllers.**

# 11. Modular Application Structure

## What

Modular application structure means organizing the application around features or business modules instead of keeping everything flat.

---

## Why

Large applications become easier to maintain when separated into modules.

Smart Society modules:

```text
Admin module
Resident module
Staff module
Complaint module
Dashboard module
Reports module
Identity/security module
```

Areas help with MVC module separation.

Services and repositories help with business/data separation.

---

## Smart Society Modular Structure

```text
Areas
├── Admin
│   ├── Controllers
│   └── Views
├── Resident
│   ├── Controllers
│   └── Views
└── Staff
    ├── Controllers
    └── Views

Services
├── ComplaintService
├── DashboardService
└── ComplaintLookupService

Repositories
├── ComplaintRepository
└── GenericRepository

Models
├── Complaint
├── ComplaintComment
├── ComplaintAttachment
└── ComplaintStatusHistory
```

---

## Module Responsibility

| Module | Responsibility |
|---|---|
| Admin Area | Admin dashboard, assignment, reports |
| Resident Area | My complaints, create complaint, track complaint |
| Staff Area | Assigned complaints, status updates, proof upload |
| Services | Business workflows |
| Repositories | Data access |
| Models | Database entities |
| ViewModels | Screen-specific data |

---

## Enterprise Thinking

A modular project should help answer:

```text
Where should this feature go?
Who owns this workflow?
Which role uses this screen?
Which service handles this business rule?
Which repository handles data access?
Which route should expose this feature?
```

---

## When Not To Use Areas

Areas may be unnecessary if:

```text
Application is very small
Only few controllers exist
No clear module separation exists
Project is a simple demo
```

But for Smart Society, Areas are useful because roles and modules are clearly separated.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Creating Areas but keeping all logic in one service/controller | Keep module separation meaningful |
| Duplicating same logic in every Area | Reuse services |
| Creating separate entities per Area unnecessarily | Share domain models where appropriate |
| Putting business rules in Area controllers | Keep rules in service |
| Ignoring route/navigation consistency | Standardize Area routes |

---

## Interview Line

**Modular application structure organizes large MVC applications by business areas such as Admin, Resident, and Staff, improving maintainability and clarity.**

```text

```

Possible causes:

```text
Area route missing
Controller missing [Area("Admin")]
Controller not inside correct namespace/folder
Action missing
User not authorized and redirect behavior misunderstood
```

Expected view path:

```text
Areas/Admin/Views/Dashboard/Index.cshtml
```

Check:

```text
Area name
Controller name
View folder name
Action name
File spelling
```

---

## Common Problem 3: Link Goes To Root Controller

Cause:

```text
asp-area missing
```

Fix:

```html
<a asp-area="Admin" asp-controller="Dashboard" asp-action="Index">
    Admin Dashboard
</a>
```

---

## Common Problem 4: Cannot Link Back To Home

Inside Area, link may stay in same area unless area is cleared.

Fix:

```html
<a asp-area="" asp-controller="Home" asp-action="Index">
    Home
</a>
```

## Common Problem 5: Access Denied

Cause:

```text
User is authenticated but does not have required role.
```

Fix:

```text
Check user role assignment
Check Authorize attribute
Check seeded roles
Check user-role mapping
```

# 15. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Missing `[Area]` attribute | MVC may not resolve Area controller | Add `[Area("Admin")]` |
| Missing area route | Area URLs do not work | Add `{area:exists}` route |
| Area route after default route | Routing confusion | Put Area route first |
| Wrong view folder | View not found | Use Area view convention |
| Forgetting asp-area | Link goes to wrong place | Add asp-area |
| Not clearing asp-area for root links | Home link may search within area | Use `asp-area=""` |
| Relying only on Area for security | Area is organization only | Use `[Authorize]` |
| Showing all Area links to all users | Poor UX/security confusion | Use role-based navigation |
| Duplicating business logic inside Area controllers | Maintenance issue | Use shared services |
| Creating too many Areas too early | Complexity | Use Areas when module boundaries are clear |
