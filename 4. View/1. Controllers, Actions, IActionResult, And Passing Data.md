# 1. What Is A Controller?

## What

A **Controller** is a class in ASP.NET Core MVC that handles incoming browser requests.

In simple words:

```text
Controller receives the request,
decides what action should happen,
calls required service/business logic,
and returns a response.
```

Example:

```csharp
public class ComplaintsController : Controller
{
    public IActionResult Index()
    {
        return View();
    }
}
```

Here:

```text
ComplaintsController handles complaint-related requests.
Index() is an action method.
return View() sends a Razor view response.
```

---

## Why

Controllers are needed because the application must respond to user actions.

For example, in the **Smart Society Issue Management System**, users will do things like:

```text
Open complaint list
Open complaint creation form
Submit complaint form
View complaint details
Open admin dashboard
View dashboard summary
```

Each request needs a controller action.

---

## When

Use controllers when the application needs to handle:

```text
Page requests
Form submissions
Data display
Redirects
Errors
JSON responses
Role-based page actions
```

---

## How

A controller class usually:

```text
Inherits from Controller
Contains action methods
Uses services through Dependency Injection
Returns IActionResult
```

Example:

```csharp
public class ComplaintsController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintsController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }

    public IActionResult Index()
    {
        return View();
    }
}
```

---

## Real-Life Analogy

Think of a society office reception desk.

```text
Resident comes with a request
Reception identifies the request
Reception sends it to the right department
Reception gives a response back to resident
```

Controller works like that reception desk.

```text
Browser sends request
Controller identifies request
Controller calls service
Controller returns response
```

---

## Smart Society Mapping

| User Request                      | Controller             |
| --------------------------------- | ---------------------- |
| Resident wants to see complaints  | `ComplaintsController` |
| Resident wants to raise complaint | `ComplaintsController` |
| Admin wants dashboard             | `AdminController`      |
| Admin wants complaint summary     | `DashboardController`  |
| Staff wants assigned work later   | `StaffController`      |

---

## Interview Line

**A controller in ASP.NET Core MVC receives incoming requests, coordinates with the service layer, and returns a response such as a view, redirect, JSON, or error result.**

# 2. Controller Responsibility

## What

Controller responsibility means what a controller should and should not do.

A controller should focus on request-response coordination.

---

## Controller Should Do

```text
Receive request
Accept route/form/query values
Check ModelState
Call service layer
Handle service result
Return View, Redirect, JSON, NotFound, or BadRequest
Set TempData success/error messages
```

---

## Controller Should Not Do

```text
Write long business logic
Write direct database queries everywhere
Handle complex workflow rules
Perform file processing completely inside action
Calculate reports directly in action
Send emails directly from controller
Contain repeated logic
```

---

## Good Controller Style

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

The controller:

```text
Receives form
Checks validation
Calls service
Sets success message
Redirects user
```

That is clean.

---

## Bad Controller Style

```csharp
[HttpPost]
public IActionResult Create(ComplaintCreateViewModel model)
{
    // Build complaint object
    // Validate business rules
    // Open database connection
    // Save complaint
    // Calculate dashboard
    // Send email
    // Write file
    // Update status history
    // Return response

    return View();
}
```

This is bad because the controller becomes too heavy.

---

## Smart Society Mapping

`ComplaintsController` should handle:

```text
Complaint page requests
Complaint form submissions
Basic ModelState check
Calling IComplaintService
Returning view or redirect
Returning NotFound for invalid complaint ID
```

`ComplaintService` should handle:

```text
Complaint creation logic
Complaint listing logic
Complaint details retrieval
Status update business rules
Dashboard summary preparation
Database interaction later
```

---

## Interview Line

**A controller should coordinate the request and response flow, while business logic should be placed in services. This keeps the controller clean and maintainable.**

---

# 3. Controller Vs Service

## What

Controller and service are different.

| Layer      | Main Responsibility               |
| ---------- | --------------------------------- |
| Controller | Handles HTTP request and response |
| Service    | Handles business logic            |

---

## Controller

Controller is web-facing.

It knows about:

```text
HTTP request
Route values
ModelState
Views
Redirects
TempData
IActionResult
```

---

## Service

Service is business-facing.

It knows about:

```text
Business rules
Complaint creation
Status update
Dashboard calculations
Database operations later
Logging
Configuration
```

---

## Example Flow

```text
Browser
↓
ComplaintsController
↓
IComplaintService
↓
ComplaintService
↓
Database later
```

---

## Smart Society Example

Resident submits complaint form.

Controller responsibility:

```text
Receive form
Check ModelState
Call CreateComplaintAsync()
Redirect after success
```

Service responsibility:

```text
Read default status
Create complaint object
Apply complaint rules
Save complaint later using DbContext
Log complaint creation
```

---

## Code Example

### Controller

```csharp
public class ComplaintsController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintsController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }

    [HttpPost]
    public async Task<IActionResult> Create(ComplaintCreateViewModel model)
    {
        if (!ModelState.IsValid)
        {
            return View(model);
        }

        await _complaintService.CreateComplaintAsync(model);

        return RedirectToAction(nameof(Index));
    }
}
```

### Service

```csharp
public class ComplaintService : IComplaintService
{
    public Task CreateComplaintAsync(ComplaintCreateViewModel model)
    {
        // Business logic will come here.
        return Task.CompletedTask;
    }
}
```

---

## Common Mistake

| Mistake                                                 | Correction                                         |
| ------------------------------------------------------- | -------------------------------------------------- |
| Treating controller as business layer                   | Controller should coordinate request-response only |
| Returning View from service                             | Service should not know Razor views                |
| Injecting controller into service                       | Service should not depend on controller            |
| Writing duplicate logic in multiple actions             | Move repeated logic to service                     |
| Directly querying database from every controller action | Use service/repository structure                   |

---

## Interview Line

**Controller handles HTTP flow, while service handles business logic. In my Smart Society project, ComplaintsController receives complaint requests and ComplaintService processes complaint-related operations.**

# 4. Action Methods

## What

An **action method** is a public method inside a controller that handles a specific request.

Example:

```csharp
public IActionResult Index()
{
    return View();
}
```

Here:

```text
Index() is an action method.
```

---

## Why

Different user actions require different methods.

For Smart Society:

```text
View complaint list → Index()
Open complaint form → Create() GET
Submit complaint form → Create() POST
View complaint details → Details(int id)
```

---

## Common Action Names

| Action            | Purpose                    |
| ----------------- | -------------------------- |
| `Index()`         | List or landing page       |
| `Create()` GET    | Display create form        |
| `Create()` POST   | Receive submitted form     |
| `Details(int id)` | Show details of one record |
| `Edit(int id)`    | Display edit form          |
| `Delete(int id)`  | Delete/confirm delete      |
| `Dashboard()`     | Show summary dashboard     |

---

## Smart Society Actions

```csharp
public IActionResult Index()
{
    return View();
}

[HttpGet]
public IActionResult Create()
{
    return View();
}

public IActionResult Details(int id)
{
    return View();
}
```

---

## GET And POST Create Actions

For forms, we normally create two actions:

```csharp
[HttpGet]
public IActionResult Create()
{
    return View();
}

[HttpPost]
public IActionResult Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    return RedirectToAction(nameof(Index));
}
```

## Why Two Create Methods?

| Method               | Purpose                           |
| -------------------- | --------------------------------- |
| GET `Create()`       | Opens empty complaint form        |
| POST `Create(model)` | Receives submitted complaint data |

---

## Common Mistake

| Mistake                         | Correction                                               |
| ------------------------------- | -------------------------------------------------------- |
| Using one action for everything | Create focused action methods                            |
| Not separating GET and POST     | Use GET for displaying form and POST for submitting form |
| Action name does not match view | Keep view and action naming clear                        |
| Not passing route parameter     | Use `Details(int id)` for detail pages                   |

---

## Interview Line

**An action method is a public method inside a controller that handles a specific request and returns a response.**

# 5. IActionResult Object

## What

`IActionResult` is a return type used by controller actions.

It represents different kinds of HTTP responses.

Example:

```csharp
public IActionResult Index()
{
    return View();
}
```

Here:

```text
IActionResult means this action can return a view, redirect, JSON, error, or other response.
```

---

## Why

A controller action may need to return different responses.

For example:

```text
Show page
Redirect user
Return JSON
Return NotFound
Return BadRequest
Return Unauthorized
Return file
```

`IActionResult` gives flexibility.

---

## Common IActionResult Responses

| Method               | Result Type                             | Usage                      |
| -------------------- | --------------------------------------- | -------------------------- |
| `View()`             | ViewResult                              | Return Razor view          |
| `RedirectToAction()` | RedirectResult / RedirectToActionResult | Redirect to another action |
| `Json()`             | JsonResult                              | Return JSON data           |
| `NotFound()`         | NotFoundResult                          | Return 404                 |
| `BadRequest()`       | BadRequestResult                        | Return 400                 |
| `Unauthorized()`     | UnauthorizedResult                      | Return 401                 |
| `File()`             | FileResult                              | Return file                |

---

## Smart Society Example

```csharp
public async Task<IActionResult> Details(int id)
{
    var complaint = await _complaintService.GetComplaintByIdAsync(id);

    if (complaint == null)
    {
        return NotFound();
    }

    return View(complaint);
}
```

This action can return:

```text
NotFound if complaint does not exist
View if complaint exists
```

That is why `IActionResult` is useful.

---

## Interview Line

**IActionResult is a flexible return type for controller actions that allows returning different responses such as View, Redirect, JSON, NotFound, or BadRequest.**

---

| Mistake                              | Correction                                         |

# 7. RedirectResult

## What

Redirect result sends the browser to another URL or action.

In MVC, we commonly use:

```csharp
return RedirectToAction(nameof(Index));
```

---

## Why

After successful form submission, we should redirect.

This follows the **Post-Redirect-Get** pattern.

```text
POST form submit
↓
Save/process data
↓
Redirect to GET page
```

This avoids duplicate form submission on browser refresh.

---

## Smart Society Example

After creating complaint:

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

---

## Common Redirect Methods

| Method                                   | Usage                                    |
| ---------------------------------------- | ---------------------------------------- |
| `RedirectToAction("Index")`              | Redirect to action in same controller    |
| `RedirectToAction("Dashboard", "Admin")` | Redirect to action in another controller |
| `Redirect("/Home/Index")`                | Redirect to specific URL                 |
| `LocalRedirect("/Home/Index")`           | Safer local redirect                     |

---

## Common Mistake

| Mistake                                        | Correction                          |
| ---------------------------------------------- | ----------------------------------- |
| Returning View after successful POST           | Redirect after successful POST      |
| Redirecting to wrong action name               | Use `nameof(Index)` where possible  |
| Losing success message after redirect          | Use TempData                        |
| Redirecting to external URL without validation | Be careful with open redirect risks |

---

## Interview Line

**RedirectResult sends the browser to another action or URL. After successful form submission, RedirectToAction is commonly used to follow the Post-Redirect-Get pattern.**

# 9. NotFoundResult

## What

`NotFound()` returns HTTP 404 response.

It means the requested resource does not exist.

Example:

```csharp
return NotFound();
```

---

## Why

If user requests invalid complaint ID, we should not show wrong data or crash.

Example:

```text
/Complaints/Details/9999
```

If complaint 9999 does not exist, return 404.

---

## Smart Society Example

```csharp
public async Task<IActionResult> Details(int id)
{
    var complaint = await _complaintService.GetComplaintByIdAsync(id);

    if (complaint == null)
    {
        return NotFound();
    }

    return View(complaint);
}
```

---

## Common Mistake

| Mistake                                  | Correction                             |
| ---------------------------------------- | -------------------------------------- |
| Returning empty view when data not found | Return NotFound                        |
| Throwing exception for missing record    | Missing record is not always exception |
| Not checking null                        | Always check if record exists          |
| Revealing too much error detail          | Keep error response safe               |

---

## Interview Line

**NotFoundResult returns HTTP 404 when the requested resource does not exist, such as an invalid complaint ID.**

---

# 10. BadRequestResult

## What

`BadRequest()` returns HTTP 400 response.

It means the request is invalid.

Example:

```csharp
return BadRequest();
```

---

## When To Use

Use `BadRequest()` when:

```text
Request data is invalid
Required parameter is missing
Invalid ID is supplied
API input is malformed
Business request cannot be accepted due to invalid input
```

---

## Smart Society Example

```csharp
public IActionResult Details(int id)
{
    if (id <= 0)
    {
        return BadRequest("Invalid complaint id.");
    }

    return View();
}
```

Better future version:

```csharp
public async Task<IActionResult> Details(int id)
{
    if (id <= 0)
    {
        return BadRequest("Invalid complaint id.");
    }

    var complaint = await _complaintService.GetComplaintByIdAsync(id);

    if (complaint == null)
    {
        return NotFound();
    }

    return View(complaint);
}
```

---

## BadRequest Vs NotFound

| Case                                         | Response       |
| -------------------------------------------- | -------------- |
| ID is `0` or negative                        | `BadRequest()` |
| ID is valid format but record does not exist | `NotFound()`   |

Example:

```text
/Complaints/Details/-1 → BadRequest
/Complaints/Details/9999 → NotFound if no record exists
```

---

## Interview Line

**BadRequestResult returns HTTP 400 when the client sends invalid input, while NotFoundResult returns HTTP 404 when the requested resource does not exist.**

## When To Use

Small temporary values
Dropdown helper data in simple demos

## Smart Society Example

```csharp
public IActionResult Create()
{
    ViewBag.PageTitle = "Raise New Complaint";
    return View();

---

## Common Mistake

| Mistake                              | Correction                                 |

# 14. TempData

## What

`TempData` is used to pass data between requests.

```

---

## Why

After successful form submission, we redirect.

Normal `ViewBag` does not survive redirect.

`TempData` can survive one redirect request.

---

## Smart Society Usage

Use TempData for:

```text
Complaint created successfully
Complaint updated successfully
Complaint assigned successfully
Status updated successfully
Invalid operation message
```

---

## Common Mistake

| Mistake                               | Correction                |
| ------------------------------------- | ------------------------- |
| Using ViewBag after redirect          | Use TempData              |
| Storing large data in TempData        | Store only short messages |
| Storing sensitive data in TempData    | Avoid sensitive data      |
| Expecting TempData to persist forever | It is temporary           |

---

## Interview Line

**TempData is used to pass short-lived data between requests, commonly for success or error messages after redirects.**

# 16. ViewModel Awareness

## What

A **ViewModel** is a class created specifically for a view or screen.

It contains only the data required by that view.

---

## Why

Database entity and UI screen are not always the same.

For example, `Complaint` entity may contain:

```text
ComplaintId
CreatedByUserId
AssignedToStaffId
CreatedDate
UpdatedDate
InternalRemarks
Status
```

But complaint creation screen needs only:

```text
Title
Description
Category
Priority
```

So we create:

```text
ComplaintCreateViewModel
```

---

## Example

```csharp
public class ComplaintCreateViewModel
{
    public string Title { get; set; } = string.Empty;

    public string Description { get; set; } = string.Empty;

    public string Category { get; set; } = string.Empty;

    public string Priority { get; set; } = string.Empty;
}
```

---

## Smart Society ViewModels

| ViewModel                   | Purpose                        |
| --------------------------- | ------------------------------ |
| `ComplaintCreateViewModel`  | Complaint creation form        |
| `ComplaintListViewModel`    | Complaint list page            |
| `ComplaintDetailsViewModel` | Complaint details and timeline |
| `DashboardSummaryViewModel` | Dashboard counts               |
| `StatusUpdateViewModel`     | Status update form/API         |

---

## ViewModel Benefits

```text
Prevents overposting
Keeps views clean
Avoids exposing database entity directly
Supports validation
Supports screen-specific data
Improves maintainability
```

---

## Common Mistake

| Mistake                                       | Correction                          |
| --------------------------------------------- | ----------------------------------- |
| Using database entity directly for every form | Use ViewModel for forms             |
| Adding UI-only fields to entity               | Put UI-specific fields in ViewModel |
| Creating one ViewModel for all screens        | Create screen-specific ViewModels   |
| Ignoring overposting risk                     | Use ViewModels for safe binding     |

---

## Interview Line

**A ViewModel is a screen-specific model used to pass only required data between controller and view. It improves security, validation, and maintainability.**

# 17. Smart Society Controller Implementation

Now we create the required controllers.

---

## 17.1 Create ComplaintsController

```csharp
using Microsoft.AspNetCore.Mvc;
using SmartSociety.Web.Interfaces;
using SmartSociety.Web.ViewModels;

namespace SmartSociety.Web.Controllers
{
    public class ComplaintsController : Controller
    {
        private readonly IComplaintService _complaintService;
        private readonly ILogger<ComplaintsController> _logger;

        public ComplaintsController(
            IComplaintService complaintService,
            ILogger<ComplaintsController> logger)
        {
            _complaintService = complaintService;
            _logger = logger;
        }

        public async Task<IActionResult> Index()
        {
            _logger.LogInformation("Complaint list requested");

            var complaints = await _complaintService.GetAllComplaintsAsync();

            return View(complaints);
        }

        [HttpGet]
        public IActionResult Create()
        {
            ViewBag.PageTitle = "Raise New Complaint";

            return View();
        }

        [HttpPost]
        public async Task<IActionResult> Create(ComplaintCreateViewModel model)
        {
            if (!ModelState.IsValid)
            {
                ViewBag.PageTitle = "Raise New Complaint";

                return View(model);
            }

            await _complaintService.CreateComplaintAsync(model);

            TempData["SuccessMessage"] = "Complaint created successfully.";

            return RedirectToAction(nameof(Index));
        }

        public async Task<IActionResult> Details(int id)
        {
            if (id <= 0)
            {
                return BadRequest("Invalid complaint id.");
            }

            var complaint = await _complaintService.GetComplaintByIdAsync(id);

            if (complaint == null)
            {
                return NotFound();
            }

            return View(complaint);
        }
    }
}
```

# 20. Common Mistakes

| Mistake                              | Why It Is Wrong                | Correction                         |
| ------------------------------------ | ------------------------------ | ---------------------------------- |
| Controller contains all logic        | Hard to maintain               | Move business logic to service     |
| Returning View after successful POST | Can duplicate submission       | Use RedirectToAction               |
| Using ViewBag for complex data       | No type safety                 | Use strongly typed model/ViewModel |
| Not checking `id <= 0`               | Invalid request may continue   | Return BadRequest                  |
| Not checking null result             | May cause runtime error        | Return NotFound                    |
| Forgetting service injection         | Controller cannot call service | Inject service through constructor |
| Forgetting view file                 | Runtime view not found error   | Create matching `.cshtml`          |
| View folder name mismatch            | MVC cannot locate view         | Match controller name convention   |
| Using entity for every form          | Overposting risk               | Use ViewModel                      |
| Not using TempData after redirect    | Success message lost           | Use TempData                       |

# 23. Short Answers

1. A controller handles incoming requests and returns responses.
2. A controller coordinates request flow, calls service logic, and returns view, redirect, JSON, or error result.
3. Controller handles HTTP flow; service handles business logic.
4. An action method is a public method inside a controller that handles a specific request.
5. `IActionResult` is a flexible return type for MVC responses.
6. Use `View()` to return a Razor page.
7. Use `RedirectToAction()` after successful POST or when navigating to another action.
8. Use `Json()` when returning data for AJAX or JavaScript.
9. Use `NotFound()` when requested data does not exist.
10. Use `BadRequest()` when input/request is invalid.
11. `ViewBag` passes small dynamic data from controller to view.
12. `ViewData` passes data using dictionary style.
13. `TempData` passes short-lived data across redirects.
14. A strongly typed model is a specific model type passed to a Razor view.
15. A ViewModel is a screen-specific model created for view/form needs.
16. It prevents overposting and contains only fields needed for complaint creation.
17. It makes controller large and hard to maintain; service layer should handle logic.
18. `ComplaintsController`.
19. `DashboardController`.
20. `Details(int id)`.
