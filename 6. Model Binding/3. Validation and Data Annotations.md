# 1. Why Validation Is Important

## What

Validation means checking whether user input is correct, complete, safe, and acceptable before the application processes it.

In simple words:

```text
Validation protects the application from wrong, missing, incomplete, or unsafe data.
```

In the Smart Society Issue Management System, validation ensures that a resident submits a meaningful complaint.

---

## Why

Without validation, users may submit bad data such as:

```text
Empty title
Empty description
Very short description
Invalid category
Invalid priority
Wrong format
Duplicate complaint
Critical complaint without emergency details
```

This creates problems for:

```text
Resident
Admin
Maintenance staff
Reports
Database quality
Workflow accuracy
```

---

## Smart Society Example

Bad complaint submission:

```text
Title: 
Description: fix it
Category: 
Priority: Critical
```

This is not enough for the admin or maintenance staff.

Better complaint submission:

```text
Title: Water leakage in basement
Description: Water is continuously leaking near parking area B2 since morning. It may damage nearby electrical wiring.
Category: Plumbing
Priority: Critical
Emergency Details: Water is close to electrical panel.
```

---

## Real-Life Analogy

Think of a complaint register in a society office.

If a resident writes:

```text
Problem: issue
Location: blank
Urgency: blank
```

The admin cannot act properly.

A good complaint form forces useful information:

```text
What happened?
Where did it happen?
How serious is it?
Who raised it?
Is proof attached?
```

Validation performs this quality check digitally.

---

## Engineering View

```text
User Input
↓
Model Binding
↓
Validation
↓
ModelState
↓
If Valid → Process Request
↓
If Invalid → Return Same Form With Errors
```

## Interview Line

**Validation ensures that user input is complete, correct, safe, and meaningful before the application processes it or stores it in the database.**

# 2. Data Annotations And Validations Overview

## What

**Data Annotations** are attributes added to model or ViewModel properties to define validation rules.

They are available in:

```csharp
using System.ComponentModel.DataAnnotations;
```

Example:

```csharp
[Required]
[StringLength(100)]
public string Title { get; set; } = string.Empty;
```

---

## Why

Data Annotations allow us to define validation rules close to the data model or ViewModel.

They help with:

```text
Required field checks
Length checks
Range checks
Display names
Format checks
Error messages
Client-side validation support
Server-side validation support
```

---

## Smart Society ViewModel With Validation

```csharp
using System.ComponentModel.DataAnnotations;

namespace SmartSociety.Web.ViewModels
{
    public class ComplaintCreateViewModel
    {
        [Required(ErrorMessage = "Complaint title is required.")]
        [StringLength(100, ErrorMessage = "Complaint title cannot exceed 100 characters.")]
        [Display(Name = "Complaint Title")]
        public string Title { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint description is required.")]
        [StringLength(1000, MinimumLength = 20, ErrorMessage = "Description must be between 20 and 1000 characters.")]
        [Display(Name = "Complaint Description")]
        public string Description { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint category is required.")]
        [Display(Name = "Category")]
        public string Category { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint priority is required.")]
        [Display(Name = "Priority")]
        public string Priority { get; set; } = string.Empty;
    }
}
```

---

## Smart Society Mapping

| Validation Need | Data Annotation |
|---|---|
| Title required | `[Required]` |
| Title max length | `[StringLength]` |
| Description required | `[Required]` |
| Description minimum length | `[StringLength(MinimumLength = ...)]` |
| Category required | `[Required]` |
| Priority required | `[Required]` |
| Friendly label | `[Display]` |
| Format check | `[RegularExpression]` where needed |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Keeping validation only in UI | Always validate on server |
| Not giving proper error messages | Use clear user-friendly messages |
| Adding validation on entity blindly | Prefer ViewModel validation for form-specific rules |
| Assuming Data Annotations cover every business rule | Use custom validation or service-level rules where needed |

---

## Interview Line

**Data Annotations are validation attributes applied to model or ViewModel properties to define rules such as required fields, length limits, range checks, display names, and format validation.**

# 3. Required

## What

`[Required]` ensures that a value must be provided.

Example:

```csharp
[Required(ErrorMessage = "Complaint title is required.")]
public string Title { get; set; } = string.Empty;
```

---

## Why

Some fields are mandatory.

In Smart Society complaint creation, these fields must be required:

```text
Title
Description
Category
Priority
```

Without them, the complaint cannot be processed properly.

---

## Smart Society Example

```csharp
[Required(ErrorMessage = "Complaint title is required.")]
[Display(Name = "Complaint Title")]
public string Title { get; set; } = string.Empty;
```

---

## User Experience

If the resident leaves the title empty, the form should show:

```text
Complaint title is required.
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Not marking important fields as required | Add `[Required]` |
| Using technical error messages | Write user-friendly messages |
| Depending only on HTML `required` | Server-side `[Required]` is still needed |
| Forgetting validation message in view | Add `asp-validation-for` |

---

## Interview Line

**Required validation ensures that mandatory fields are provided before the form is processed.**

# 4. StringLength

## What

`[StringLength]` controls the maximum length and optionally the minimum length of a string.

Example:

```csharp
[StringLength(100, ErrorMessage = "Complaint title cannot exceed 100 characters.")]
public string Title { get; set; } = string.Empty;
```

With minimum length:

```csharp
[StringLength(1000, MinimumLength = 20, ErrorMessage = "Description must be between 20 and 1000 characters.")]
public string Description { get; set; } = string.Empty;
```

---

## Why

Length validation prevents:

```text
Very short meaningless input
Very long database-unfriendly input
Poor-quality complaint descriptions
Unexpected UI layout issues
```

---

## Smart Society Rules

| Field | Rule |
|---|---|
| Title | Maximum 100 characters |
| Description | Minimum 20 and maximum 1000 characters |
| Category | Maximum 50 characters |
| Priority | Maximum 20 characters |

---

## Example

```csharp
[Required(ErrorMessage = "Complaint description is required.")]
[StringLength(1000, MinimumLength = 20, ErrorMessage = "Description must be between 20 and 1000 characters.")]
[Display(Name = "Complaint Description")]
public string Description { get; set; } = string.Empty;
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Allowing unlimited text length | Add maximum length |
| Allowing one-word descriptions | Add minimum length |
| Confusing StringLength with Required | Use both where needed |
| Setting unrealistic length limits | Choose practical business limits |

---

## Interview Line

**StringLength validates the allowed length of a string field and can enforce both maximum and minimum length rules.**

# 5. Range

## What

`[Range]` validates that a numeric value falls within a specific range.

Example:

```csharp
[Range(1, 5, ErrorMessage = "Rating must be between 1 and 5.")]
public int Rating { get; set; }
```

---

## Why

Range is useful for numeric values.

In the current complaint creation form, Priority is a string such as:

```text
Low
Medium
High
Critical
```

So `[Range]` is not required for Priority in this version.

But it may be useful later for:

```text
Complaint rating
Satisfaction score
Escalation level
Expected resolution days
Dashboard filter range
```

---

## Smart Society Example

Later, after complaint resolution, resident may give feedback:

```csharp
[Range(1, 5, ErrorMessage = "Satisfaction rating must be between 1 and 5.")]
[Display(Name = "Satisfaction Rating")]
public int SatisfactionRating { get; set; }
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using Range for string dropdowns | Use Required or enum-based validation |
| Not validating numeric input | Use Range where numeric limits exist |
| Using unrealistic numeric limits | Match business rules |
| Thinking Range works for all field types | It is mainly for numeric/date-like validations |

---

## Interview Line

**Range validation ensures that a numeric value falls within a defined minimum and maximum range.**

# 7. RegularExpression Awareness

## What

`[RegularExpression]` validates input against a pattern.

Example:

```csharp
[RegularExpression("^[a-zA-Z0-9 ]+$", ErrorMessage = "Only letters, numbers, and spaces are allowed.")]
public string Title { get; set; } = string.Empty;
```

---

## Why

Regular expressions are useful when a field must follow a format.

Examples:

```text
Phone number
Flat number
Ticket code
Reference number
Vehicle number
Simple title format
```

---

## Smart Society Possible Use Cases

| Field | Regex Use |
|---|---|
| Flat number | Allow patterns like A-101 |
| Vehicle number | Validate vehicle format |
| Phone number | Validate digits |
| Complaint reference | Validate ticket code |
| Title | Restrict unsafe characters if needed |

---

## Example: Flat Number

```csharp
[RegularExpression(@"^[A-Z]-\d{3}$", ErrorMessage = "Flat number must be in format A-101.")]
[Display(Name = "Flat Number")]
public string FlatNumber { get; set; } = string.Empty;
```

---

## Caution

Regex can become hard to read and maintain.

Use it only when format validation is truly needed.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using complex regex everywhere | Keep validation simple where possible |
| Using regex for business logic | Business rules may need custom validation |
| Not testing regex | Test with valid and invalid values |
| Giving unclear regex error message | Explain expected format clearly |

---

## Interview Line

**RegularExpression validation checks whether input matches a defined pattern, useful for fields like flat number, phone number, vehicle number, or reference code.**

# 8. Server-Side Validation

## What

Server-side validation runs on the server after form submission.

It is mandatory because client-side validation can be bypassed.

---

## Why

Users can bypass browser validation by:

```text
Disabling JavaScript
Using developer tools
Sending manual HTTP requests
Using Postman
Manipulating hidden fields
```

So server-side validation is essential.

---

## Smart Society Controller Example

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await _complaintService.CreateComplaintAsync(model);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

---

## Flow

```text
POST complaint form
↓
Model binding fills ViewModel
↓
Data Annotation validation runs
↓
ModelState is updated
↓
If invalid, return same form
↓
If valid, process complaint
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Relying only on JavaScript validation | Always validate on server |
| Not checking ModelState | Check before service call |
| Redirecting when invalid | Return View(model) |
| Losing user input on validation error | Return same model to view |

---

## Interview Line

**Server-side validation runs on the server and must always be used because client-side validation can be bypassed.**

---

| Mistake | Correction |

---

## Interview Line

**Client-side validation runs in the browser and improves user experience, but server-side validation is still required for security and correctness.**

# 12. Custom Server-Side Validation

## What

Custom server-side validation is used when built-in attributes are not enough.

Example business rule:

```text
Complaint title cannot contain only repeated characters.
```

or:

```text
Emergency complaints must include useful emergency details.
```

---

## Why

Real business rules often go beyond Required and StringLength.

Smart Society examples:

```text
Critical complaint must include emergency details
Description must not be too generic
Complaint category must be valid
Duplicate complaints should be checked
Resolution proof required for resolved status
```

---

## Custom Validation Attribute Example

Create folder:

```text
Validations
```

Create file:

```text
MeaningfulDescriptionAttribute.cs
```

Code:

```csharp
using System.ComponentModel.DataAnnotations;

namespace SmartSociety.Web.Validations
{
    public class MeaningfulDescriptionAttribute : ValidationAttribute
    {
        private readonly int _minimumWords;

        public MeaningfulDescriptionAttribute(int minimumWords)
        {
            _minimumWords = minimumWords;
        }

        protected override ValidationResult? IsValid(
            object? value,
            ValidationContext validationContext)
        {
            var description = value as string;

            if (string.IsNullOrWhiteSpace(description))
            {
                return ValidationResult.Success;
            }

            var wordCount = description
                .Split(' ', StringSplitOptions.RemoveEmptyEntries)
                .Length;

            if (wordCount < _minimumWords)
            {
                return new ValidationResult(
                    $"Description must contain at least {_minimumWords} meaningful words.");
            }

            return ValidationResult.Success;
        }
    }
}
```

Use it:

```csharp
[MeaningfulDescription(5)]
public string Description { get; set; } = string.Empty;
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Using custom validation for simple Required checks | Use built-in attributes |
| Putting database-heavy logic in validation attribute | Prefer service/remote validation for database checks |
| Not returning clear error message | Return user-friendly message |
| Making validation too strict | Match real business need |

---

## Interview Line

**Custom server-side validation is used when built-in Data Annotations cannot express a specific business rule.**

# 13. Model-Level Validation Using IValidatableObject

## What

`IValidatableObject` is used when validation depends on multiple properties of the model.

Example:

```text
If Priority is Critical, EmergencyDetails must be provided.
```

This rule depends on both:

```text
Priority
EmergencyDetails
```

---

## Why

Property-level attributes validate one property at a time.

Model-level validation checks the relationship between multiple properties.

---

## Smart Society Updated ViewModel

```csharp
using System.ComponentModel.DataAnnotations;

namespace SmartSociety.Web.ViewModels
{
    public class ComplaintCreateViewModel : IValidatableObject
    {
        [Required(ErrorMessage = "Complaint title is required.")]
        [StringLength(100, ErrorMessage = "Complaint title cannot exceed 100 characters.")]
        [Display(Name = "Complaint Title")]
        public string Title { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint description is required.")]
        [StringLength(1000, MinimumLength = 20, ErrorMessage = "Description must be between 20 and 1000 characters.")]
        [Display(Name = "Complaint Description")]
        public string Description { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint category is required.")]
        [Display(Name = "Category")]
        public string Category { get; set; } = string.Empty;

        [Required(ErrorMessage = "Complaint priority is required.")]
        [Display(Name = "Priority")]
        public string Priority { get; set; } = string.Empty;

        [Display(Name = "Emergency Details")]
        public string? EmergencyDetails { get; set; }

        public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
        {
            if (Priority == "Critical" && string.IsNullOrWhiteSpace(EmergencyDetails))
            {
                yield return new ValidationResult(
                    "Emergency details are required for critical complaints.",
                    new[] { nameof(EmergencyDetails) });
            }
        }
    }
}
```

---

## Smart Society Rule

```text
If Priority = Critical
EmergencyDetails must not be empty
```

This is model-level validation because it depends on two fields.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Trying to handle cross-field rules with Required only | Use IValidatableObject |
| Not mapping error to field name | Return property name in ValidationResult |
| Putting too many business rules in ViewModel | Keep complex workflow rules in service |
| Forgetting server-side check | IValidatableObject runs during server validation |

---

## Interview Line

**IValidatableObject supports model-level validation where rules depend on multiple properties, such as requiring emergency details when complaint priority is Critical.**

# 15. Remote Validation

## What

Remote validation checks a value by calling the server from the browser before the form is submitted.

It is useful when validation needs server-side data.

Example:

```text
Check whether a similar complaint already exists.
```

---

## Why

Some validations need database or service checks.

Examples:

```text
Duplicate complaint title for same flat
Duplicate vehicle number
Existing email
Existing username
Repeated complaint for same issue
```

---

## Smart Society Concept

When resident enters complaint title and category, the system can check:

```text
Is there already an open complaint for the same resident, same category, and similar title?
```

This can be implemented as remote validation conceptually.

---

## Remote Validation Attribute Example

```csharp
[Remote(
    action: "IsDuplicateComplaint",
    controller: "Complaints",
    ErrorMessage = "A similar open complaint already exists.")]
public string Title { get; set; } = string.Empty;
```

---

## Controller Action Concept

```csharp
[AcceptVerbs("GET", "POST")]
public IActionResult IsDuplicateComplaint(string title)
{
    var isDuplicate = false;

    // Later this will call service/database.
    // isDuplicate = _complaintService.ExistsOpenComplaint(title);

    if (isDuplicate)
    {
        return Json(false);
    }

    return Json(true);
}
```

---

## Important Note

Remote validation requires client-side validation scripts to be active.

It should not replace final server-side validation during form submission.

A duplicate check must still be repeated in service/database logic before saving.

---

## Smart Society Mapping

| Remote Validation Scenario | Purpose |
|---|---|
| Duplicate complaint title | Avoid repeated open complaints |
| Flat number check | Ensure flat exists |
| Vehicle number check | Avoid duplicate vehicle entry |
| Staff code check | Validate staff identity |
| Email check | Avoid duplicate registration |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Relying only on remote validation | Recheck on final POST |
| Calling database too frequently | Optimize remote checks |
| Returning wrong JSON format | Return `true` for valid, `false` or message for invalid |
| Not enabling validation scripts | Include `_ValidationScriptsPartial` |
| Checking duplicate only by title | Use title + resident + category + status where possible |

---

## Interview Line

**Remote validation performs server-side checks from the browser, useful for database-backed validation such as duplicate complaint detection, but final validation must still happen on form submission.**

```text
Resident opens complaint form
↓
View displays validation-enabled fields
↓
Resident submits form
↓
Client-side validation may run in browser
↓
POST request reaches server
↓
Model binding fills ComplaintCreateViewModel
↓
Data Annotation validation runs
↓
IValidatableObject model-level validation runs
↓
```

# 18. Common Mistakes

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Relying only on client-side validation | Can be bypassed | Always check ModelState on server |
| Forgetting validation messages in view | User cannot see field errors | Add `asp-validation-for` |
| Forgetting validation summary | Model-level errors may not be visible | Add `asp-validation-summary` |
| Not including validation scripts | Client-side validation may not work | Add `_ValidationScriptsPartial` |
| Putting every rule in Data Annotations | Complex rules need custom/model/service validation | Use correct validation layer |
| No model-level validation for Critical priority | Emergency info may be missing | Use `IValidatableObject` |
| Remote validation trusted as final validation | Race conditions possible | Recheck on final POST/service |
| Technical error messages | Poor UX | Use business-friendly messages |
| Validating entity instead of ViewModel | Form validation becomes unclear | Validate ViewModel |
| Ignoring duplicate complaint scenario | Duplicate workflow issues | Use remote/service-level duplicate check |

# 21. Short Answers

1. Validation checks whether user input is correct, complete, safe, and meaningful.
2. It prevents bad data, workflow problems, database issues, and poor user experience.
3. Data Annotations are attributes used to define validation rules on model or ViewModel properties.
4. Required ensures that a value must be provided.
5. StringLength controls minimum and maximum allowed text length.
6. Range ensures a numeric value falls within a defined range.
7. Display provides user-friendly labels.
8. RegularExpression validates input against a pattern.
9. Server-side validation runs on the server after form submission.
10. It is mandatory because client-side validation can be bypassed.
11. Client-side validation runs in the browser before form submission.
12. Validation Summary displays form-level or model-level errors.
13. Validation Message displays field-specific errors.
14. Custom server-side validation handles business rules not covered by built-in attributes.
15. Use IValidatableObject when validation depends on multiple properties.
16. If Priority is Critical, EmergencyDetails must be provided.
17. It adds browser-side support for custom validation rules.
18. Remote validation calls the server from the browser to validate a value.
19. Remote validation can be bypassed or become stale, so final server-side validation is still required.
20. Return the same view with the submitted model so the user can fix errors.
