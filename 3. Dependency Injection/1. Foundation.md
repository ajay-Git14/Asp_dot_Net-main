# 1. What Is A Dependency?

## What

A **dependency** is anything a class needs in order to complete its work.

In simple words:

```text
If Class A needs Class B to work, then Class B is a dependency of Class A.
```

## Example

Suppose `ComplaintController` needs complaint-related business logic.

That logic may be inside:

```text
ComplaintService
```

So, `ComplaintService` becomes a dependency of `ComplaintController`.

---

## Real-Life Analogy

Think of a society admin office.

The admin cannot solve every complaint alone.

Admin depends on:

```text
Electrician
Plumber
Lift technician
Security guard
Housekeeping staff
```

These people are dependencies required to complete society operations.

Similarly, in code:

```text
ComplaintController depends on ComplaintService
ComplaintService may depend on ApplicationDbContext
ComplaintService may depend on ILogger
ComplaintService may depend on configuration
```

---

## Smart Society Mapping

In our Smart Society project:

| Class                 | Dependency Needed           | Why                                  |
| --------------------- | --------------------------- | ------------------------------------ |
| `ComplaintController` | `IComplaintService`         | To create, list, and view complaints |
| `ComplaintService`    | `ApplicationDbContext`      | To save and retrieve complaints      |
| `ComplaintService`    | `ILogger<ComplaintService>` | To log complaint operations          |
| `ComplaintService`    | `IConfiguration`            | To read settings if needed           |

---

## Bad Direct Dependency Example

```csharp
public class ComplaintController : Controller
{
    private readonly ComplaintService _complaintService;

    public ComplaintController()
    {
        _complaintService = new ComplaintService();
    }
}
```

## Why This Is Bad

This creates tight coupling.

Problems:

```text
Controller is directly creating the service
Service implementation cannot be changed easily
Testing becomes difficult
Controller controls object creation
Application becomes harder to maintain
```

---

## Interview Line

**A dependency is an object or service that another class needs to complete its responsibility. In the Smart Society project, ComplaintController depends on a complaint service to perform complaint-related operations.**

---

# 2. What Is Dependency Injection?

## What

**Dependency Injection** is a design technique where required objects are provided to a class from outside, instead of the class creating them by itself.

Simple meaning:

```text
Do not create dependency inside the class.
Ask for it through constructor.
Let ASP.NET Core provide it.
```

---

## Why

Dependency Injection helps us build applications that are:

```text
Loosely coupled
Easier to test
Easier to maintain
Easier to extend
Cleaner in architecture
Better for enterprise applications
```

---

## Without Dependency Injection

```csharp
public class ComplaintController : Controller
{
    private readonly ComplaintService _complaintService;

    public ComplaintController()
    {
        _complaintService = new ComplaintService();
    }
}
```

Problem:

```text
ComplaintController is responsible for creating ComplaintService.
```

---

## With Dependency Injection

```csharp
public class ComplaintController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }
}
```

Better:

```text
ComplaintController only asks for IComplaintService.
ASP.NET Core provides the actual ComplaintService.
```

---

## Real-Life Analogy

A society admin does not manufacture tools.

The admin says:

```text
I need a plumber for leakage complaint.
```

The society system provides the plumber.

Similarly:

```text
ComplaintController says: I need IComplaintService.
ASP.NET Core provides ComplaintService.
```

---

## Smart Society Mapping

For our project:

```text
ComplaintController should not create ComplaintService manually.
ComplaintController should receive IComplaintService through constructor.
ASP.NET Core should inject ComplaintService automatically.
```

---

## Interview Line

**Dependency Injection means providing required dependencies to a class from outside, usually through the constructor, instead of creating them inside the class. ASP.NET Core has built-in support for Dependency Injection.**

# 3. Inversion Of Control

## What

**Inversion of Control**, or **IoC**, means the control of object creation is moved away from the class and given to an external container or framework.

In simple words:

```text
The class does not control dependency creation.
The framework controls dependency creation.
```

---

## Without IoC

```text
ComplaintController creates ComplaintService.
```

## With IoC

```text
ASP.NET Core creates ComplaintService and gives it to ComplaintController.
```

---

## Why

IoC improves flexibility.

If tomorrow we want to replace:

```text
ComplaintService
```

with:

```text
CachedComplaintService
```

or:

```text
MockComplaintService
```

we can change registration without rewriting controller logic.

---

## Engineering View

```text
Without IoC

ComplaintController
      ↓ creates
ComplaintService


With IoC

ASP.NET Core DI Container
      ↓ provides
ComplaintService
      ↓ injected into
ComplaintController
```

---

## Smart Society Example

Today:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

Future:

```csharp
builder.Services.AddScoped<IComplaintService, CachedComplaintService>();
```

Controller remains the same:

```csharp
public ComplaintController(IComplaintService complaintService)
{
    _complaintService = complaintService;
}
```

---

## Common Mistake

| Mistake                                       | Correction                                            |
| --------------------------------------------- | ----------------------------------------------------- |
| Thinking IoC and DI are exactly same          | DI is one way to implement IoC                        |
| Thinking IoC means no object creation happens | Objects are created, but framework controls creation  |
| Thinking controller creates services          | ASP.NET Core DI container creates registered services |

---

## Interview Line

**Inversion of Control means the responsibility of creating and managing dependencies is transferred from the class to the framework or DI container. Dependency Injection is a common way to implement IoC.**

---

# 4. Tight Coupling Vs Loose Coupling

## What

Coupling means how strongly one class depends on another class.

There are two common types:

```text
Tight Coupling
Loose Coupling
```

---

# Tight Coupling

## What

Tight coupling means one class directly depends on a concrete class.

Example:

```csharp
public class ComplaintController : Controller
{
    private readonly ComplaintService _complaintService;

    public ComplaintController()
    {
        _complaintService = new ComplaintService();
    }
}
```

## Problem

`ComplaintController` is tightly connected to `ComplaintService`.

If `ComplaintService` changes, controller may also need changes.

---

# Loose Coupling

## What

Loose coupling means one class depends on an abstraction, not a concrete implementation.

Example:

```csharp
public class ComplaintController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }
}
```

Now controller depends on:

```text
IComplaintService
```

not directly on:

```text
ComplaintService
```

---

## Why Loose Coupling Is Better

Loose coupling helps with:

```text
Testing
Maintenance
Changing implementation
Mocking dependencies
Clean architecture
Team development
```

---

## Smart Society Mapping

Bad design:

```text
ComplaintController directly creates ComplaintService.
```

Better design:

```text
ComplaintController depends on IComplaintService.
ComplaintService implements IComplaintService.
ASP.NET Core injects ComplaintService.
```

---

## Interview Line

**Tight coupling means a class directly depends on a concrete implementation, while loose coupling means a class depends on an abstraction such as an interface. Dependency Injection helps achieve loose coupling.**

---

# 5. Constructor Injection

## What

**Constructor Injection** means dependencies are provided through the constructor of a class.

It is the most common and recommended DI approach in ASP.NET Core.

---

## Example

```csharp
public class ComplaintController : Controller
{
    private readonly IComplaintService _complaintService;

    public ComplaintController(IComplaintService complaintService)
    {
        _complaintService = complaintService;
    }
}
```

Here:

```text
IComplaintService is injected through constructor.
```

---

## Why

Constructor Injection is useful because:

```text
Required dependencies are clearly visible
Class cannot be created without required dependency
Code is easier to test
Code is easier to maintain
Dependency usage is explicit
```

---

## Smart Society Mapping

`ComplaintController` needs complaint operations.

So it asks for:

```text
IComplaintService
```

through constructor.

Later, `ComplaintService` may need:

```text
ApplicationDbContext
ILogger<ComplaintService>
```

So `ComplaintService` will also use constructor injection.

Example:

```csharp
public class ComplaintService : IComplaintService
{
    private readonly ILogger<ComplaintService> _logger;

    public ComplaintService(ILogger<ComplaintService> logger)
    {
        _logger = logger;
    }
}
```

---

## Common Mistake

| Mistake                                            | Correction                                      |
| -------------------------------------------------- | ----------------------------------------------- |
| Creating dependency using `new` inside constructor | Inject dependency through constructor           |
| Adding too many dependencies to controller         | Move logic to service or split responsibilities |
| Keeping injected dependency public                 | Use private readonly fields                     |
| Injecting concrete class everywhere                | Prefer interface where useful                   |

---

## Interview Line

**Constructor Injection is a DI technique where required dependencies are supplied through the class constructor. It makes dependencies explicit and supports clean, testable design.**

---

# 6. Interface-Based Design

## What

An **interface** defines what a service can do, without defining how it does it.

In simple words:

```text
Interface = contract
Class = implementation
```

---

## Example Interface

```csharp
public interface IComplaintService
{
    Task<List<Complaint>> GetAllComplaintsAsync();

    Task<Complaint?> GetComplaintByIdAsync(int id);

    Task CreateComplaintAsync(ComplaintCreateViewModel model);
}
```

This interface says:

```text
Any complaint service must provide these methods.
```

---

## Example Implementation

```csharp
public class ComplaintService : IComplaintService
{
    public Task<List<Complaint>> GetAllComplaintsAsync()
    {
        return Task.FromResult(new List<Complaint>());
    }

    public Task<Complaint?> GetComplaintByIdAsync(int id)
    {
        return Task.FromResult<Complaint?>(null);
    }

    public Task CreateComplaintAsync(ComplaintCreateViewModel model)
    {
        return Task.CompletedTask;
    }
}
```

---

## Why Interface-Based Design Is Useful

It helps with:

```text
Loose coupling
Testing with mock services
Changing implementation
Following clean architecture
Separating contract from implementation
```

---

## Smart Society Mapping

In our project:

```text
IComplaintService = contract
ComplaintService = actual implementation
ComplaintController = depends on contract
```

Flow:

```text
ComplaintController
      ↓ depends on
IComplaintService
      ↓ implemented by
ComplaintService
```

---

## Common Mistake

| Mistake                                         | Correction                                |
| ----------------------------------------------- | ----------------------------------------- |
| Creating interface but not using it             | Inject interface into controller          |
| Creating interface for every tiny class blindly | Use interface where abstraction is useful |
| Putting implementation logic inside interface   | Interface only defines method signatures  |
| Naming interface randomly                       | Use clear name like `IComplaintService`   |

---

## Interview Line

**Interface-based design allows a controller to depend on a contract instead of a concrete implementation, making the application loosely coupled, testable, and easier to maintain.**

# 7. IServiceCollection

## What

`IServiceCollection` is used to register services in ASP.NET Core.

It is available through:

```csharp
builder.Services
```

Example:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

---

## Why

ASP.NET Core needs to know:

```text
When someone asks for IComplaintService,
which class should be provided?
```

This registration tells ASP.NET Core:

```text
Use ComplaintService whenever IComplaintService is requested.
```

---

## Program.cs Example

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddScoped<IComplaintService, ComplaintService>();

var app = builder.Build();
```

---

## Smart Society Mapping

We will register:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

This allows:

```text
ComplaintController to receive IComplaintService automatically.
```

---

## Common Mistake

| Mistake                                                        | Correction                                   |
| -------------------------------------------------------------- | -------------------------------------------- |
| Forgetting to register service                                 | Register service in Program.cs               |
| Registering after `builder.Build()`                            | Register before `builder.Build()`            |
| Registering implementation but injecting interface incorrectly | Make sure interface and implementation match |
| Registering wrong lifetime                                     | Choose lifetime carefully                    |

---

## Interview Line

**IServiceCollection is the service registration collection in ASP.NET Core. We use it in Program.cs to register application services for dependency injection.**

# 8. IServiceProvider

## What

`IServiceProvider` is the component that resolves services at runtime.

In simple words:

```text
IServiceCollection registers services.
IServiceProvider provides services.
```

---

## Flow

```text
Register service in IServiceCollection
↓
ASP.NET Core builds IServiceProvider
↓
Controller asks for dependency
↓
IServiceProvider creates/provides required object
```

---

## Example Flow

Registration:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

Controller:

```csharp
public ComplaintController(IComplaintService complaintService)
{
    _complaintService = complaintService;
}
```

Runtime:

```text
ASP.NET Core sees ComplaintController needs IComplaintService
IServiceProvider checks registration
It creates ComplaintService
It injects ComplaintService into ComplaintController
```

---

## Important Note

In normal ASP.NET Core application code, we usually do not manually call `IServiceProvider`.

We usually rely on constructor injection.

Avoid this style unless necessary:

```csharp
var service = serviceProvider.GetService<IComplaintService>();
```

Better:

```csharp
public ComplaintController(IComplaintService complaintService)
{
    _complaintService = complaintService;
}
```

---

## Interview Line

**IServiceProvider is the runtime service resolver created by ASP.NET Core. It provides registered dependencies to classes that request them, usually through constructor injection.**

# 9. Service Registration In Program.cs

## What

Service registration means telling ASP.NET Core which implementation should be used for an interface or service.

## Syntax

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

Meaning:

```text
When IComplaintService is requested, provide ComplaintService.
```

---

## Full Example

```csharp
using SmartSociety.Web.Interfaces;
using SmartSociety.Web.Services;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

builder.Services.AddScoped<IComplaintService, ComplaintService>();

var app = builder.Build();

app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseAuthorization();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

---

## Smart Society Mapping

We will create:

```text
Interfaces/IComplaintService.cs
Services/ComplaintService.cs
```

Then register:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

Then inject into:

```text
ComplaintsController
```

---

## Common Mistake

| Mistake                                           | Correction                            |
| ------------------------------------------------- | ------------------------------------- |
| Missing namespace imports                         | Add correct `using` statements        |
| Registering wrong implementation                  | Register interface with correct class |
| Forgetting service registration                   | Add registration in Program.cs        |
| Creating service manually even after registration | Use constructor injection             |

---

## Interview Line

**Service registration in Program.cs tells ASP.NET Core how to map an abstraction to an implementation, such as mapping IComplaintService to ComplaintService.**

# 10. AddTransient, AddScoped, AddSingleton

## What

These methods define the lifetime of a service.

Service lifetime means:

```text
How long the object should live
How often a new object should be created
```

ASP.NET Core provides three common lifetimes:

```text
AddTransient
AddScoped
AddSingleton
```

---

# AddTransient

## What

`AddTransient` creates a new instance every time the service is requested.

```csharp
builder.Services.AddTransient<IComplaintService, ComplaintService>();
```

## When To Use

Use Transient for:

```text
Lightweight stateless services
Services that do not store request-specific data
Services where new instance every time is acceptable
```

## Caution

Too many transient objects can create unnecessary overhead if service is heavy.

---

# AddScoped

## What

`AddScoped` creates one instance per HTTP request.

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

## When To Use

Use Scoped for:

```text
Services that work within one web request
Business services
Services using DbContext
Request-level operations
```

## Smart Society Recommendation

For the Smart Society project, use:

```csharp
builder.Services.AddScoped<IComplaintService, ComplaintService>();
```

because complaint operations are request-based.

---

# AddSingleton

## What

`AddSingleton` creates one instance for the entire application lifetime.

```csharp
builder.Services.AddSingleton<IAppClock, SystemClock>();
```

## When To Use

Use Singleton for:

```text
Application-wide stateless services
Configuration-like services
Shared utility services that are thread-safe
```

## Caution

Do not store user-specific or request-specific data in Singleton.

Do not inject Scoped services like DbContext into Singleton services.

---

## Lifetime Comparison

| Lifetime  | Object Created             | Best For                                         | Smart Society Example              |
| --------- | -------------------------- | ------------------------------------------------ | ---------------------------------- |
| Transient | Every time requested       | Lightweight stateless services                   | Simple formatter                   |
| Scoped    | Once per HTTP request      | Business services and DbContext-related services | ComplaintService                   |
| Singleton | Once for whole application | App-wide thread-safe services                    | App settings helper, clock service |

---

## Common Mistake

| Mistake                                            | Correction                                      |
| -------------------------------------------------- | ----------------------------------------------- |
| Registering DbContext-related service as Singleton | Use Scoped                                      |
| Using Singleton for current user data              | Use Scoped/request context                      |
| Using Transient for heavy services unnecessarily   | Prefer Scoped when request-based                |
| Not understanding object lifetime                  | Choose lifetime based on service responsibility |

---

## Interview Line

**Transient creates a new instance every time, Scoped creates one instance per HTTP request, and Singleton creates one instance for the entire application lifetime. In web applications, business services that use DbContext are usually registered as Scoped.**

---

# 11. Service Lifetime Selection

## How To Choose

Use this thinking:

```text
Does service need fresh instance every time? → Transient
Does service work within one user request? → Scoped
Does service safely live for whole application? → Singleton
```

---

## Smart Society Examples

| Service                  | Suggested Lifetime | Reason                             |
| ------------------------ | ------------------ | ---------------------------------- |
| `IComplaintService`      | Scoped             | Works with request and database    |
| `ApplicationDbContext`   | Scoped             | EF Core DbContext is request-based |
| `ILogger<T>`             | Built-in           | Framework handles it               |
| `IConfiguration`         | Built-in           | Framework handles it               |
| `IEmailTemplateRenderer` | Transient/Scoped   | Depends on implementation          |
| `IApplicationClock`      | Singleton          | If stateless and thread-safe       |

---

## Decision Rule

For most application services in ASP.NET Core MVC:

```text
Start with Scoped unless there is a clear reason to choose another lifetime.
```

This is especially true when the service uses EF Core `DbContext`.

            return Task.FromResult(complaints);
        }

        public Task<Complaint?> GetComplaintByIdAsync(int id)
        {
            _logger.LogInformation("Fetching complaint details for ComplaintId: {ComplaintId}", id);

            Complaint? complaint = null;

            return Task.FromResult(complaint);
        }

        public Task CreateComplaintAsync(ComplaintCreateViewModel model)
        {
            _logger.LogInformation("Creating complaint with title: {Title}", model.Title);

            return Task.CompletedTask;
        }
    }
}

## Step 8: Inject Service In ComplaintsController

```csharp
using Microsoft.AspNetCore.Mvc;
using SmartSociety.Web.Interfaces;

namespace SmartSociety.Web.Controllers
{
    public class ComplaintsController : Controller
    {
        private readonly IComplaintService _complaintService;

        public ComplaintsController(IComplaintService complaintService)
        {
            _complaintService = complaintService;
        }

        public async Task<IActionResult> Index()
        {
            var complaints = await _complaintService.GetAllComplaintsAsync();

            return View(complaints);
        }

        public async Task<IActionResult> Details(int id)
        {
            var complaint = await _complaintService.GetComplaintByIdAsync(id);

            if (complaint == null)
            {
                return NotFound();
            }

            return View(complaint);
        }

        [HttpGet]
        public IActionResult Create()
        {
            return View();
        }
    }
}
```

# 14. Common Dependency Injection Mistakes

| Mistake                                            | Why It Is Wrong                          | Correction                        |
| -------------------------------------------------- | ---------------------------------------- | --------------------------------- |
| Creating service using `new` inside controller     | Causes tight coupling                    | Use constructor injection         |
| Forgetting service registration                    | Runtime error occurs                     | Register service in Program.cs    |
| Registering after `builder.Build()`                | Too late for service registration        | Register before `builder.Build()` |
| Registering DbContext-related service as Singleton | Can cause lifetime/threading issues      | Use Scoped                        |
| Injecting too many services into controller        | Controller has too many responsibilities | Move logic into focused services  |
| Depending on concrete classes everywhere           | Harder to test/change                    | Depend on interfaces where useful |
| Storing user data in Singleton service             | Shared across users dangerously          | Use Scoped/request-based services |
| Not using private readonly field                   | Dependency can be accidentally changed   | Use `private readonly`            |
| Interface and implementation mismatch              | DI cannot resolve correctly              | Ensure class implements interface |

while attempting to activate 'ComplaintsController'.

## Meaning

ASP.NET Core tried to create `ComplaintsController`, but it did not know how to provide `IComplaintService`.

Register service in `Program.cs`:

builder.Services.AddScoped<IComplaintService, ComplaintService>();

# 18. Short Answers

1. A dependency is an object or service that a class needs to complete its responsibility.
2. Dependency Injection means providing dependencies from outside instead of creating them inside the class.
3. Inversion of Control means the framework controls object creation instead of the class.
4. Tight coupling means a class directly depends on a concrete implementation.
5. Loose coupling means a class depends on an abstraction such as an interface.
6. Loose coupling improves testing, maintainability, flexibility, and clean architecture.
7. Constructor injection provides dependencies through a class constructor.
8. An interface is a contract that defines what methods a service must provide.
9. It keeps the controller loosely coupled and allows the implementation to change without changing controller code.
10. `IServiceCollection` is used to register services in ASP.NET Core.
11. `IServiceProvider` resolves and provides registered services at runtime.
12. Services are registered in `Program.cs` before `builder.Build()`.
13. Transient creates a new instance every time, Scoped creates one per request, Singleton creates one for the entire application lifetime.
14. `AddScoped` is suitable for `ComplaintService` because it is request-based and will later work with DbContext.
15. ASP.NET Core throws an error saying it is unable to resolve the service for the requested type.
