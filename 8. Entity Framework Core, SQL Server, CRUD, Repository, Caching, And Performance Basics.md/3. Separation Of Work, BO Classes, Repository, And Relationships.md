# 1. Why This Topic Is Important

## What

In the previous topic, we implemented CRUD operations using EF Core.

Now we need to organize the code properly.

If we put everything inside controllers, the application becomes difficult to maintain.

Bad structure:

```text
Controller
↓
Validation
↓
Business rules
↓
EF Core queries
↓
Status history logic
↓
File upload logic
↓
Assignment logic
↓
Database save
```

This creates large, messy controllers.

Better structure:

```text
Controller
↓
Service Layer / BO Layer
↓
Repository Layer
↓
DbContext
↓
Database
```

---

## Why

Enterprise applications need clean separation because:

```text
Code changes frequently
Multiple developers work together
Business rules grow over time
Data access becomes complex
Testing becomes important
Maintenance becomes long-term
Features must be extended safely
```

In the Smart Society Issue Management System, complaint workflow will grow beyond simple CRUD.

It will include:

```text
Resident complaint creation
Admin assignment
Staff status update
Complaint comments
Attachments
Status timeline
Dashboard reports
Ownership-based access
Audit trail
```

So we need maintainable organization.

---

## Smart Society Mapping

Move complaint operations into:

```text
IComplaintService
ComplaintService
IComplaintRepository
ComplaintRepository
```

Controller should not directly contain EF Core queries.

---

The receptionist should not personally:


The receptionist coordinates.

Different departments handle different responsibilities.

Similarly:

```text

```

# 2. Separation Of Work Using BO Classes / Service Classes

## What

Separation of work means each class should have a clear responsibility.

A **BO class** usually means **Business Object** or **Business Operation** class depending on organization terminology.

In modern ASP.NET Core applications, we commonly call this:

```text
Service class
Business service
Application service
Domain service
```

For this course, we will treat BO/service class as the class that contains business logic.

---

## Why

Business logic should not be scattered across controllers.

Example business rules:

```text
New complaint should always start with New status
Resident should not assign complaint
Admin can assign complaint to staff
Status update should create status history
Resolved complaint should store resolved date
Archived complaint should not appear in active list
Staff can update only assigned complaints
```

These rules belong in service/BO layer, not directly inside controller.

---

## Bad Controller-Heavy Design

```csharp
[HttpPost]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    var complaint = new Complaint
    {
        Title = model.Title,
        Description = model.Description,
        Category = model.Category,
        Priority = model.Priority,
        Status = "New",
        CreatedDate = DateTime.UtcNow
    };

    await _context.Complaints.AddAsync(complaint);
    await _context.SaveChangesAsync();

    return RedirectToAction(nameof(Index));
}
```

Problem:

```text
Controller knows business rules
Controller knows EF Core
Controller knows database save logic
Controller becomes hard to test
Controller grows quickly
```

---

## Better Service-Based Design

Controller:

```csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(ComplaintCreateViewModel model)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    var userId = User.FindFirst(System.Security.Claims.ClaimTypes.NameIdentifier)?.Value;

    if (string.IsNullOrWhiteSpace(userId))
    {
        return Unauthorized();
    }

    await _complaintService.CreateComplaintAsync(model, userId);

    TempData["SuccessMessage"] = "Complaint created successfully.";

    return RedirectToAction(nameof(Index));
}
```

Service:

```csharp
public async Task CreateComplaintAsync(
    ComplaintCreateViewModel model,
    string createdByUserId)
{
    var complaint = new Complaint
    {
        Title = model.Title,
        Description = model.Description,
        Category = model.Category,
        Priority = model.Priority,
        Status = "New",
        CreatedByUserId = createdByUserId,
        CreatedDate = DateTime.UtcNow
    };

    await _complaintRepository.AddAsync(complaint);
    await _complaintRepository.SaveChangesAsync();
}
```

---

## Smart Society Separation

| Layer | Responsibility |
|---|---|
| Controller | Receive request, check ModelState, call service, return response |
| Service / BO | Apply business rules and workflow decisions |
| Repository | Query and persist data |
| DbContext | Track changes and communicate with database |
| Database | Store permanent data |

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Putting all logic in controller | Move business logic to service |
| Putting business decisions in repository | Keep repository focused on data access |
| Service returning Razor View | Service should return data/result, not UI |
| Controller directly using DbContext everywhere | Use service/repository structure |
| Creating too many layers without purpose | Keep separation practical and useful |

---

## Interview Line

**BO or service classes contain business logic and keep controllers clean by handling rules such as complaint creation, assignment, status update, and archive workflow.**

# 3. Service Layer

## What

The service layer contains business operations.

In Smart Society, `ComplaintService` is responsible for complaint-related business rules.

---

## Why

The service layer protects the application from scattered logic.

It ensures that complaint workflow rules are applied consistently.

For example:

```text
Every new complaint starts as New
Every status update creates history
Every assignment sets AssignedDate
Every archive sets IsArchived
Every user access rule is checked consistently where needed
```

---

## IComplaintService

```csharp
using SmartSociety.Web.Models;
using SmartSociety.Web.ViewModels;

namespace SmartSociety.Web.Interfaces
{
    public interface IComplaintService
    {
        Task CreateComplaintAsync(ComplaintCreateViewModel model, string createdByUserId);

        Task<List<Complaint>> GetComplaintsForResidentAsync(string residentUserId);

        Task<List<Complaint>> GetAllComplaintsAsync();

        Task<List<Complaint>> GetAssignedComplaintsAsync(string staffUserId);

        Task<Complaint?> GetComplaintDetailsAsync(int complaintId);

        Task<Complaint?> GetResidentComplaintDetailsAsync(int complaintId, string residentUserId);

        Task AssignComplaintAsync(int complaintId, string staffUserId, string adminUserId);

        Task UpdateComplaintStatusAsync(
            int complaintId,
            string newStatus,
            string changedByUserId,
            string? remarks);

        Task ArchiveComplaintAsync(int complaintId, string archivedByUserId);
    }
}
```

---

## ComplaintService Responsibility

```text
Convert ViewModel to entity
Set system-controlled fields
Apply workflow rules
Call repository methods
Create status history records
Control archive behavior
Coordinate related operations
Log important business events
```

---

## Service Example

```csharp
using SmartSociety.Web.Interfaces;
using SmartSociety.Web.Models;
using SmartSociety.Web.ViewModels;

namespace SmartSociety.Web.Services
{
    public class ComplaintService : IComplaintService
    {
        private readonly IComplaintRepository _complaintRepository;
        private readonly ILogger<ComplaintService> _logger;

        public ComplaintService(
            IComplaintRepository complaintRepository,
            ILogger<ComplaintService> logger)
        {
            _complaintRepository = complaintRepository;
            _logger = logger;
        }

        public async Task CreateComplaintAsync(
            ComplaintCreateViewModel model,
            string createdByUserId)
        {
            var complaint = new Complaint
            {
                Title = model.Title,
                Description = model.Description,
                Category = model.Category,
                Priority = model.Priority,
                Status = "New",
                CreatedByUserId = createdByUserId,
                CreatedDate = DateTime.UtcNow
            };

            await _complaintRepository.AddAsync(complaint);
            await _complaintRepository.SaveChangesAsync();

            _logger.LogInformation(
                "Complaint created. ComplaintId: {ComplaintId}",
                complaint.ComplaintId);
        }

        public async Task<List<Complaint>> GetComplaintsForResidentAsync(string residentUserId)
        {
            return await _complaintRepository
                .GetComplaintsForResidentAsync(residentUserId);
        }

        public async Task<List<Complaint>> GetAllComplaintsAsync()
        {
            return await _complaintRepository.GetAllActiveComplaintsAsync();
        }

        public async Task<List<Complaint>> GetAssignedComplaintsAsync(string staffUserId)
        {
            return await _complaintRepository.GetAssignedComplaintsAsync(staffUserId);
        }

        public async Task<Complaint?> GetComplaintDetailsAsync(int complaintId)
        {
            return await _complaintRepository.GetComplaintDetailsAsync(complaintId);
        }

        public async Task<Complaint?> GetResidentComplaintDetailsAsync(
            int complaintId,
            string residentUserId)
        {
            return await _complaintRepository
                .GetResidentComplaintDetailsAsync(complaintId, residentUserId);
        }

        public async Task AssignComplaintAsync(
            int complaintId,
            string staffUserId,
            string adminUserId)
        {
            var complaint = await _complaintRepository.GetByIdAsync(complaintId);

            if (complaint == null || complaint.IsArchived)
            {
                throw new InvalidOperationException("Complaint not found.");
            }

            var oldStatus = complaint.Status;

            complaint.AssignedToStaffId = staffUserId;
            complaint.AssignedDate = DateTime.UtcNow;
            complaint.Status = "Assigned";

            var history = new ComplaintStatusHistory
            {
                ComplaintId = complaint.ComplaintId,
                OldStatus = oldStatus,
                NewStatus = "Assigned",
                ChangedByUserId = adminUserId,
                ChangedDate = DateTime.UtcNow,
                Remarks = "Complaint assigned to staff."
            };

            await _complaintRepository.AddStatusHistoryAsync(history);
            await _complaintRepository.SaveChangesAsync();

            _logger.LogInformation(
                "Complaint assigned. ComplaintId: {ComplaintId}, StaffUserId: {StaffUserId}",
                complaintId,
                staffUserId);
        }

        public async Task UpdateComplaintStatusAsync(
            int complaintId,
            string newStatus,
            string changedByUserId,
            string? remarks)
        {
            var complaint = await _complaintRepository.GetByIdAsync(complaintId);

            if (complaint == null || complaint.IsArchived)
            {
                throw new InvalidOperationException("Complaint not found.");
            }

            var oldStatus = complaint.Status;

            complaint.Status = newStatus;

            if (newStatus == "Resolved")
            {
                complaint.ResolvedDate = DateTime.UtcNow;
            }

            var history = new ComplaintStatusHistory
            {
                ComplaintId = complaint.ComplaintId,
                OldStatus = oldStatus,
                NewStatus = newStatus,
                ChangedByUserId = changedByUserId,
                ChangedDate = DateTime.UtcNow,
                Remarks = remarks
            };

            await _complaintRepository.AddStatusHistoryAsync(history);
            await _complaintRepository.SaveChangesAsync();

            _logger.LogInformation(
                "Complaint status updated. ComplaintId: {ComplaintId}, OldStatus: {OldStatus}, NewStatus: {NewStatus}",
                complaintId,
                oldStatus,
                newStatus);
        }

        public async Task ArchiveComplaintAsync(
            int complaintId,
            string archivedByUserId)
        {
            var complaint = await _complaintRepository.GetByIdAsync(complaintId);

            if (complaint == null || complaint.IsArchived)
            {
                throw new InvalidOperationException("Complaint not found.");
            }

            complaint.IsArchived = true;
            complaint.ArchivedDate = DateTime.UtcNow;
            complaint.ArchivedByUserId = archivedByUserId;

            await _complaintRepository.SaveChangesAsync();

            _logger.LogInformation(
                "Complaint archived. ComplaintId: {ComplaintId}",
                complaintId);
        }
    }
}
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Service only passes data without purpose | Service should apply business rules |
| Service directly returns IActionResult | Controller returns IActionResult |
| Service becomes too large | Split services by feature when needed |
| Service does not use interface | Use interface for DI/testability |
| Service hides exceptions without logging | Log and handle appropriately |

---

## Interview Line

**The service layer contains business operations and coordinates workflow rules while delegating data access to repositories.**

# 4. Repository Pattern

## What

Repository pattern creates a separate class responsible for data access.

Simple meaning:

```text
Repository hides EF Core query details from the service layer.
```

Example:

```text
ComplaintService asks repository for complaints.
ComplaintRepository uses DbContext to query SQL Server.
```

---

## Why

Repository pattern can help with:

```text
Centralizing data access queries
Keeping services cleaner
Reusing query logic
Improving testability in some cases
Separating business logic from data access details
```

---

## Smart Society Repository Structure

```text
Repositories
│
├── IComplaintRepository.cs
└── ComplaintRepository.cs
```

---

## IComplaintRepository

```csharp

        Task<Complaint?> GetComplaintDetailsAsync(int complaintId);
```

## ComplaintRepository

```csharp
using Microsoft.EntityFrameworkCore;
using SmartSociety.Web.Data;
using SmartSociety.Web.Models;

namespace SmartSociety.Web.Repositories
{
    public class ComplaintRepository : IComplaintRepository
    {
        private readonly ApplicationDbContext _context;

        public ComplaintRepository(ApplicationDbContext context)
        {
            _context = context;
        }

        public async Task AddAsync(Complaint complaint)
        {
            await _context.Complaints.AddAsync(complaint);
        }

        public async Task<Complaint?> GetByIdAsync(int complaintId)
        {
            return await _context.Complaints
                .FirstOrDefaultAsync(c => c.ComplaintId == complaintId);
        }

        public async Task<List<Complaint>> GetComplaintsForResidentAsync(
            string residentUserId)
        {
            return await _context.Complaints
                .Where(c => c.CreatedByUserId == residentUserId && !c.IsArchived)
                .OrderByDescending(c => c.CreatedDate)
                .ToListAsync();
        }

        public async Task<List<Complaint>> GetAllActiveComplaintsAsync()
        {
            return await _context.Complaints
                .Include(c => c.CreatedByUser)
                .Include(c => c.AssignedToStaff)
                .Where(c => !c.IsArchived)
                .OrderByDescending(c => c.CreatedDate)
                .ToListAsync();
        }

        public async Task<List<Complaint>> GetAssignedComplaintsAsync(
            string staffUserId)
        {
            return await _context.Complaints
                .Include(c => c.CreatedByUser)
                .Where(c => c.AssignedToStaffId == staffUserId && !c.IsArchived)
                .OrderByDescending(c => c.CreatedDate)
                .ToListAsync();
        }

        public async Task<Complaint?> GetComplaintDetailsAsync(int complaintId)
        {
            return await _context.Complaints
                .Include(c => c.CreatedByUser)
                .Include(c => c.AssignedToStaff)
                .Include(c => c.Comments)
                .Include(c => c.Attachments)
                .Include(c => c.StatusHistory)
                .FirstOrDefaultAsync(c =>
                    c.ComplaintId == complaintId &&
                    !c.IsArchived);
        }

        public async Task<Complaint?> GetResidentComplaintDetailsAsync(
            int complaintId,
            string residentUserId)
        {
            return await _context.Complaints
                .Include(c => c.Comments)
                .Include(c => c.Attachments)
                .Include(c => c.StatusHistory)
                .FirstOrDefaultAsync(c =>
                    c.ComplaintId == complaintId &&
                    c.CreatedByUserId == residentUserId &&
                    !c.IsArchived);
        }

        public async Task AddStatusHistoryAsync(
            ComplaintStatusHistory statusHistory)
        {
            await _context.ComplaintStatusHistories.AddAsync(statusHistory);
        }

        public async Task AddCommentAsync(ComplaintComment comment)
        {
            await _context.ComplaintComments.AddAsync(comment);
        }

        public async Task AddAttachmentAsync(ComplaintAttachment attachment)
        {
            await _context.ComplaintAttachments.AddAsync(attachment);
        }

        public async Task SaveChangesAsync()
        {
            await _context.SaveChangesAsync();
        }
    }
}
```

---

```csharp

```

Also ensure service is registered:

| Mistake | Correction |
|---|---|
| Repository contains business workflow rules | Keep business logic in service |
| Repository returns ViewModels for every UI | Prefer service/projection layer decisions |
| Repository hides all EF Core capability badly | Keep repository useful, not restrictive |

# 5. Writing Generic Class / Repository

## What

A generic repository is a reusable repository class that works with multiple entity types.

Example:

```text
GenericRepository<T>
```

can work with:

```text
Complaint
ComplaintComment
ComplaintAttachment
ComplaintStatusHistory
```

---

## Why

Generic repositories reduce repetitive code for common operations such as:

```text
Add
GetById
List
Update
Delete
Save
```

---

## IGenericRepository

```csharp
namespace SmartSociety.Web.Repositories
{
    public interface IGenericRepository<T> where T : class
    {
        Task AddAsync(T entity);

        Task<T?> GetByIdAsync(int id);

        Task<List<T>> GetAllAsync();

        void Update(T entity);

        void Remove(T entity);

        Task SaveChangesAsync();
    }
}
```

---

## GenericRepository

```csharp
using Microsoft.EntityFrameworkCore;
using SmartSociety.Web.Data;

namespace SmartSociety.Web.Repositories
{
    public class GenericRepository<T> : IGenericRepository<T>
        where T : class
    {
        private readonly ApplicationDbContext _context;
        private readonly DbSet<T> _dbSet;

        public GenericRepository(ApplicationDbContext context)
        {
            _context = context;
            _dbSet = _context.Set<T>();
        }

        public async Task AddAsync(T entity)
        {
            await _dbSet.AddAsync(entity);
        }

        public async Task<T?> GetByIdAsync(int id)
        {
            return await _dbSet.FindAsync(id);
        }

        public async Task<List<T>> GetAllAsync()
        {
            return await _dbSet.ToListAsync();
        }

        public void Update(T entity)
        {
            _dbSet.Update(entity);
        }

        public void Remove(T entity)
        {
            _dbSet.Remove(entity);
        }

        public async Task SaveChangesAsync()
        {
            await _context.SaveChangesAsync();
        }
    }
}
```

---

## Register Generic Repository

```csharp
builder.Services.AddScoped(typeof(IGenericRepository<>), typeof(GenericRepository<>));
```

---

## When Generic Repository Helps

Useful for:

```text
Simple common CRUD operations
Admin maintenance screens
Small utility data access
Reducing repetitive Add/Get/List methods
```

---

## When Specific Repository Is Better

Specific repository is better when query logic is business-specific.

Example:

```text
Get complaints for resident
Get assigned complaints for staff
Get complaint details with comments, attachments, and history
Get active complaints excluding archived records
```

These are better in `IComplaintRepository`.

---

## Recommended Approach For Smart Society

Use both carefully:

```text
GenericRepository for simple common operations
ComplaintRepository for complaint-specific queries
```

But for this course, keep focus on:

```text
IComplaintRepository
ComplaintRepository
```

because it maps better to real project workflows.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forcing all queries into generic repository | Use specific repository for complex queries |
| Generic repository hides Include/filtering needs | Add specific methods where needed |
| Calling Update blindly from generic repo | Prefer safe update pattern |
| Creating generic repository without business need | Keep it practical |
| Duplicating DbContext behavior unnecessarily | Understand DbContext already provides generic access |

---

## Interview Line

**A generic repository provides reusable data access methods for multiple entity types, but business-specific queries should remain in specific repositories such as ComplaintRepository.**

# 6. Repository Mistakes

## What

Repository pattern is useful, but it can be misused.

---

## Mistake 1: Putting Business Logic In Repository

Bad:

```csharp
public async Task AssignComplaintAsync(...)
{
    // Business rules
    // Role checks
    // Status workflow decisions
    // Notification decisions
}
```

Better:

```text
Service handles business workflow.
Repository handles database query/save.
```

---

## Mistake 2: Repository Saves Automatically Everywhere

Bad:

```csharp
public async Task AddAsync(Complaint complaint)
{
    await _context.Complaints.AddAsync(complaint);
    await _context.SaveChangesAsync();
}
```

Problem:

```text
Service cannot coordinate multiple related changes in one save.
```

Better:

```csharp
await _context.Complaints.AddAsync(complaint);
```

and service calls:

```csharp
await _complaintRepository.SaveChangesAsync();
```

after all related operations.

---

## Mistake 3: Creating Too Many Repositories

Bad structure:

```text
IComplaintTitleRepository
IComplaintStatusRepository
IComplaintPriorityRepository
```

Better:

```text
IComplaintRepository
```

Group related data access by aggregate/feature.

---

## Mistake 4: Hiding EF Core Too Much

A repository should not make queries harder.

If every useful query requires complex workaround, repository design is poor.

---

## Mistake 5: Ignoring DbContext's Built-In Unit Of Work

EF Core DbContext already tracks changes and saves them together.

Repository should not fight DbContext.

---

## Smart Society Practical Rule

```text
Use repository to organize complaint data access.
Use service to organize complaint business workflow.
Use DbContext to coordinate tracked changes and SaveChanges.
```

---

## Common Mistake Table

| Mistake | Why It Is Wrong | Correction |
|---|---|---|
| Business rules in repository | Mixed responsibilities | Put rules in service |
| SaveChanges inside every repository method | Breaks workflow transaction control | Save once from service |
| Generic repository for every query | Restrictive | Use specific repository |
| Repository returns IActionResult | Repository should not know MVC | Return entities/data |
| Controller bypasses service and calls repository directly | Business rules skipped | Controller should call service |

---

## Interview Line

**Common repository mistakes include putting business logic in repositories, saving too early, overusing generic repositories, and bypassing the service layer.**

# 7. DbContext As Unit Of Work

## What

Unit of Work means grouping multiple database changes and saving them together as one operation.

EF Core `DbContext` already behaves like a Unit of Work.

---

## Why

Many business operations involve multiple changes.

Example: Assign complaint.

```text
Update complaint AssignedToStaffId
Update complaint Status
Create ComplaintStatusHistory
Save all together
```

These changes should succeed together.

---

## DbContext Unit Of Work Flow

```text
Load complaint
↓
Modify complaint
↓
Add status history
↓
DbContext tracks all changes
↓
SaveChangesAsync saves everything together
```

---

## Smart Society Example

```csharp
complaint.AssignedToStaffId = staffUserId;
complaint.AssignedDate = DateTime.UtcNow;
complaint.Status = "Assigned";

var history = new ComplaintStatusHistory
{
    ComplaintId = complaint.ComplaintId,
    OldStatus = oldStatus,
    NewStatus = "Assigned",
    ChangedByUserId = adminUserId,
    ChangedDate = DateTime.UtcNow
};

await _complaintRepository.AddStatusHistoryAsync(history);

await _complaintRepository.SaveChangesAsync();
```

One save persists both:

```text
Complaint update
Status history insert
```

---

## Why Not Save Too Early

Bad:

```text
Save complaint assignment
Then try to save status history
Status history fails
Complaint assignment already saved
```

This creates inconsistent workflow.

Better:

```text
Track both changes
Save once
```

---

## Important Note

For very complex workflows, explicit database transactions may be needed.

But for many EF Core operations, one DbContext with SaveChangesAsync is enough.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Calling SaveChanges after every small change | Save once after related changes |
| Creating multiple DbContext instances unnecessarily | Use scoped DbContext |
| Thinking repository itself is always Unit of Work | DbContext is already Unit of Work |
| Not understanding EF change tracking | Learn tracked entity updates |
| Splitting related workflow changes across unrelated saves | Coordinate in service |

---

## Interview Line

**DbContext acts as a Unit of Work because it tracks multiple entity changes and saves them together when SaveChangesAsync is called.**

# 8. One-To-Many Relationships

## What

One-to-many relationship means one record in a table is related to many records in another table.

---

## Smart Society Relationships

```text
One Complaint has many Comments
One Complaint has many Attachments
One Complaint has many Status History records
```

---

## Relationship Diagram

```text
Complaint
   │
   ├── Many ComplaintComments
   │
   ├── Many ComplaintAttachments
   │
   └── Many ComplaintStatusHistory
```

---

## Why

A complaint is not just one row.

It can have:

```text
Multiple comments
Multiple uploaded files
Multiple status changes
```

So we need related tables.

---

## Example

Complaint:

```text
ComplaintId = 10
Title = Lift not working
```

Comments:

```text
Comment 1 → ComplaintId = 10
Comment 2 → ComplaintId = 10
Comment 3 → ComplaintId = 10
```

# 14. EF Core Relationship Configuration Awareness

## What

EF Core can infer many relationships from foreign keys and navigation properties.

But sometimes we configure relationships explicitly using `OnModelCreating`.

---

## Why

Explicit configuration helps when:

```text
Multiple relationships point to ApplicationUser
Cascade delete creates SQL Server errors
Delete behavior must be controlled
Table relationships need clarity
```

---

## Smart Society OnModelCreating Example

```csharp
protected override void OnModelCreating(ModelBuilder builder)
{
    base.OnModelCreating(builder);

    builder.Entity<Complaint>()
        .HasOne(c => c.CreatedByUser)
        .WithMany()
        .HasForeignKey(c => c.CreatedByUserId)
        .OnDelete(DeleteBehavior.Restrict);

    builder.Entity<Complaint>()
        .HasOne(c => c.AssignedToStaff)
        .WithMany()
        .HasForeignKey(c => c.AssignedToStaffId)
        .OnDelete(DeleteBehavior.Restrict);

    builder.Entity<ComplaintComment>()
        .HasOne(c => c.CreatedByUser)
        .WithMany()
        .HasForeignKey(c => c.CreatedByUserId)
        .OnDelete(DeleteBehavior.Restrict);

    builder.Entity<ComplaintAttachment>()
        .HasOne(a => a.UploadedByUser)
        .WithMany()
        .HasForeignKey(a => a.UploadedByUserId)
        .OnDelete(DeleteBehavior.Restrict);

    builder.Entity<ComplaintStatusHistory>()
        .HasOne(h => h.ChangedByUser)
        .WithMany()
        .HasForeignKey(h => h.ChangedByUserId)
        .OnDelete(DeleteBehavior.Restrict);
}
```

---

## Why Restrict Delete?

If a user is deleted, we usually do not want all complaint history to disappear.

Better:

```text
Restrict delete
Deactivate user instead of deleting
Preserve complaint audit history
```

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Ignoring cascade delete issues | Configure delete behavior |
| Forgetting base.OnModelCreating with Identity | Always call base first |
| Deleting users with complaint history | Prefer deactivate user |
| Not configuring multiple user relationships | Configure explicitly |
| Applying cascade delete blindly | Preserve audit history |

---

## Interview Line

**EF Core relationships can be configured explicitly in OnModelCreating to control foreign keys, navigation properties, and delete behavior.**

## Why Scoped?

Repositories and services use DbContext.

DbContext is scoped per request.

So service and repository should also be scoped.

---

## Common Mistake

| Mistake | Correction |
|---|---|
| Forgetting repository registration | DI error occurs |
| Registering repository as Singleton | DbContext lifetime mismatch |
| Registering service but not repository | Service cannot be created |
| Injecting concrete repository instead of interface | Prefer interface |
| Multiple registrations with confusion | Keep DI clean and explicit |
